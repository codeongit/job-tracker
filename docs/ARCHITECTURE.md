# 架构与维护边界

## 运行方式

界面使用静态 HTML/CSS/ES modules，`dist/` 是直接维护的公开源码，也是唯一公开发布目录，没有构建阶段。无第三方运行依赖；Prettier 和 Playwright 仅用于开发检查。Node 24 LTS 用于本机服务和测试，pnpm 精确版本及依赖由 `package.json`、`pnpm-lock.yaml` 固定。

v0.8.0 区分两种模式：本机模式由服务保存唯一正式工作区，浏览器 IndexedDB 是缓存，草稿仍在浏览器；手机/公开静态模式继续由自己的 IndexedDB 独立保存。两种模式只通过用户明确发起的 GitHub 同步交换共享数据。已选择本机模式后，服务不可用只允许读取缓存和保留草稿，不能静默退回独立正式写入。干净的新浏览器可读取同一服务；若浏览器已有不同 IndexedDB 或曾绑定其他工作区，先拒绝缓存覆盖，只有下载完整备份并明确切换后才采用服务正式数据。

## 草稿与磁盘模块

- `dist/draft-data.js`：草稿字段白名单、原记录基线校验；设置/PAT 不属于草稿。
- `dist/drafts.js`：输入时同步写入 localStorage，草稿使用页面拥有的 ID 和不可变版本键；恢复时创建新 ID，清理仅删除精确版本，避免影响另一页的新输入。满200份或配额错误明确提示。
- `dist/disk-backup.js`：读取完整状态并合并草稿，2.5秒聚合、30秒重试、Web Locks 协调同源页面；仅有内容变化或跨日才写入。读取状态不会触发“已保存”循环。
- `scripts/disk-backups.mjs`：固定私有目录、来源 UUID 分隔、50MB完整备份上限；临时文件 fsync 后独占建立每日首份，再原子替换 latest，成功后保留30个日期。普通目录权限0700、文件0600，拒绝符号链接和任意路径。

备份会话独立于 SSH 能力，同样校验 Host、Origin 与随机会话。恢复备份先预检并准备整批草稿，失败时删除本批新副本；工作区恢复成功后才完成草稿导入。不自动正式提交草稿或上传 GitHub。

## 数据流

岗位资料判断由 `collector/boss/job-evidence.mjs` 共用：仅对调用方已选关联执行精确岗位 ID／规范链接匹配、证据排序、详情矛盾和人工确认匹配。采集展示、详情交付、旧消息身份映射采用三个固定用途；旧映射保留加载名称优先、招聘方匹配、原文字比较和缺省值，避免改变旧事件 ID。现代用途保留详情优先及规范化矛盾判断，各自的输出缺省值保持。会话关联选择、列表外资料资格、输出格式与哈希仍在原模块；资料判断不执行 I/O、不改写输入，也不证明简历归属。

本机用户保存 → 读取正式 revision → 页面生成最小白名单业务变更 → 服务重跑校验与所有权规则 → 固定命令 CAS 写入不可变完整工作区及 catalog → 原子更新包含两者指针的 HEAD → 更新浏览器缓存。网页不能调用服务内部整库提交，也不能用人工编辑改写来源账本。静态用户保存仍通过 IndexedDB 事务。两者均保持“待同步 → 用户手动读取远端 → base/local/remote 合并 → 确认实际上传快照”的云同步流程；本机 SSH 额外由服务为每次真实读取签发一次性事务，绑定正式 revision、远端 SHA 和计划摘要，实际 PUT 前再次核对写者、目标、基线和 pending，成功后才允许用事务 ID 确认，网页不回传 captured/uploaded 整库。已有同步基线时远端文件缺失或远端单边转移本机 BOSS 账号身份在服务端停止/形成冲突；HEAD 原子替换已可见但目录 fsync 报错时核对完整根并只重试持久化屏障，持续失败隔离写者且不确认提交。上传期间的新正式编辑在服务端以签发快照为基线重基，仍保持待同步。

本机客户端的普通编辑与固定操作共用一条内部命令交付流程：在同一串行队列内读取正式状态，核对显式审阅的 revision，再计算业务差异或准备固定请求。无变化的普通编辑直接返回，不生成 commandId；实际提交只生成一次 commandId，底层请求用同一 ID、revision 和 payload 精确重试。版本冲突刷新缓存后报错，不重新计算编辑或自动跟随新版本；旧幂等结果先读取当前正式工作区再缓存。缓存写入失败仍返回已确认的正式结果。首次迁移继续使用原有独立备份预检，静态模式和平台请求不采用这条命令流程。

本机服务控制 module 共用运行记录中的端口和身份执行健康检查，返回固定原因及耗时；doctor 只读取该 interface 的已验证版本、SSH 状态或未确认原因。只有 start 对仍存活进程的超时／连接拒绝允许一次有界补查，补查重新读取身份，不重置首次启动等待窗口；明确身份矛盾以固定错误结束。失败 start 的诊断写入仅在现有私有日志追加最小摘要，不额外修改运行记录、启动意图、工作区或 BOSS 授权；status 和 doctor 不写诊断。原运行记录与命令协议格式保持。

BOSS 只读接入是另一条本机入口：用户明确开始跟踪 → 仓库内固定 `collector/boss/` 采集器 → 不可变快照 → 确定性批次 → 私有队列 → 本机单写者提交岗位、来源事实、应用结果和命令回执元数据 → 提交成功后确认队列。页面关闭不阻止正式录入；服务启动只处理本地队列，不访问 BOSS，服务重启不自动恢复跟踪。正常链路不调用模型，GitHub 仍只有人工触发同步。采集器进程继续与工作台服务隔离，但源码、协议和测试同仓版本化；私有运行材料固定在 `.local/boss-collector/`。

账号 namespace 与稳定服务工作区 ID 先确认绑定，初次迁移转换 data、pending 本机候选及冲突中两个可选 live 结果的旧浏览器归属；同步基线、pending remote 数据集与冲突 base 保留迁移前云端身份，首次同步据此上传新绑定。会话以账号 namespace、`friendId`、`friendSource` 标识，并核对 `uniqueId`；姓名和公司不能替代稳定身份主键。岗位以账号范围内的平台岗位 ID/规范链接精确关联，多个会话可指向同岗位；同一会话换岗时不继承旧岗位名称、确认状态或业务阶段。已有人工岗位的日期和字段不覆盖，主动清空也保留人工所有权。来源账本的 sourceFacts 与 sourceApplications 分别记录事实及规则应用，旧 sourceEvents 保留；缺稳定消息 ID 时只保留等待证据，不创建岗位或语义事实。缺证据为 waiting、人工保护为 protected、真正身份歧义为 review，不都要求人工重核。受同步冲突影响的岗位和依赖延后，无关岗位仍可提交；重基时新发现的岗位冲突会自动重新求解为等待项，只有账号或无法隔离的结构冲突才中止整批。旧观察不回退新状态，不复活已删除岗位。精确简历白名单可按 D025 联动本机消息和阶段，普通平台回执仍不冒充人工消息状态。

首批导入继续锁定 2026-09-18 快照、`Asia/Shanghai` 和用户指定首次联系日，只纳入 30 条时分记录；10 条“昨天”和 60 条空标签不推断日期。持续跟踪不复用首批筛选，新岗位无可靠首次联系日则留空。平台访问、显式授权和隐私边界见 [操作规约](AUTOMATION_POLICY.md)；调度、动作预算及阶段暂停/恢复规则统一见 [BOSS 接入设计](BOSS_AUTOMATION_DESIGN.md#频率与实际动作预算)。

当前增量列表的明确 `HH:mm` 标签，以原快照 `capturedAt` 对应的上海日期作为证据日期和新岗位首次联系日；延迟入库或恢复不改为执行当天。“昨天”、空标签及其他不可靠日期留空，已有岗位的首次联系日、人工阶段和删除标记保持。列表外详情补交的时间边界见下方“详情读取与列表外交付修正”，不能用新快照时间重新解释旧标签。

“行动”沿用 `today.js` 的纯分组规则：今天展示今天到期和逾期待办，接下来按日期展示未来待办，待整理分组展示核实项、无日期待办和未设下一步的岗位。以本地 `createdAt` 判断“今天新增”，今天页的数量入口直达待整理中的这些岗位。核实按问题展开，无关待办不遮挡核实项；确认写入已有状态/沟通记录，稍后处理写入当天待办，完成该待办时使用相同确认语义。固定文案和写入规则仍由 `today.js` 集中维护。

页面、行动页签、筛选、页码、各视图滚动位置与详情选中项独立维护在页面内存中。岗位详情默认关闭；打开、关闭、保存、恢复草稿或切换页面不重置查询。主动修改筛选才将列表重置到第一页，结果减少则收敛到最后有效页。关闭详情恢复来源位置及焦点；触发控件已消失则聚焦结果标题。刷新不恢复浏览会话，默认进入行动今天且岗位筛选为空。详情与查询结果独立：编辑后不再匹配时保留详情并提示，删除岗位时关闭详情。桌面以大于 760px 为右侧详情面板，手机使用全页详情。

岗位详情通过 `planning.js` 从结构化的招聘阶段、简历状态和面试活动生成可编辑的下一步预填；已有待办、已结束或暂缓时不预填。日期从浏览器本地 `today()` 开始按日历日进位，避免跨时区或夏令时的毫秒换算偏差。表单默认值先渲染再绑定草稿，已保存草稿和用户输入优先；未修改的默认值在同步、跨标签更新和提交事务中重新核对，任务仍需用户明确提交。

岗位列表调用 `getFilteredOpportunities(data, { query, stage, date })`，结果为排序后的 `{ opportunity, dailyRecord }` 数组。关键词忽略大小写匹配公司、岗位或联系人，阶段匹配当前阶段，所有条件取交集。无日期时按未删除岗位的 `createdAt` 实际时间倒序并返回 `dailyRecord: null`，包含已结束和无日期岗位；缺失或无效添加时间排在最后，同时间及无有效时间的记录保留原相对顺序，不以 `updatedAt` 或 `appliedAt` 替代，不修改源数组。指定日期时复用 `daily.js` 的岗位分组和排序。排序后分页，列表每页 10 个结果。

新增岗位的同公司提示调用纯查询 `findCompanyMatches(data, { company, role, excludeId })`。公司和岗位分别经 NFKC、首尾空白、连续空白及英文大小写规范化；公司只做完全匹配，不删除企业后缀或做包含匹配。查询使用未删除岗位并保留已结束岗位，同岗位排在前面，其余保持原顺序。新增及新增草稿恢复时绑定公司、岗位的已提交输入，只更新专用提示节点；中文组合输入结束后及跨标签状态刷新时重新计算，不重建表单或改变草稿。提示最多呈现 3 条和总数，不参与校验或阻止提交。

`getOpportunityStatus(opportunity)` 集中处理人工状态兼容：旧“待联系”按“已触达”使用，人工消息状态保留“已读”，其余按“未读”使用。表单仅提供五个当前招聘阶段和“未读、已读”两种人工消息状态；自动接入且没有人工消息状态的岗位在列表与详情中显示独立“平台观察”，避免缺省值看似平台确认的未读。`validateData` 继续接受旧“待联系”，不改写正式记录、同步 `base`/`pending` 或草稿 `original`；恢复草稿只调整表单呈现，明确保存岗位才写入人工新状态。兼容归并本身不生成阶段变化活动。新 Markdown 导入缺省未读并保留 `rawStatus`。

`getResumeLinkedStatus` 处理 BOSS 简历状态联动：渠道为 BOSS/BOSS直聘（忽略大小写和空格），且简历已发送或对方已接收时，消息设为已读，已触达或旧待联系推进至沟通中，其他阶段保留。编辑器在草稿监听器之前联动表单字段，恢复草稿后及提交时再次应用；渠道自由文本在 change 时处理，中文组合输入期间不联动。原始记录和草稿原版本仍用于并发比较，不自动提交。`getSentResumeStatus` 供沟通记录、核实与行动完成共用，并保留已有“对方已接收”；取消、仅被索要及其他渠道不触发 BOSS 联动。普通读取、Markdown 导入、同步和恢复不批量改写旧记录；BOSS 精确新证据仅经已授权应用规则和字段所有权核对后联动。

`daily.js` 按明确日期筛选并按岗位合并当天事件。计划使用 `dueAt`，完成和取消使用浏览器本地日期下的 `completedAt`，沟通使用 `activities.date`，首次联系使用 `appliedAt`；导入流程生成的同日“首次联系”活动折叠到首次联系里程碑。列表和详情复用事件渲染，不再提供独立每日记录页。历史查询显示当前岗位信息，不推断所选日期的历史阶段；详情中的新沟通默认今天、任务日期继续遵循 `planning.js`，完成/取消保存实际操作时间。

`base` 是最后确认过的云端数据，不是备份。上传期间的新编辑仍待同步。同记录两端同时变化由用户选择；父岗位删除与新增子记录也作为冲突保留。删除使用 `deletedAt`，不能直接移除删除标记，否则其他设备可能复活记录。

## 公开和私有内容

公开仓库只含界面代码、采集器源码、说明和合成测试。IndexedDB、草稿 localStorage、下载备份及整个 `.local/`（包括 workspace、服务身份、backups、boss-integration、boss-collector、config、SSH 缓存）均为私有。采集原始快照、连接状态和浏览器 profile 固定留在 `.local/boss-collector/`；禁止把真实记录、源 Markdown、简历或令牌放入 `dist/`、`collector/` 或测试 fixture。PAT 只在页面内存，SSH key 由系统 Git/SSH 使用。服务仅监听回环地址，写接口校验 Host/Origin、随机会话与协议版本；旧客户端不可绕过工作区协议写本机远端。

本机 SSH 固定目标、独立缓存、普通 push，只修改指定 JSON；不操作 Obsidian 工作树。网页手机访问使用 REST，不能调用本机 SSH key。

## 大小与外部接口

同步上限统一为最终 JSON 文件的 5,000,000 个 UTF-8 字节，上传前在客户端和 SSH 服务端校验。HTTP 外层请求额度允许少量封装开销；下载完整备份独立于同步限额。导入原文会计入文件体积，设置页显示当前体积。暂不自动清理原文或删除标记。

REST 小文件使用 Contents Base64；大文件使用元数据给出的 blob SHA 读取 raw，避免分支变化导致内容和 SHA 不一致。SSH 输出先拼接字节再做严格 UTF-8 解码。

官方接口依据：[Contents](https://docs.github.com/en/rest/repos/contents#get-repository-content)、[Git blobs](https://docs.github.com/en/rest/git/blobs#get-a-blob)。外部 API 有变化时先更新合成测试，再改适配器。

## 简历规则的维护

简历语义以 `dist/resume-rules.js` 的 `RESUME_RULES` 为唯一规则定义。平台观察标识与业务含义分开：旧 `request_sent` / `resume_request_sent` 保留作兼容标识，其含义明确为 `resume_sent`，不能从名称重新推断为“被索要”。枚举校验、转换和展示均读取该定义。当前与兼容历史采集、DOM 补采使用同一纯识别函数的序列化代码；模拟接口响应测试验证生成表达式的执行结果。

状态转换函数只决定已核对观察能否推进简历状态。账号、会话、岗位归属和人工字段所有权仍由接入层验证；来源否决仍由应用账本保存。识别结果不授予岗位归属，也不绕过人工字段保护。未知观察类型拒绝进入规则，普通卡片不提升状态，较高状态不回退。

修改业务含义时先核对用户确认的业务样例与 ADR，再修改规则。测试中的预期业务结果独立写出，不能从规则表自动生成预期值，以免规则与测试一起接受同一误解。保留原始事件及事实 ID；修改持久标识须另做迁移设计。见 [D031](adr/0031-explicit-resume-semantics.md)。

### 卡片模板与发送依据（D044，0.10.15）

平台通用卡片结构不能单独证明简历发送。类型 4 卡片没有明确发送依据时仍按既有卡片观察存档；精确系统文案“附件简历请求已发送”的业务含义保持已发送。采集保存 `resumeEvidence` 的消息类型、固定字段路径及已识别的状态文字，附件文件名替换为固定占位，服务消费重算含义后再执行独立归属与人工字段检查。

私有快照与交付批次升至 v5，历史检查点升至 v3，旧版本仍可读取。旧 `request_sent` 卡片的类型信息只证明它是普通卡片，不把旧分类当作发送证据；旧队列缺少该信息时等待 `resume_semantics_missing`。新证据属于一份独立候选，不拼接身份或语义材料；明确归属冲突保持 review。事件、事实及应用 ID 保持，批次摘要覆盖新增依据；已应用历史不批量回退，用户指认的错误观察通过既有否决命令纠正，否决持续阻止同事实重放。共享数据及各正式外层格式不变，规则 v12。详见 [D044](adr/0044-boss-card-semantics-evidence.md)。

### 已审阅清单的人工简历与阶段纠错（D045/D046，0.10.17）

`correct_boss_resume_semantics` 通过现有版本化本机命令交付，仅接收已审阅的 `applicationIds`；服务依据当前工作区绑定、预期 revision 和持久 commandId 核对整批准入。纯业务规则按来源事实识别全部旧应用映射，确认自动简历字段仍为错误判断维护的已发送，且没有其他有效发送或接收支持后，纠正为未知并保存 `protected / user_rejected_wrong_resume_semantics`。阶段仍由自动维护且当前值与 last-auto 都为“沟通中”、没有人工沟通活动时，同时退回“已触达”；消息已读、人工阶段和面试及后续阶段保持。任一身份或简历准入失败时不保存部分结果。

已是同一语义否决且简历为自动未知的清单可用新命令补偿阶段遗漏，原否决时间与决定不重写；其它保护原因不准入。无变化时服务拒绝新增提交，原 commandId 重试只读取原持久结果，不因修复代码重算。原始观察和事实保持不可变，纯卡片不构成发送支持，同一会话的新消息仍正常处理。该命令是明确清单的人工纠错，不参与自动历史回退或自动选择岗位。

恢复旧备份或快照时保留当前人工否决，并在当前岗位确实已纠正为自动“已触达”时保护阶段，简历已经为未知也执行该检查。原来仅纠正简历的决定不自动扩大为阶段回退；人工值、有效沟通活动、不同事实的真实发送支持保留。保护不补造缺失材料、不复活删除，同事实观察全部缺失或删除时仍保留恢复缺口。共享与私有格式、规则 v12 不变，详见 [D045](adr/0045-boss-reviewed-resume-semantics-correction.md) 与 [D046](adr/0046-boss-resume-correction-linked-stage.md)。

## BOSS 导入收敛（D033，v0.9.0）

正常链路为显式调度 → 采集标准观察 → 统一归属判断 → 业务应用 → 工作区提交。`dist/boss-attribution.js` 集中归属规则和只读摘要；`dist/boss-batch.js` 是服务与页面共用的批次结构、事件身份及摘要定义。`dist/boss-integration.js` 在修改简历及联动字段前重算判定，未验证观察的候选岗位不获得正式关联。

`scripts/boss-conversion.mjs` 负责快照到批次的纯转换，兼容事件 ID 所需的补齐字段仅是候选；`scripts/boss-legacy-import.mjs` 隔离首批固定范围及指定日期策略。原集成脚本保留命令入口、磁盘恢复和入队编排。当前历史分页、增量与回填以及旧整批表达式共用同一联系人/消息读取实现。控制器只负责生命周期和任务编排，采集进度归采集器，交付状态归私有队列，是否应用归来源账本。

证据不足进入 waiting，身份冲突进入 review，并记录固定原因；纯存档卡片从 0.10.12 起按下文 D043 处理。该阶段正式数据为 v3；新私有快照 v4、队列 v3、历史检查点内容 v2 携带依据。批次摘要包含依据，旧批次缺依据的新应用会等待；已应用事实不回退、不重放。新材料可以重评等待项，不额外触发平台请求。DOM/列表无独立归属材料时只保留观察。

本轮不引入会话长期隔离或提醒处理工作流。异常集中展示于本机 BOSS 接入状态，按当前事实应用去重；只读候选标签不代表归属确认。诊断写入由 `scripts/boss-attribution-diagnostics.mjs` 共用，失败中止配套提交。已有样本已部分核对联系人、本人身份与消息参与者，但消息岗位依据仍不足，当前自动简历更新可能全部等待，这不影响原岗位基础资料导入规则。

### 工作区历史内存边界

v0.9.5 保留启动时的完整提交链、哈希和工作区格式校验，但幂等命令索引仅保存提交定位与小型回执，完整工作区只常驻当前 HEAD。v0.10.3 按 D041 改用 HEAD 绑定的持久 catalog，索引仅保存定位而不保留结果；旧命令重试及结果查询按需读取并重新完整校验对应提交，返回原提交结果。回执仍不能代替恢复后的事实存在性检查。

## 跨观察归属上下文（D034，v0.9.7）

统一归属模块的 `buildBossAttributionContext` 由未删除的 BOSS 来源事件和整个批次构建临时消息/会话候选岗位集合，按账号隔离。应用层每批构建一次，不持久化索引，也不把候选集合当成归属证明。普通消息、简历观察及人工否决保留的原始观察均可提供线索。同消息不同候选岗位阻止尚未应用的简历联动；会话岗位变化只在缺少消息岗位身份时增加等待原因，完整且一致的身份仍执行原检查。

采集诊断使用本阶段观察、列表和岗位关联，队列使用整批，正式消费使用当前工作区加整批。缺少全局材料的早期诊断不是最终应用判定；固定原因复用现有归属摘要。已应用/人工保护/人工否决不重评，事件及事实 ID、共享 v3 和私有协议不变。岗位专属会话路径仍未启用。

## 会话关联应用（D035，v0.9.8）

消息自身岗位身份不再是自动简历应用的必要字段；`assessBossAttribution` 仍检查账号、观察绑定、联系人响应和双方参与者，并执行 D034 跨观察检查。有明确消息岗位身份时保持原有一致性检查，没有时以既有会话候选作为应用依据，返回 attribution_conversation_association。应用层仍要求该岗位唯一绑定且未删除；会话岗位变化或跨岗位重复不能由此绕过。

内部 verified 表示满足选定规则，不表示平台消息自带岗位身份。成功应用与无效果记录的原因追加 conversation_association，保护和否决原因保持。新观察、等待项、补录与明确恢复重放统一处理，不建立新增消息基线。共享 v3、事件/事实 ID 与私有协议不变；旧材料缺完整联系人/参与者依据仍等待。本节按 D035 调整上文 D033 的消息岗位必填要求，不宣称已证明历史按岗位隔离。

## 历史等待与人工忽略（0.9.16）

普通观察缺标题可按完整的账号/岗位 ID/链接唯一绑定完成关联，原始观察不补写推断资料。来源应用的 protected + user_ignored_unresolved_observation 是持久人工忽略，同一事实各入口均在业务变更前跳过；原始观察继续参与跨岗位上下文。设置页只读列出等待原因，用户多选确认后调用固定 ignore_boss_observations 命令。已忽略独立计数。

## 等待观察复用本机资料（0.9.19）

普通缺标题观察在共用业务应用模块核对唯一现有岗位 ID、平台链接、公司、账号绑定与删除标记，满足条件时只建立非自动字段绑定，不改岗位字段。无唯一绑定的观察卡片提供本机候选详情入口；同公司候选仅用于人工导航，不参与自动归属。简历观察继续执行原归属关卡。详见 D037。

## BOSS 资料与观察边界（0.10.0）

共用链接解析器负责规范岗位身份；批次 v4 的详情资料只用于岗位基础资料，原事件不改写。人工补齐、平台状态传播和消息汇总由纯规则模块处理，服务命令负责版本比较、幂等与原子提交。页面按消息显示，底层事实和应用保持独立；平台状态与个人跟进阶段独立。

### 详情读取与列表外交付修正（0.10.5）

`dist/boss-detail-title.js` 只接受完整招聘标题及已核实的 SEO 标题形态，返回岗位名称和用人公司。采集解析与 `collector/boss/model-v2.mjs` 的详情证据校验共用这一定义，保留原始标题；部分标题、验证页、重复岗位名称不一致或字段边界不明确时不生成可信详情。`cdp-browser.mjs` 负责确认目标地址、文档地址、加载完成及导航产生新文档；`detail-enrich.mjs` 再检查标题稳定，不能仅凭新地址与短暂残留的旧标题保存证据。

精确岗位 ID、规范链接及当前会话关联一致的详情证据，按 D038 优先提供岗位名称和用人公司，聊天公司继续表示招聘方。旧显式候选不会因解析器修正而自动提升；同一岗位的详情名称或公司互相矛盾时保留全部证据并返回 `detail_page_conflict`，不选择最新值或退回列表资料掩盖矛盾。资料补齐不改变简历归属检查及人工字段所有权。

`scripts/boss-conversion.mjs` 在增量资料交付中同时读取当前列表记录和采集状态中保留的、具有完整精确详情依据的记录；缺详情的历史记录不因此全量重发。列表外资料交付使用记录自身已有观察时间，不以新快照时间重新解释旧时分或“昨天”标签，不制造新的消息、回执或首次联系日期。普通及简历事件的稳定身份保持；交付仍通过不可变批次、队列与服务消费。采集证据保存、批次交付和业务应用各自确认，读取成功不能代替入队或正式提交成功。

### 人工指定现存目标（0.10.1，D039）

`resolve_boss_job_details` 在同一事务中从精确规范链接补齐目标的空 `externalId`，并保存普通资料观察的人工决定。可选 `retiredOpportunityIds` 精确列出同一职位的全部已删除重复岗位；现存目标、账号绑定、链接与岗位 ID 必须一致，指向删除记录的有效来源绑定仍阻止处理。纯规则模块校验全部目标后返回候选数据，服务负责 CAS、持久幂等与原子提交。

人工指定不创建平台详情证据或简历归属依据，不改岗位公司、名称、简历或阶段，也不移除删除标记。自动导入仍执行包含删除记录的多目标检查，不读取人工命令排除列表。共享数据 v4、应用规则 v9 及私有批次格式保持不变。

## 重复计算与同事实重评（0.10.2，D040）

v0.10.2 启动仍读取并验证完整提交链、提交摘要和工作区格式；启动范围从 v0.10.3 起由 D041 调整。确定性身份计算可在进程内有界复用完整输入一致的结果，容量限制后淘汰旧项；该复用不代表磁盘提交已通过验证，也不持久化。v3→v4 迁移去除重复的来源账本适配，data、base、pending 和冲突各侧仍各自完整处理。

服务正式消费按当前已有来源记录及待处理批次构建临时同事实候选集合。附加批次必须满足当前账号绑定、回执及恢复检查、删除与同步关卡，并成功保存诊断；失败批次或账号受阻后续材料不参与。`buildBossAttributionContext(events, { observations })` 按 `bossFactId` 区分账号、会话、稳定消息及事实类型，业务应用通过内部 `attributionObservations` 传入候选，不增加批次协议字段。

每个完整候选独立经过统一纯归属关卡，任何冲突优先；跨候选非空联系人、双方参与者或岗位身份矛盾也保留为冲突。完整验证不能来自不同观察字段的拼接，也不能仅选择最新观察。全部证据不足时，固定依次选择会话岗位变化、缺岗位身份、缺参与者、缺会话、缺依据原因，不随批次顺序变化。恢复后重新构建候选，业务结果与字段没有变化时，不因观察遍历顺序或重复消费改变原因并产生新提交。

归属纯模块负责候选判定，正式消费负责传入当前可见材料及上下文，服务提交负责持久化与幂等。早期采集诊断仅表达当时材料，正式诊断表达本次完整候选判断；保存失败仍阻止相关进度确认。规则升至 v10，数据 v4、各私有格式、采集预算与显式授权生命周期保持不变。

## 工作区启动 catalog（0.10.3，D041）

工作区存储模块在正常启动时完整校验最新提交的摘要及工作区 data、base、pending 和冲突各侧，再校验 HEAD 指定的不可变 catalog。catalog 仅保存每条命令的 ID、请求摘要、revision、提交文件与摘要，完整覆盖 1 到 HEAD revision；命令 ID 和 revision 唯一，身份和末条与当前提交一致。完整历史工作区不常驻内存，也不在正常启动逐条读取。首次旧 HEAD v1 则先完整审计原始链条，再建立 catalog 并原子发布 HEAD v2，旧提交和 identity 保持 v1。

每次业务提交先将完整候选提交及新 catalog 独占写入，各自完成文件和所在目录 fsync，最后原子替换唯一 HEAD 并同步根目录。HEAD v2 同时绑定提交与 catalog 的文件、摘要和 revision，运行期间外部替换完整根会停止写入。响应丢失复用原请求；目录 fsync 失败只重试持久化屏障，持续失败隔离写者。目录 0700、文件 0600；保留当前及必要上一版本的派生 catalog，清理失败不将已提交业务报告为失败，原始历史和迁移原件不删除。

catalog 的可信度来自首次完整审计和单写者原子追加，不代表历史档案每次启动重新通过验证。索引缺失、损坏、不完整、未知字段或未来格式不能降级为空 Map。旧命令的 `execute` 和 `commandResult` 命中后仍完整读取原提交；原提交异常隔离写者，不能当作未执行而重新提交。显式 `auditHistory` 完整检查当前 HEAD 对应的历史链和工作区格式，不自动运行、不访问招聘平台、不触发云同步。

当前状态、catalog 和输入候选中的未知字段及未来版本继续立即拒写；未读取旧历史的缺失、篡改或未知格式会延后到访问或完整审计时发现。该发现时机调整由用户明确接受，不能描述为安全检查完全不变。SHA 与原子 HEAD 不提供防止同用户重写整套文件或完整磁盘回滚的保证；备份、删除保护、人工所有权和恢复后的事实检查继续适用。

服务运行记录显示 starting、ready、failed 及阶段时间，重复 start 复用正在启动的实例。服务协议仍 v1，本机客户端接受 storageVersion 2；应用 0.10.3、规则 v10、数据 v4、工作区 v3、备份 v2。完整非浏览器检查、首次旧盘转换及普通冷进程启动已核对，真实界面待人工验收。普通启动成本随当前工作区和 catalog 命令数量增长，不承诺固定启动时限。

## 数据与同步的异常引导（0.10.6，D042）

设置渲染按 BOSS 接入、手动 GitHub 同步、备份与文件组织。每项任务从当前服务或工作区状态计算状态、最近成功时间和问题入口，异常说明原因、影响及可执行的下一步；页面不创建新的正式任务或持久提醒。正常预算等待、跟踪停止与人工处理记录不作为故障；发生采集、连接或备份失败时保留问题及相关排障路径。

普通资料确认由页面重新读取正式工作区及当前应用记录，校验同账号、岗位 ID、规范链接一致的唯一现存目标后，复用 `resolve_boss_job_details` 固定命令。服务仍负责完整准入、当前 revision、持久幂等和原子保存；网页入口不处理多目标或已删除重复岗位。结果是普通资料的人工处理决定，不改写原始平台观察，也不授予简历归属验证。候选岗位查看、岗位编辑、waiting 忽略与归属 review 的原有边界继续有效。

同步冲突展示层把既有双方候选转换为可读差异和岗位、关联记录或身份问题分组；独立字段仍由现有模型自动合并。逐组选择仅保存在页面，全部冲突最终通过原 `resolve_sync_conflict` 一次提交，原子字段组不拆开。保存后的待上传状态与用户明确触发的 GitHub 同步分别展示，网页不自动上传。账号绑定、来源应用及删除关联冲突同样保留双方，不能只展示岗位字段后漏掉其余冲突。

资料编辑或同步冲突解决后，结果反馈复用现有约 30 秒串行本机消费及页面状态刷新；现存证据仍经同一关卡重评，没有变化不产生新提交。读取状态不提交命令，服务失联保持缓存及状态待更新提示，不把过期结果当作已解决。恢复缺口仍需用户针对当前 revision 明确核对重放，不纳入自动重评。该版本不新增平台访问、采集任务、重评命令、通用 review 终结或存储格式；规则 v10、数据 v4、工作区 v3、备份 v2 不变。
