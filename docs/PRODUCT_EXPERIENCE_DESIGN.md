# 求职工作台：产品体验设计草案

- 日期：2026-10-12。
- 基线：应用 `0.10.21`、规则 `v16`，提交 `68187539e26899042a4add76b10b5bec9a8a18fb`。
- 状态：**待实施建议**。本轮交付设计与示例草图，未改变正式功能、数据或已接受的决策。
- 来源：用户要求从产品功能视角梳理项目，并同意进一步设计状态说明、待核对处理、复盘与日常入口。

## 1. 产品目标与范围

每次打开工作台，能够回答四个问题：

1. 今天应该跟进哪些岗位？
2. 一个岗位现在是什么状态，这个状态如何得到？
3. 未处理的资料影响什么，我现在可以做什么？
4. 最近做了哪些行动，哪些岗位还没有下一步？

首版优先解决第 2、3 个问题；随后增加有可靠统计口径的复盘，再改善跟踪启停入口。先保留现有操作和保护规则，减少用户理解内部采集、事实、回执的负担。

### 现状与设计建议

| 领域          | 当前已有能力                                         | 本次设计建议                                       |
| ------------- | ---------------------------------------------------- | -------------------------------------------------- |
| 日常行动      | 今天、接下来、待整理；行动建议、计划日期、完成记录   | 岗位详情统一状态说明；完成操作后说明结果与下一步   |
| 岗位管理      | 列表、筛选、详情、沟通时间线、人工编辑、平台关闭状态 | 摘要回答“现在怎样”，展开后回答“依据与维护方式”     |
| BOSS 问题处理 | 消息汇总、候选详情、受限资料确认、等待项忽略         | 按可执行动作组织入口，就地核对，保留返回位置和选择 |
| 复盘          | 按单日汇总岗位与事件                                 | 在行动页增加周/月记录回顾及当前阶段分布            |
| 数据保障      | 手动同步、冲突核对、完整备份、恢复与草稿             | 日常只显示保存/连接提示；技术信息留在数据与同步    |
| 跟踪与提醒    | 终端显式启停；页面到期/逾期清单                      | 后续设计网页显式启停；系统通知另行评估             |

现状依据见 [README](../README.md)、[架构](ARCHITECTURE.md)、[领域术语](../CONTEXT.md)及 [D016](adr/0016-two-entries-unified-detail.md)、[D018](adr/0018-simplified-status-paginated-jobs.md)、[D042](adr/0042-data-sync-guided-resolution.md)。

## 2. 页面结构

保留“行动、岗位”两个业务入口及“数据与同步”，草稿箱仍是独立入口。

```text
行动
  今天 / 接下来 / 待整理 / 复盘（后续）
  打开岗位 → 统一详情 → 记录沟通、安排下一步、编辑状态

岗位
  搜索与筛选 → 统一详情
  详情中的状态依据与相关候选材料

数据与同步
  BOSS：运行状态 → 待处理问题 → 处理记录 / 运行详情
  GitHub：最近同步结果 → 手动同步 / 冲突核对
  备份与文件：最近备份结果 → 备份、导入、恢复
```

不新增独立异常中心或任务实体。岗位入口只在存在精确且唯一的本机候选时提示“相关候选材料”，不能把候选提示呈现为归属确认；多候选或没有精确目标的材料留在数据与同步中。

## 3. 岗位状态：摘要与依据分开

### 3.1 默认只显示当前状态

详情顶部按固定顺序显示四项：

| 字段     | 用户问题                   | 展示边界                                                |
| -------- | -------------------------- | ------------------------------------------------------- |
| 招聘阶段 | 跟进到哪一步？             | 继续使用已触达、沟通中、面试中、Offer、已结束           |
| 简历状态 | 简历是否发出或被接收？     | 未知、被索要、已发送、对方已接收；未知不表示未发送      |
| 消息状态 | 当前保存的消息状态是什么？ | 保留人工未读/已读与 BOSS 平台观察的区别；送达不推断已读 |
| 平台职位 | 职位是否仍开放？           | 未知、开放、关闭；关闭不自动结束跟进或忽略材料          |

列表沿用现有紧凑标签；详细含义与来源在详情中展开，不给每条列表记录增加整段技术解释。

### 3.2 “查看状态依据”回答两个不同问题

1. **谁维护当前字段：** 自动维护、人工维护、来源未记录。复用字段所有权和既有人工处理记录；没有明确确认记录时不能写成“你已确认”。
2. **有什么支持材料：** 当前有效的已应用平台事实、人工记录，或“历史状态，缺少可追溯依据”。材料候选、等待、冲突、忽略、否决和纯卡片不能证明当前简历状态。

展示例：“简历：已发送；自动维护；存在已录入的发送确认材料。”点击后再看材料类别、应用结果及其适用规则，不以当前新规则重新认证全部已应用历史。

一个字段可能有多份支持材料；按事实身份去重列出。人工维护字段即使有相同平台材料，仍保持人工维护，不用一条自动观察覆盖其来源说明。找不到支持材料时说明可追溯性不足，不自动回退字段。

### 3.3 时间必须注明含义

- 岗位 `updatedAt` 只标“最近岗位编辑”，不能标成某一字段的修改时间。
- 应用 `appliedAt` 可标“本机录入时间”，不能当作平台发送时间。
- 来源事件 `observedAt` 在不同转换路径中可能使用平台时间或采集时间，不能统一标成其中一种。仅当现有材料能确定含义时展示相应标签，否则标“记录时间（来源未区分）”或不展示。
- 只有日期的材料不补出时分秒；无有效时间则显示“时间未记录”。

首版不新增字段级审计历史，也不从整条岗位更新时间推断它。依据见 [model.js](../dist/model.js)、[boss-integration.js](../dist/boss/application/integration.js)和 [boss-conversion.mjs](../scripts/boss/delivery/conversion.mjs)。

## 4. 待处理问题：按动作组织，按消息核对

### 4.1 一级入口与计数

BOSS 默认显示“跟踪状态、最近成功处理（含本机恢复）、待处理问题”三项。现有成功时间包含纯本机恢复，不能显示成最近平台采集。人工保护、已忽略、回执、队列及额度进入详情，正常状态不要求用户处理。

待处理入口分为：

| 展示名称       | 判断与影响                                                     | 提供的操作                                                            |
| -------------- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| 岗位资料待核对 | 普通观察资料缺失或现有受限资料差异，包括暂不满足确认准入的材料 | 查看候选、编辑岗位；满足准入时确认岗位资料，有效 waiting 仍可选择忽略 |
| 聊天依据不足   | 现有材料不能支持归属或简历含义                                 | 查看候选及原因、明确保存岗位编辑；有效 waiting 可单独选择忽略         |
| 材料存在矛盾   | 身份或其他依据明确矛盾，仍拦截相关应用                         | 查看矛盾与候选；一般归属 review 不提供忽略或确认归属                  |
| 采集需要处理   | 缺稳定消息身份、请求/转换未完成等技术原因                      | 原因、影响及现有排障步骤；不提供岗位资料确认或假定职位关闭            |

“岗位资料待核对”中的普通 `identity_conflict` 仅在现有受限规则允许时确认；不能将所有冲突改名为资料问题。同步冲突单独展示，并继续约束受影响的操作。

业务问题计数以“同账号＋同会话＋稳定消息 ID”的未处理消息组为单位，同时注明观察数。混合组仅计一次，按仍未解决的主要问题分类：归属矛盾优先，其次资料核对，再次证据不足；组内始终列出所有原因。没有稳定消息身份的采集问题独立计数，不能当作一条已识别聊天。

这个展示分类只整理既有结果，不改变 waiting/review、原因码或操作准入；具体分类由共用查询规则计算，页面不复制归属规则。

### 4.2 打开后先知道“为什么、影响、下一步”

每个消息组包含：

- 候选岗位、招聘方/联系人及可用日期；没有唯一目标时明确提示。
- 问题原因与具体缺项；多字段矛盾逐项列出，避免只写“身份有问题”。
- 当前未处理材料不会更新哪些字段。
- 当前可执行的主要动作及限制；额外技术字段折叠。
- 组内观察类别与结果，例如普通消息、送达回执；事实仍分别保存。

可增加岗位级展示分组，帮助连续核对同一候选岗位，但消息组和勾选目标仍按稳定身份保存；跨账号、多候选及无目标不能强行塞入某个岗位。一个多候选消息组只在未确认分组出现一次。

### 4.3 就地核对与独立保存

桌面：点击“查看候选岗位”在当前页面打开现有岗位详情；返回问题清单时保留展开、滚动、筛选与有效选择。手机：使用现有带返回按钮的全页详情。

核对后按实际目的选择：

本机材料已足够且既有重评能够处理时，优先让现有纯本机消费完成，按正式结果退出清单；不为了新界面增加一次人工确认。资料确认仅用于当前受限规则允许、仍待用户核对的普通资料项；等待重评期间明确显示处理结果待更新。

1. **修改正式岗位状态：** 打开现有编辑表单，用户明确保存；保留人工字段规则。先反馈“岗位已保存；材料处理结果待更新”，回读后再说明是否仍待核对；不能以编辑本身宣称已确认归属。
2. **完成资料核对：** 仅现有命令准入的普通资料项显示“确认岗位资料”；确认页展示候选、身份摘要、消息数与观察数。保存不证明简历归属。
3. **忽略旧等待材料：** 默认不勾选；确认页同时显示消息数量和实际 waiting 应用数量。反馈“已忽略 X 条消息中的 Y 项等待观察”；混合组的 review 继续可见。

无唯一目标时列出候选与差异，提供查看及现有岗位列表核对路径；有效 waiting 仍可选择并确认忽略，但不能确认岗位资料或确认归属。编辑、资料确认和忽略互不代替，不自动执行下一步或清空其他材料。

### 4.4 刷新、断连与结果反馈

- 自动状态刷新不折叠详情或清空整批勾选；按来源应用 ID 保留仍有效的选择，移除失效项并说明数量。
- 工作区版本变化使已展示的确认内容失效，重新读取并展示，用户再次核对；不能把保留的勾选当作对新版本的确认。
- 服务断连时保留最后结果，提示“状态尚未更新”，禁用正式操作并说明原因；不能显示待处理为 0 或保存成功。
- 响应不确定的业务命令只精确重试原请求；版本冲突重新核对，不自动计算并提交新请求。
- 操作后反馈本次结果及该组剩余原因；等待本机重评时显示“已保存，处理结果待更新”，不承诺固定耗时。
- 打开或刷新问题清单只读取本机状态，不触发平台补录。

边界依据见 [D033](adr/0033-boss-import-convergence.md)、[D036](adr/0036-boss-waiting-observation-ignore.md)、[D038](adr/0038-boss-job-details-and-observation-groups.md)及 [D042](adr/0042-data-sync-guided-resolution.md)。

## 5. 复盘：先看记录，再讨论转化

建议放在“行动 → 复盘”，默认本周；提供上周、本月及选择日期范围。自然周从星期一开始，按本地日历日解释范围，并显示起止日期。

首版推荐“当前阶段分布＋每周行动回顾”。这是假定的推荐范围，尚未收到用户对统计偏好的单独选择；若用户更重视转化，可先设计统计口径与历史记录补齐方案。

| 指标           | 口径                                                                         | 必须说明                                                               |
| -------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 当前阶段分布   | 当前未删除岗位按岗位 ID 去重，复用 `getOpportunityStatus` 的当前阶段展示规则 | 与所选周期无关，标题写“当前”，不是周期历史；旧“待联系”仍按“已触达”展示 |
| 本期新增建档   | 岗位 createdAt 落在范围内                                                    | 历史导入今天建档也计入，不等于今天首次联系                             |
| 本期首次联系   | 岗位 appliedAt 日期落在范围内                                                | 首次联系与建档分别统计，缺日期不猜测                                   |
| 本期沟通记录   | 活动 date 落在范围内，沿用活动分类与首次联系去重                             | 称“已记录”，不表示平台全部真实聊天                                     |
| 已记录面试事项 | 本期有效面试类型活动                                                         | 按活动计；另列涉及岗位数，不称新增面试阶段                             |
| 本期完成行动   | 已完成任务 completedAt 落在范围内                                            | 按任务 ID 去重；缺日期单独说明，不能用 updatedAt 补齐                  |
| 仍需安排下一步 | 当前有效待跟进岗位中没有有效下一步行动的集合                                 | 当前工作清单；复用既有待整理准入，不计已结束等排除项                   |

所有指标可展开构成它的具体岗位/活动/任务，查看后可以进入现有详情、安排下一步。无效或缺失日期显示排除数量和原因。取消任务只有有效取消时间时才能按周期统计；首版可先不提供取消数量。

部分人工阶段变化已记录在活动文字中，自动联动并无完整对应历史，故首版不计算历史阶段分布、周期新增 Offer 或简历→面试→Offer 转化率。后续若需要，先定义完整结构化阶段记录及缺失口径，再讨论数据与决策变更。不能仅解析历史活动文字宣称统计完整。依据见 [daily.js](../dist/daily.js)、[app.js](../dist/app.js)及 [D015](adr/0015-date-based-daily-record.md)。

## 6. 日常启动与提醒：后续范围

### 网页显式启停

在本机模式的 BOSS 卡片中设计“开始只读跟踪 / 暂停 / 停止”，复用已有固定控制接口。开始前显示本次作用范围、账号与限制；用户点击才授权开始，不在打开页面、保存岗位或服务重启时恢复。

按钮必须读取真实运行状态；服务不可连接时显示终端启动指引，静态模式解释仅本机可用。控制响应不确定时先查运行状态，不能套用业务命令重试机制而再次发起平台动作。控制服务已有白名单与保护应独立核对，不能绕过串行预算或替用户回复、投递。

现有接口为 [boss-controller-api.mjs](../scripts/boss/control/controller-api.mjs) 的版本化 `{ action }` 控制请求；它不同于带 revision/commandId 的正式数据命令。新增网页控制是待实施建议，现有页面仍以终端指令启动。

### 提醒

第一步继续使用行动页的到期、逾期及未安排入口。以后若需要系统通知，先确认用户是否需要、提醒时间与关闭页面后的运行方式；浏览器权限、去重和后台能力另作设计。当前不创建定时任务或自动化，不承诺现有页面关闭后能发系统通知。

## 7. 实现分期与完成条件

| 阶段       | 建议内容                             | 可观察的完成条件                                                                  |
| ---------- | ------------------------------------ | --------------------------------------------------------------------------------- |
| 第一阶段 A | 共用状态摘要与依据解释               | 从行动、岗位、BOSS 候选打开时说明一致；所有权与材料支持分开，缺依据不误报为已确认 |
| 第一阶段 B | 待处理分组、就地核对、稳定选择及反馈 | 看懂原因和可用动作；返回不丢位置；混合 waiting/review、版本变化与断连不误清空     |
| 第二阶段   | 周/月记录复盘                        | 每个统计可列出成员并核对；当前阶段不冒充历史，缺时间不猜测                        |
| 第三阶段   | 网页显式跟踪启停                     | 点击才开始；未知响应读状态；服务重启后仍停止；静态模式无控制入口                  |
| 后续评估   | 转化统计、系统提醒                   | 先确认完整历史与提醒运行条件，再提出具体范围                                      |

第一阶段不需要新增正式实体、迁移数据或改变 BOSS 归属语义。布局可先使用“按问题进入、按候选岗位连续核对”的组合，避免额外的多层页面；若清单规模仍影响使用，再评估岗位级导航。

### 查询与写入职责

- 共用只读查询接收当前数据、工作区版本和本机状态，返回字段摘要、依据说明、消息组、候选、可用动作及结果新鲜度；名称与文件位置在实施时确定。
- 复用现有归属、语义、候选与操作准入规则，不能在查询或页面中另造“已确认”判断。页面只保存展开、筛选、选择等交互状态。
- 写入沿用现有编辑、`resolve_boss_job_details` 和 `ignore_boss_observations`；服务按真实状态重新校验，原子提交与持久幂等继续有效。
- 候选材料是只读展示关系，不新增持久归属映射。复盘计算不改变业务状态，不自动创建行动。
- 本机新鲜度与静态模式的数据来源分别标注；缓存、已读取批次、回执都不能代替正式应用结果。摘要和日志不增加聊天正文、简历或凭据副本。

与 [架构重构清单](ARCHITECTURE_REFACTOR_PLAN.md) 的详情导航、编辑职责整理配合；产品分期不要求先完成全部重构，也不复制新的存储或控制链路。

## 8. 后续实施验收

1. **状态解释：** 自动、人工、历史来源未知，多份材料，纯卡片、否决、忽略、已应用历史以及岗位编辑时间；说明不能改变正式字段。
2. **问题与往返：** 唯一候选、多候选、跨账号、缺稳定消息 ID、混合 waiting/review、删除目标、资料已补齐及同步冲突；桌面和手机返回位置、有效勾选与焦点。
3. **正式操作：** 无变化编辑、整批原子提交、精确重试、版本冲突、缓存失败、断连与重新读取；保存反馈不能冒充归属已确认。
4. **统计：** 周/月边界、导入建档与首次联系差异、去重、缺时间、已删除记录、任务跨日完成及当前阶段口径；每个数字与展开成员一致。
5. **启停：** 明确点击、账号与预算限制、未知响应、重启不恢复；不得以验证为由访问真实平台。

本轮仅检查文档链接、格式及合成草图交互，不作正式功能验收。实际代码阶段遵循 [变更共用规则](agents/change-workflow.md)，运行相关非浏览器测试、`pnpm check`、`pnpm format:check`，发布前运行完整 `pnpm test`；真实浏览器按 [D017](adr/0017-manual-browser-testing.md) 由用户验收。关键决定若变化，实施前另记 ADR；本草案不提前替代现有决策。
