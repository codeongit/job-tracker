# 研发流程证据与交付记录改造规格

- **日期与状态：** 2026-10-26；规格草稿，可供设计审阅与拆分准备，工具改造尚未实施。
- **本轮授权：** 整理已有讨论及验收条件，交付规格文档。实现选择的推荐不等于逐项用户确认，规格保存也不启动功能实施。
- **现行规则：** 继续以[变更共用规则](../agents/change-workflow.md)、[本机证据核验](../agents/task-evidence.md)和[维护手册](../MAINTENANCE.md)为准。本文中的新入口、字段和转换均为目标设计。

## 问题与目标

现有流程已有检查、证据快照、独立审查及任务记录。已核对的落地缺口集中在记录组装和环境准备：手写报告引用了不存在的文件，同一报告中重复维护的状态不一致，任务起点迟记，以及校验器反复缺少依赖或不接受项目使用的元数据字段。这些问题不等同于检查或审查完全缺失。

本次目标是让交付事实从各自的权威记录生成，及时暴露缺失或过期材料，并使技能校验环境可以按固定声明重建。每项结果应能说明对应版本、来源、范围和限制；人工判断保留明确依据。通过后续实际任务观察返工和复发，样本不足时不承诺效率收益或缺陷率下降。

本规格覆盖两个方向：

1. 复用现有证据与审查工具，增加任务汇总入口，生成交付记录及不可变历史。
2. 固定技能校验器、依赖与项目兼容契约，分开环境准备和日常检查。

## 核心实体与职责

这些概念属于研发工具，定义放在本规格及实施后的流程文档；根目录 `CONTEXT.md` 继续维护求职领域术语。

| 实体             | 权威内容                                             | 身份、关联及更新规则                                                                      |
| ---------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Task             | 任务身份、目标来源引用、类型、时间依据、当前声明位置 | UUID 固定。同一验收目标的复查与修复沿用任务；独立新目标另建任务并关联来源。恢复不重置起点 |
| EvidenceSnapshot | 某次目标、规则、检查声明、文件和环境的版本记录       | 快照创建后固定；一个任务可有多个快照。当前声明是维护入口，快照是历史副本                  |
| CheckRun         | 某次命令的开始和结束事实、退出信息、执行前后输入版本 | 每次执行独立编号，关联检查与快照；重跑保留旧记录。复用保留原运行及来源关系                |
| Review           | 受审基线与目标、首报、发现、反馈和复查关系           | 继续由审查工具管理。首报固定；反馈追加；新版本复查建立关联记录，不向审查记录复制任务台账  |
| Delivery         | 一次核验后的固定材料包、核验结果及说明               | UUID 固定，关联任务和选定材料。发布后不可覆盖；新交付创建新 ID                            |

验收与交付声明作为绑定 Delivery 的追加事件，不增加独立业务实体。事件至少能定位版本、适用范围、事实发生时间及其来源、记录时间、结论和依据。反馈更正保留原事件并明确替代关系；不维护第二份可编辑的验收总数或缺陷总数。

目标与关键验收条件由人工在当前结构化声明中维护；人工说明解释其来源、取舍、授权及限制，引用声明，不另维护一份可独立修改的目标契约。声明位置改变时，汇总入口核对新位置与所选快照，不能继续默认使用旧文件。仅修改来源网页而未更新声明无法被本机自动发现，执行者仍负责核对来源。

### 时间语义

- 工具自动记录的是操作发生时间。任务实际开始时间来自明确的首次动作声明及来源；迟记时保留未知，不以创建记录、审查开始或首次提交时间倒推。
- 交付快照的生成时间与实际交付时间分开。生成文件不证明已经向用户交付；实际交付声明必须对应已发生的交付及来源，不能将预计发送时间写成事实。
- 交付声明可通过追加事件补记，保留实际时间与记录时间；来源不足时实际时间未知。首次可验收交付依据最早的有效交付声明固定保留，后续修正版不覆盖它。
- 只有两端时间可靠且顺序合理时计算首次可验收耗时；包含等待。时间带时区，未知和异常分别表达，不生成估算值。

## 状态、转换与不变量

### 保存发生的事实

| 对象                     | 转换或追加                                   | 判定条件                                                                                                     |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| CheckRun                 | 开始后追加结束事实：成功、失败或有证据的中断 | 成功需要完整的正常退出证据。只有开始记录时为未完成、结果未知；单凭残留锁或记录年龄不能断定仍在运行或已经中断 |
| Review                   | 已创建 → 首报已保存；随后追加反馈或关联复查  | 首报存在不代表 Spec 与 Standards 均通过；两轴结论与覆盖限制须明确                                            |
| Finding（Review 内记录） | 追加有效性判断及对具体版本的处理结论         | 历史成立与当前阻塞分开；修复不把有效发现改成误报，纠正原判断也保留依据和历史                                 |
| Delivery                 | 准备材料 → 原子发布                          | 准备是内部写入过程，失败不产生可见的半份正式快照                                                             |
| 验收事件                 | 待确认 → 对声明范围通过或需修正              | 依据明确反馈，绑定交付版本、场景和来源；有冲突或范围不足时保留未完成部分                                     |

Task 不持久化一套“开发中、测试中、已完成”的阶段枚举。实际是否获授权、材料是否充分、是否可交付和是否已验收分别依据现行交接条件判断。

### 计算当前适用性

- 执行结果和证据适用性分开。历史命令成功后文件变化，运行事实仍为成功，当前适用性为过期；执行期间输入变化也不能提供当前有效通过证据。
- 适用性表达为当前、过期或无法判断；没有所需记录另报缺失。核验提供原因和受影响路径，不能只给一个总布尔值。
- 最新一次失败、未完成或输入不稳定不能被旧成功掩盖。复用仅限既有工具规则允许的相同输入和完整成功记录。
- 材料核验通过只说明声明范围内版本、记录和必要材料满足契约。它不证明需求正确、声明完整、审查独立或人工验收通过。
- 新交付的验收默认待确认，旧交付的反馈保留在原版本；局部验收只覆盖声明的场景。授权实施、自动检查成功和用户沉默均不是验收。

## 版本绑定与交付材料

### 版本身份

新审查材料使用结构化绑定，至少包括修改前基线身份、目标材料、适用规则、检查声明和相应证据内容摘要。基线为提交时保存已解析的提交身份；存在原有未提交修改时，使用明确范围的修改前清单及摘要，保留其归属和限制。

保留两个不同含义的摘要：固定记录的摘要用于定位那一份记录；内容摘要用于判断目标和输入是否相同。后者采用版本化的规范化编码，排除快照 UUID 和捕获时间，保留会影响结论的输入与配置。不能直接比较现有 `snapshot_digest` 和 `current_digest`，二者编码对象不同。

仅重新捕获相同内容不使材料过期；目标、规则、基线、命令、检查集合、输入范围或相关文件变化时，重新判断受影响检查及审查。删除检查或缩小范围同样进入审查，重新捕获不代表允许降低要求。工具提供变化位置，审查者负责判断覆盖是否仍充分。

### 固定交付包

交付包保存本次核验结果、所选快照与运行身份及摘要、必要的结构化证据副本、人工说明副本和审查导出；大型基线材料可继续引用具有固定身份的原件，缺失时明确报错。引用由实际记录生成，不猜测报告文件名。

审查导出包含当时的首报、反馈版本和完整性摘要。原审查以后追加反馈，不改变旧交付中的内容；当前补充判断另行追加。导出必须能够独立阅读，不能只链接一个会继续变化的 `record.json` 并称其为历史快照。

顶层 `delivery.md` 是最新交付和历史导航的生成视图，标明生成时间及选用的交付 ID。人工反馈可更新这个视图，但不能重写历史交付正文、时间和当时的核验结果。历史视图明确区分“当时的材料”与“之后收到的反馈”。

建议存储布局为忽略目录中的任务元数据、当前声明、人工说明、既有证据目录、交付快照目录和追加事件目录；具体文件分拆可由实施确定。人工材料与生成视图分离是约束，目录名称不作为业务需求。

## 操作契约

以下命令名为建议接口；最终参数可以在实施时确定，成功依据和失败语义须保持。

| 操作                               | 输入与结果                                         | 必须封装的行为                                                                               |
| ---------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `task start`                       | 新建或恢复明确任务，返回 ID 和材料位置             | 初始化缺失模板；已有记录不覆盖，恢复不改时间，旧格式先识别                                   |
| `task check`                       | 读取当前声明与指定材料，输出核验结果和报告预览     | 只读，不运行检查命令；核对版本、引用、必需检查及审查材料，逐项说明失败或未知                 |
| `task record`                      | 使用任务、交付 ID 和明确选定的输入，保存固定交付包 | 内部执行同一套核验；失败保存必要诊断并非零退出，成功返回实际路径和固定身份                   |
| 事件登记（可归入 `task feedback`） | 追加已发生的交付声明、验收或纠正事件               | 明确事件类型、来源、版本和范围；相同事件 ID 重试不重复追加，不从自然语言自行推定未声明的范围 |

日常开始和收尾主要使用 start 与 record；check 用于独立诊断，事件按实际交付及自然反馈登记。没有可靠交付时间来源时保持未知，不为减少操作而补造时间，也不每次额外索取用户验收确认。

核验发布条件包括：必需检查的证据适用于当前版本，审查材料可定位且版本匹配，Spec 与 Standards 的显式结论及当前阻断项处理依据齐备，报告准确表达剩余限制。工具校验这些材料的结构和绑定，不代替审查者判断结论是否充分。明确仍未解除的阻断项阻止正式记录。

CI 未查询、人工验收待完成等状态可以如实记录；若某任务明确要求某项结果作为本次交付前提，则缺失时阻止发布。通用工具不把 CI 结果当成人工验收。纯文字小改动保留现行例外，以明确理由、文件摘要、人工报告的命令结果及审查材料交付，标注人工来源，不伪装成工具启动的检查。

### 幂等与失败恢复

- 对固定输入做规范化指纹。同一交付 ID、相同冻结输入的重试返回原记录与原时间；不同输入拒绝覆盖。新版本使用新交付 ID。
- 单任务写入串行化；并发请求不能覆盖当前入口或产生两个相同 ID 的正式交付。无法确认残留写入已经停止时，报出状态未知，不仅凭超时删除锁。
- 暂存完整材料后，重新核对相关输入及选定记录未变化，再原子发布。复制或核验期间变化时中止本次发布，保留诊断；恢复后重新核验。
- 交付包已发布而最新阅读入口更新失败时，明确返回“快照已保存、入口待修复”，附快照位置。重试重建入口，不新建交付或改写时间；只读 check 仍保持只读。
- 事件同样有稳定身份与幂等写入。事件已保存但阅读入口刷新失败不判为事件丢失；历史内容不因渲染失败撤回。
- 检查与固定材料期间暂停相关范围的外部编辑。前后采样不能发现修改后又恢复的瞬时变化；本机文件、锁与摘要不是防篡改或授权边界。

## 可重建的技能校验环境

建议提供两个职责分离的入口：

| 入口          | 契约                                                                                           |
| ------------- | ---------------------------------------------------------------------------------------------- |
| `skill:setup` | 显式准备被忽略的独立 venv；核对支持的 Python，按固定版本和哈希安装依赖；失败不把半成品标为可用 |
| `skill:check` | 只使用该环境及固定校验器，日常检查不联网、不安装、不回退系统解释器；环境未准备时返回明确诊断   |

仓库固定未修改的上游校验器及其来源、源码摘要和许可；固定兼容适配器版本与 Python 依赖。运行证据记录实际解释器版本、校验器、兼容规则和依赖身份。支持某段 Python 版本范围不等于字节级重建同一个解释器。

兼容适配器从原始 frontmatter 安全解析 YAML，允许固定上游字段与明确登记的项目扩展；未知字段拒绝，避免静默忽略拼写错误。现有 `disable-model-invocation` 扩展独立核对布尔类型及项目约定，保留源文件。

在临时目录生成仅包含上游支持字段的 frontmatter 视图，正文保持原样，再运行固定上游校验器。分别报告项目兼容规则与上游字段视图的结果，不声称原始文件直接通过了上游检查。检查前后源文件字节必须一致；不修改系统安装或运行时替换上游源码。

环境未准备、材料不合规、工具完整性异常分别诊断并非零退出。固定依赖版本、支持的解释器范围和上游修订需在实施时依据实际源码、许可及兼容测试确定；不得把目前某台机器上的全局安装作为长期依赖。

## 兼容与范围边界

- 保留现有 `task:evidence` 的检查范围声明、目录成员追踪、最近运行与复用规则；调整输出时先明确版本协议，历史结果不根据新展示口径无依据地改判。
- 旧审查记录继续读取和导出，缺少结构化绑定时标为 legacy／无法自动核验。不得从自由文本中提取一个像 SHA 的片段就宣称绑定成功；需要新自动绑定时取得对相应版本的真实核对及新记录。
- 旧任务的手写 `delivery.md` 不被 start 或 record 静默覆盖。显式迁移先保留原文件及原身份，区分人工声明与机器事实；缺失时间、缺失验收和坏链接不自动补全。旧任务可继续以旧方式读取。
- 未知 schema 版本、未知字段或损坏记录不得默默丢弃后重写；返回可定位的兼容错误，保留原材料。
- 保留审查首报计时及反馈规则，任务耗时不使用审查耗时替代。不新增任务统计命令、综合评分、提醒、看板或后台服务。
- 保持 [D008](../adr/0008-lightweight-static-architecture.md)、[D010](../adr/0010-ci-separate-deployment.md)及 [D017](../adr/0017-manual-browser-testing.md)的轻量架构、CI 与部署分离、人工浏览器分工；不新增浏览器运行要求或改动既有浏览器脚本与 CI。
- 工具和测试只处理公开代码或合成材料；任务记录保持在忽略目录。报告不收集原始私有命令输出、凭据或全量环境变量；不访问真实求职工作区、招聘平台或私有数据仓库。
- 本规格不实施工具功能，不发布 GitHub Issue，不创建保护分支或强制门禁。关键流程决定正式采纳时按 ADR 约定记录，现行规则的切换与工具可用性一起交付。

## 实现与验证安排

现有证据模块承担声明与版本比较、实际命令执行及证据有效性；审查模块承担首报、发现、反馈、计时与冻结导出。任务模块只组织身份、引用、核验发布及阅读视图，禁止从下层私有字段自行重建第二套判断规则。固定环境和兼容适配器通过正常检查命令进入证据链。

验证以 CLI 或模块稳定的公开入口为观察接口。已有证据测试、审查工具测试及文档检查先例继续使用；时间、进程和写入故障通过明确的组装接缝控制。跨模块发布、实际临时 venv 和文件重命名另做集成验证，替身通过不能证明真实适配器连接有效。测试使用临时目录、临时仓库和合成数据。

建议先完成证据诊断、内容身份、结构化审查绑定／导出与固定校验环境，再接入任务入口、不可变交付和事件视图，最后切换流程文档并验证 A16。这里仅说明前置依赖，不生成工单或承诺各部分已经可独立交付。

功能实施时按影响运行相关非浏览器测试、`pnpm check`、`pnpm format:check`，发布前运行完整 `pnpm test`；不运行本地 `pnpm verify`。若后续修改阶段条件或证据规则，选取[流程回归案例](../agents/workflow-regressions.md)的受影响场景进行独立前向试验，避免只验证 JSON 与渲染。

实施后的文档落点是现有变更流程、证据说明、维护手册，以及实际需要调整的实施和审查技能入口；删除重复手写机器事实的要求。仅在这些行为生效时更新正文和相关 ADR，本规格不提前改写当前行为。应用版本是否需要变化按最终实现及仓库规则判断，本次纯规格不提升应用版本。
