## 问题与目标

目前项目已有 Issue 跟踪约定、[PR 模板](../../.github/pull_request_template.md)及支持 PR 事件的 [CI](../../.github/workflows/ci.yml)，实施流程也包含验证、独立审查和本机交付记录，但没有统一要求正式仓库变更通过 PR 交付。现有 `pr` 技能主要规定正文样式，示例偏向界面；它与仓库模板的结构不同，尚未明确如何复用项目的需求、验证和审查材料。

目标是让正式变更能够从 PR 追溯到问题、范围、验收条件、最终版本和验证结论，同时减少重复填报。Issue 按任务需要承接需求与后续事项，PR 承接实现与合并核对，本机保留详细证据和私有材料。现有质量要求与检查能力继续使用。

## 材料职责

| 材料     | 负责保存                                                               | 与其他材料的关系                                                       |
| -------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Issue    | 问题、目标、范围、验收条件、后续需求修正和未完成事项                   | 已有正式规格时引用其路径与适用版本，不复制整份规格；实现由关联 PR 说明 |
| 仓库规格 | 需要跨会话交接的详细需求、保留条件、方案及关键来源                     | 沿用仓库 Markdown；普通小任务无需单独规格                              |
| PR       | 最终问题与行为变化、关联需求、文档影响、验证与审查摘要、风险和待验收项 | 面向合并核对，摘要绑定实际交付版本；需求变化回到 Issue 或正式规格维护  |
| 本机记录 | 详细检查与审查材料、私有诊断证据、必要的执行记录和远端关联位置         | 同一事项复用已有记录，公开摘要由 Issue／PR 承接，不再重复维护完整正文  |

公开材料只包含可公开的需求、合成样例和必要结果。真实求职记录、简历、凭据、私有仓库内容和原始私有输出仍按 [AGENTS](../../AGENTS.md#平台访问与隐私)处理。本机私有文件路径不充当公开审阅者必须打开的证据链接；PR 应能凭公开摘要理解结果与限制。

## 目标工作流

### Issue 按任务需要建立

建议跨会话推进、涉及设计取舍、存在依赖、暂缓处理或需要持续跟踪的任务使用 Issue；明确的小修复、文字修改可以直接进入 PR，无需为了配对而创建 Issue。直接进入 PR 的任务也要保留必要的目标与验收条件。

已有相关 Issue 时读取正文及相关评论，核对最新要求并复用，避免重复建单。Issue 不替代正式规格、领域术语或 ADR；需求与实现之间通过引用建立关联，不要求每个提交对应一张 Issue。建议以对应验收条件全部满足作为 Issue 完成依据，单个 PR 合并不能自动证明关联 Issue 的全部目标已经达成。

### 正式变更通过任务分支和 PR 交付

新流程启用后，代码、测试、配置、文档和技能等正式仓库变更均通过任务分支及 PR 进入目标分支。普通问答、无文件修改的分析、只保存在忽略目录的私有笔记不因此创建 PR。用户对某次任务有明确不同安排时保留该来源与范围。

正式文档变更本身可以独立获准实施；该授权覆盖文档编辑和对应交付，不等于授权实施文档描述的产品或流程方案。新流程启用后的正式文档任务同样按上述范围走 PR。

沿用当前实施顺序：核对目标与基线、按影响核对设计、实施及验证、独立审查与修正、提交和交付。PR 可以在工作未完成时承接草稿，但草稿存在不表示已通过检查、可合并或依赖已解除；完成后的正文应围绕最终实现整理，移除过时结论。

用户批准任务实施后，代理可以在项目仓库内推送该任务分支，创建或更新相关 Issue／PR；已有授权在同一任务后续修正中继续有效，无需对相同范围反复询问。分支推送和 PR 写入不包含向目标分支直接推送、合并、部署或发布个人记录的授权。合并仍需另行授权，并核对当时的变更范围与有效证据。

远端暂不可用时保留本地提交、正文草稿及验证依据，明确尚未推送或发布，恢复后先核对已存在的分支、Issue 和 PR。不得把失败或结果未知写成发布成功，也不因重试创建重复材料。外部状态只按实际查询结果报告。

### 复用检查与审查

检查范围、证据适用版本、Spec 与 Standards 审查、设计核对和文档维护仍由[变更共用规则](../agents/change-workflow.md)及相应技能维护。PR 写作引用已有有效结果；相关输入变化时按原流程补查，不因新增 PR 环节再执行完整流程。

本地检查、CI、人工验收和合并分别报告。涉及界面且需要人工验收的 PR，默认先完成适用人工验收，再另行授权合并（S7）；验收反馈本身不等于合并授权。CI 通过不代替人工验收，相关反馈应能定位版本与实际范围。浏览器分工沿用 [D017](../adr/0017-manual-browser-testing.md)，普通写作需求不授权代理启动浏览器或访问招聘平台。

多工单仍按 [D052](../adr/0052-coordinator-owned-ticket-review.md)由主协调者组织候选、审查和集成，前置设计核对沿用 [D053](../adr/0053-pre-implementation-design-review.md)。具体采用一个或多个 PR 随可独立审阅和合并的边界确定；本机集成或候选就绪不等于远端合并已获授权。

## PR 正文技能要求

`pr` 负责把目标、最终差异和既有交付材料整理为正文，接入 `implement` 的交付环节。它继续保持轻量，不另行定义测试、审查或 GitHub 操作流程。

技能与现有 PR 模板应采用一致的表达要求。下表是建议的三段组织方式；现有模板中的规则依据、受检版本、文档影响和数据兼容性信息应保留，可合并到相应段落，避免为两种模板各写一份。

| 部分         | 输出要求                                                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Summary      | 先说明具体问题和最终行为，再按需要加入最小图示；覆盖文档影响，简单变更允许纯文字                                               |
| Evidence     | 引用实际检查或用例、结果与适用版本，区分执行结果、说明性伪代码及待验证项；有实际观察才写失败到通过，无修改前执行记录时如实说明 |
| Merge Danger | 用具体对象和后果说明影响范围，解释能否回退及必要条件；数据变更说明撤回代码是否足以恢复数据，不限制为一个词                     |

证据按待证明的行为选择：界面可使用已有人工截图和验收反馈；导入、同步与恢复可使用合成输入输出、状态变化及失败恢复用例；文档和技能可使用规则差异、结构检查和必要的行为试验。取消截图与执行结果的固定等级排序，减少重复的界面示例，示意代码与可执行代码明确区分。

## 验收场景

以下用于后续流程改造的独立情境验证，不代表这些行为已经启用或通过验收。优先使用合成材料和隔离的远端替身，实际发布仅在对应任务范围内执行。

| 编号 | 场景                               | 可观察结果与失败反例                                                                                      |
| ---- | ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| A1   | 明确的小代码修复                   | 任务分支与 PR 可定位目标、改动和证据；不强制新增 Issue 或正式规格                                         |
| A2   | 跨会话且已有 Issue                 | 读取正文与相关评论，采用最新要求并关联 PR；不能重复建单或遗漏后续修正                                     |
| A3   | 纯文档或技能变更                   | 同样走 PR，按文档范围验证；不为凑证据启动浏览器或编造失败测试                                             |
| A4   | 新流程尚未启用时整理本轮需求       | 可以保存需求；不因未来约定已写入规格就推送、发 Issue 或发 PR                                              |
| A5   | 新流程启用后获准实施               | 可推送任务分支、创建或更新相关 Issue／PR；没有另行合并授权时保留待合并状态                                |
| A6   | 验证后又改动相关内容               | 受影响结果补查并复查，PR 对应最终版本；未变化的有效证据可复用                                             |
| A7   | 界面变更尚无人工反馈               | 分开呈现非浏览器检查、CI 和待人工验收，默认等待适用人工验收完成再另行授权合并；不把截图偏好当作浏览器授权 |
| A8   | 新功能、纯文档或缺少修改前运行记录 | 使用现有行为说明及实际验证结果，明确证据性质；不把伪代码当作真实执行记录                                  |
| A9   | 不可逆数据副作用                   | 风险描述指出具体对象、后果及恢复条件；仅撤回代码可行不能被写成数据也可恢复                                |
| A10  | 材料含真实求职信息或私有日志       | 公开正文仅有必要安全摘要或合成材料；私有证据留在忽略目录，不复制进 PR 或版本库                            |
| A11  | 远端失败或响应结果未知             | 保留本地成果及明确状态，重试前核对远端现状，避免重复建单；不宣称已发布                                    |
| A12  | 同一事项交付和后续修正             | Issue、规格、PR、本机材料各有职责，通过版本与引用关联；不要求维护多份完整流水账                           |
| A13  | 新流程启用后获准修改正式规格       | 文档按范围验证并通过 PR 交付；不据此开始实施规格描述的方案                                                |
