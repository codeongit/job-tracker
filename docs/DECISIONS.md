## 如何维护

- 改动前先读相关决策。涉及使用范围、公开与私有边界、持久化、同步、恢复或技术栈时，在同一个提交中更新决策及相关文档。
- 每条使用稳定编号，状态为“有效”“待定”或“已替代”。新想法先标待定，不当成已确认需求执行。
- 改变已有决定时追加新条目，说明替代关系；保留旧条目和原有原因，不重写历史。
- 新的用户明确要求优先于旧决策；落实时记录变更依据。日常修复不需要为日志另设审批。
- 本文件随公开代码发布，只记录设计与取舍；具体求职经历、岗位记录、简历、密钥等继续保存在私有位置。

## D001：面向个人使用的独立网页

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 如何把已有 Markdown 求职记录变成可持续使用的工具？
- **决定：** 做个人使用的独立网页，围绕岗位、沟通记录和下一步行动组织界面。目前按一个使用者管理自己的数据设计。
- **原因：** 用户明确选择“个人使用的独立网页”，需要比原表格更方便的查看、补记和跟进方式。
- **备选与取舍：** 继续维护 Markdown 的开发成本低，但交互和状态管理有限；Obsidian 插件会绑定宿主；多人服务还需要账号、权限及服务端运维，当前没有这项需求。
- **重新评估条件：** 需要多人协作、不同账号的数据隔离，或必须深度调用 Obsidian 原生能力。

## D002：公开界面代码，私有 GitHub 仓库存放求职数据

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 如何满足免费云同步目标，同时避免公开个人求职记录？
- **决定：** 界面代码使用公开仓库；业务数据存入用户指定的私有 GitHub 仓库。当前用单个 JSON 文件保存共享数据，路径由配置指定；本地配置和 Git 缓存不进入版本控制，静态发布只包含 `dist/`。
- **原因：** 用户明确接受“界面代码公开，求职数据私有”，希望利用已有 GitHub 账号完成云同步。单文件方便导出和按版本合并，也减少初版服务端维护工作。
- **备选与取舍：** 专用私有数据仓库可进一步隔离仓库权限；服务端数据库适合复杂查询和多人高频写入，但增加服务维护。拆成多个 JSON 文件需要额外处理跨文件一致性，当前先保留单文件。
- **约束：** 同步限定目标 JSON，其他笔记不随应用提交。当前上限为最终序列化文件的 5,000,000 个 UTF-8 字节，上传前在两种传输路径检查；完整备份导出不受同步限额限制。
- **重新评估条件：** 接近文件体积上限、需要简历附件、频繁出现多设备写入竞争，或仓库权限无法满足隔离需求。不要通过清空文件、删除历史或直接取消大小检查处理增长问题。

## D003：本机先保存，手动触发同步

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 网络失败或设备切换时，如何保留正在记录的内容？
- **决定：** 每次保存先写入 IndexedDB 事务，页面显示待同步状态；用户点击同步后再读取和合并云端。当前没有后台自动同步，也没有完整应用的离线启动缓存。
- **原因：** 保存不依赖 GitHub 可达；手动同步让上传、首次初始化及冲突处理保持可见，便于定位首版问题。
- **备选与取舍：** 自动同步能减少忘记同步的情况，但需要重试、后台任务、凭证生命周期和并发协调；直接依赖云端保存会让网络故障影响录入。
- **约束：** 同步基线只确认实际上传的快照，上传期间的新编辑仍待同步。不同浏览器、域名和端口的存储独立；清理网站数据会删除未另行保存的本机内容。
- **重新评估条件：** 经常忘记同步、每天跨设备切换，或需要离线重新打开应用；届时单独设计自动同步和离线缓存。

## D004：本机复用 SSH，公开网页使用会话令牌

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 用户已经配置 SSH key，能否避免在本机网页填写令牌？
- **决定：** 本机服务通过系统 Git/SSH 访问固定私有目标，使用独立 bare 缓存；浏览器调用同源本机接口。手机或公开网页使用 GitHub REST 与当前页面内存中的 PAT，刷新后重新填写。
- **原因：** 用户提出使用 SSH key 的偏好。本机桥接可以复用现有配置，同时让私钥保持在系统 SSH 环境中；浏览器静态网页本身不具备直接使用本机 SSH key 的能力。
- **备选与取舍：** 全部使用 PAT 配置简单，但本机会重复填写；原生桌面应用或 OAuth 服务可以提供其他授权体验，但引入额外平台或服务维护。持久化令牌的方便性需要另行权衡，当前不做。
- **约束：** 本机只监听回环地址，校验 Host、Origin 和随机会话；目标由服务端配置固定，不能从网页任意选择远端。不操作 Obsidian 工作树，不强推。PAT 权限覆盖所选仓库，应用的路径限制并不等于 GitHub 提供文件级授权。
- **重新评估条件：** 手机成为主要入口、需要持续登录或后台同步，或希望更细的授权范围。

## D005：三方合并、显式冲突与删除标记

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 多设备修改和删除同一批记录时，如何避免静默覆盖？
- **决定：** 使用稳定 ID 对齐 `base/local/remote`，不同记录的修改自动合并，同记录双方不同修改由用户选择整条版本。删除保留 `deletedAt`，岗位删除与新增关联任务也进入冲突处理。写入使用文件版本校验和普通 Git push。
- **原因：** 云端最后确认版本提供共同基线；保留删除标记使其他设备能够识别删除。显式选择保留双方内容，避免仅凭设备时间决定覆盖顺序。
- **备选与取舍：** “最后写入者优先”实现简单但可能覆盖另一设备的修改；字段级合并更细致，却需要维护字段之间的关联规则，当前先使用整条记录冲突。
- **约束：** 未解决冲突时不继续业务编辑或切换同步目标；超时写入先读回核实，不能盲目重复提交。非法远端数据不得解释成空数据。
- **重新评估条件：** 同记录冲突频繁且用户很难选择，或引入多人实时协作；再评估字段级规则或新的同步模型。

## D006：自动快照与独立备份，两种恢复语义

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 误删、导入错误或恢复操作本身出错时，如何找回完整状态？
- **决定：** 在删除、Markdown 导入、恢复、升级和同步前自动保存本机快照，保留最近 20 个；提供可下载的完整工作区备份，包含数据、基线和未解决冲突。提供“合并恢复”和“回到快照”两种明确操作。
- **原因：** 误操作也可能被同步到云端，因此需要独立的恢复路径；只导出当前记录会漏掉冲突另一方和必要的同步状态。
- **备选与取舍：** 单靠 Git 历史能追回已上传版本，但不包含未上传编辑；仅自动保存浏览器快照无法抵御网站存储被清理。此条首次实现时，独立备份需要用户下载并妥善保存；v0.3.0 由 D012 增加自动磁盘保存，原有下载和恢复语义继续有效。
- **约束：** 快照与对应修改在同一事务中成功或失败。普通快照恢复保持当前基线，并给快照之外的记录加删除标记，作为一次新的本机修改；包含冲突的完整备份必须保留双方。缺少工作区内容的备份不能当成空快照。恢复不自动上传。
- **重新评估条件：** 20 个快照不够、快照体积影响存储，或用户明确需要自动保存到浏览器之外；调整前先确定保留期限、存放位置和恢复演练方法。

## D007：区分数据与应用版本，升级失败保留原状态

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 后续新增字段和功能时，如何兼容旧数据及仍打开的旧页面？
- **决定：** 分别管理应用、共享数据、工作区及备份格式版本；采用逐版本纯迁移函数，迁移前同事务保存原始快照。遇到未来版本、未知字段或缺失迁移步骤时停止写入，页面仍提供原始状态导出。
- **原因：** 页面更新不一定改变云端格式；版本分开后可以明确兼容范围。拒绝未知字段能避免旧页面读取后把新字段丢掉并重新同步。
- **备选与取舍：** 只改字段白名单无需迁移代码，但无法证明旧数据和冲突内容完整保留；自动丢弃未知字段会掩盖兼容问题。
- **约束：** 迁移覆盖 data、base、pending 中的数据和冲突双方。v0.2.0 共享格式仍为 v1，本机工作区为 v2；不能直接用 v0.1.0 打开已升级的同一浏览器数据库。未来版本的支持范围以代码及数据文档为准。
- **重新评估条件：** 每次新增共享字段、修改字段含义、调整本机数据库或备份格式时，都重新核对迁移和回退路径。

## D008：保留轻量静态架构与可复现的检查流程

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 个人项目如何控制长期维护成本，并支持其他维护者接手？
- **决定：** 使用原生 HTML/CSS/ES modules，`dist/` 同时是维护的源码与静态发布目录；按视图、纯数据规则、持久化和传输拆分模块。运行时没有第三方依赖，开发工具使用锁文件固定；当前支持 Node 24 和固定 pnpm 版本。不要把 `dist/` 当成可清空后重建的缓存目录。
- **原因：** 现有功能可以由轻量结构承载。明确模块职责、格式规范和固定工具版本，比仅在聊天中约定更容易复现和交接。
- **备选与取舍：** 前端框架、构建工具或 TypeScript 能在界面和团队扩大时提供价值，但迁移本身有成本；当前先围绕现有实现完善维护机制。
- **约束：** UI 不直接操作 Git；改动应有与实际风险对应的回归检查。中文组合输入期间保持输入控件稳定。测试使用合成记录、临时 Git 仓库及隔离浏览器，禁止接入真实求职数据。
- **重新评估条件：** 路由、组件复用或状态管理持续变复杂，类型错误显著增加，或维护者增多；用具体问题证明迁移收益后再调整技术栈。

## D009：导入先核对，不推断缺失信息、不覆盖已有记录

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 如何把原始六列 Markdown 表格转换成记录，又不改变原意？
- **决定：** 提供年份和字段核对预览，用稳定 ID 跳过已经导入的岗位；疑似公司/岗位填反需要用户选择后交换。保留原文批次，不把“索要简历”推断为“已发送”，不补造没有记录的事件日期。
- **原因：** 历史表格存在简写和字段歧义；后续在网页补记的内容应当保留。用户确认原始记录属于 2026 年，新导入默认使用当前年份并允许修改。
- **备选与取舍：** 自动推断和覆盖导入更省操作，但可能写错状态或覆盖后续编辑；当前把不确定内容交给预览核对。
- **约束：** 原文只保存在私有数据里，计入同步体积。Markdown 导出用于阅读，与原六列导入布局不同；完整往返恢复使用 JSON。
- **重新评估条件：** 增加其他招聘平台、源文件格式变化，或需要重复导入更新已有记录；届时单独设计字段映射和覆盖规则。

## D010：代码推送运行 CI，网页部署单独安排

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **问题：** 如何让后续修改可追踪、可验证，同时明确代码发布和网页上线的区别？
- **决定：** 代码进入公开仓库，分支推送及 PR 运行 CI，检查测试、静态资源和格式；验证过的发布使用版本标签。当前运行入口是本机服务，尚未配置公开网页部署流程。
- **原因：** 用户明确同意维护基础版并提供公开仓库。自动检查可以持续验证后续改动；部署还涉及实际访问地址和设备使用方式，需要作为单独的后续工作落实。
- **备选与取舍：** 仅本地测试无需 CI 配置，但其他环境的问题不易发现；推送后自动部署方便，前提是确定托管目标和发布流程。当前代码仓库公开不代表网页已经上线。
- **约束：** CI 使用只读代码权限和合成测试，不配置私有数据仓库凭证。仅文档改动不提升应用版本或重打已有标签；检查文档格式及链接即可，已配置的 CI 仍按正常触发条件执行。
- **重新评估条件：** 用户确定手机/异地访问和公开网页部署需求，或需要预览环境、回退部署和发布审批时。

## D011：未提交输入保存为独立草稿

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **来源：** 用户同意补充草稿自动保存；持久化细节为实现选择。
- **问题：** 刷新、关闭表单或关页会丢失尚未点击保存的输入。
- **决定：** 新增/编辑岗位、行动、沟通按白名单保存至 localStorage，草稿箱显式恢复；正式保存才进入业务记录。每页拥有独立 ID，恢复复制为新 ID，版本键使清理不会删除较新输入。
- **原因与取舍：** 同步写入可覆盖输入后立即关页；IndexedDB 异步草稿需要额外处理关闭窗口时未完成事务。localStorage 有容量限制，当前最多200份并明确报告配额失败，不能把草稿当无限笔记仓库。
- **约束：** 设置和令牌不持久化；保留编辑时原记录基线以检测并发修改。成功清理失败不改变正式保存结果。
- **重新评估条件：** 长草稿经常触及配额、需要草稿跨设备同步或附件。

## D012：自动把完整状态保存到本机私有磁盘

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **来源：** 用户同意独立备份；扩展 D006 的下载备份方案，原有快照和恢复语义保持有效。
- **问题：** 浏览器存储被清理会同时失去记录和浏览器内快照，手工下载容易忘记。
- **决定：** 本机服务在固定 `.local/backups/` 保存v2完整备份，包含工作区和草稿。各浏览器来源保留最近30个日期的首份与 latest，设置页能列出旧来源文件并预览恢复。
- **原因与取舍：** 复用现有本机服务，无新账户或远端服务；磁盘写入独立于 GitHub。每日首份方便撤回当天误改，latest 缩短损失窗口；不逐次保留所有历史以控制空间。
- **约束：** 改动约2.5秒后写，页面打开时30秒重试；网页/服务关闭期间不运行。按来源隔离和跳过全新空状态，避免清空浏览器后覆盖旧备份。文件原子替换且不包含令牌；单机备份不能覆盖整机丢失。恢复先预检草稿容量，异常回滚本批副本。
- **兼容性：** 备份v2兼容读取v1；共享数据v1、工作区v2不变。旧版无法读取新的完整备份。D007 的版本规则继续有效。
- **重新评估条件：** 需要关页后持续运行、异地备份、更多历史或达到50MB完整备份限制。

## D013：今日页必须把提示变成可完成的行动

- **记录日期 / 状态：** 2026-09-11 / 有效。
- **来源：** 用户指出当天新增岗位不可见、建议核实无法选择；分组和持久化细节为实现选择。
- **问题：** 今日页原先只显示待办任务；未设下一步的岗位只有数量，建议核实也只有提示文字，用户无法从页面完成闭环。
- **决定：** 所有进行中且没有待办的岗位必须在今日页可见：需核实的进入“建议核实”，其他岗位进入“未设下一步”；今天新增的未安排岗位单独列出，较早的折叠在计划任务之后。核实建议按具体问题拆分，并提供确认结果或加入今日行动两个操作。
- **原因：** 统计数字必须能追溯到具体岗位，建议必须能转成状态、沟通记录或待办。否则用户仍需猜测隐藏规则并绕到其他页面操作。
- **约束：** “今天新增”使用本地日历中的 `createdAt`，不把首次联系 `appliedAt` 混作创建日期。无关待办不遮挡核实项；同一岗位可同时有多项建议。直接确认和完成核实待办使用相同的确认语义；并发时只接受仍然有效的建议选择。确认不增加共享字段，继续使用既有状态、活动和任务格式。
- **重新评估条件：** 核实类型显著增加、固定活动文本不足以稳定标识，或需要对建议本身同步独立状态；届时评估共享数据新版本。
