# 数据升级、备份与恢复

## 版本与两种存储模式

| 层次                    | 当前版本           | 含义                                                                         |
| ----------------------- | ------------------ | ---------------------------------------------------------------------------- |
| 应用                    | 0.10.3             | package.json 与 APP_VERSION 一致                                             |
| 共享数据                | schemaVersion 4    | 原业务集合、sourceBindings/sourceEvents，以及 sourceFacts/sourceApplications |
| 工作区                  | workspaceVersion 3 | data、base、config、generation、lastSync、pending；完整迁移各侧              |
| 完整备份外层            | backupVersion 2    | 完整工作区及草稿，仍兼容旧备份                                               |
| 本机服务协议            | 1                  | 固定命令协议；本机客户端接受 storageVersion 2                                |
| 本机 HEAD / catalog     | 2 / 1              | 唯一原子根绑定当前提交和完整命令定位索引                                     |
| 本机提交 / identity     | 1 / 1              | 旧不可变完整提交与稳定身份保持原格式                                         |
| 服务运行记录 / 启动意图 | 2 / 1              | 运行阶段与独占启动归属；运行记录兼容读取 v1                                  |

本机模式以 `.local/workspace/` 为正式权威存储；IndexedDB 保存读取缓存，localStorage 保存浏览器草稿。手机/公开静态版继续使用独立 IndexedDB 正式保存，经用户手动 GitHub 同步交换共享数据。IndexedDB 名称仍为 `job-tracker-v1`、结构版本 2，不因业务 schema 升级而盲目重建数据库。

一旦浏览器确认本机模式，服务失联不得退回静态模式写正式数据；可读缓存、保留草稿并提示恢复服务。同一服务下多个浏览器读同一工作区 ID，不再各自消费队列；草稿与浏览器备份来源仍彼此隔离。

## 首次迁移与版本保护

先关闭其他旧页面，在保存正式记录的原浏览器执行两步迁移：第一步生成并下载 backupVersion 2 完整备份，页面显示岗位、正式记录、同步基线、冲突、草稿数量及下载字节的 SHA-256；核对并保存文件后才能执行第二步提交。缺少 IndexedDB 原工作区、工作区与草稿均为空、备份后工作区或草稿发生变化时均停止，要求回到正确浏览器或重新导出，不能把错误浏览器的空状态初始化成正式数据。服务随后保存原始工作区文件，再完整校验、逐版本迁移并提交；不能用空对象替换损坏工作区。

迁移不会删除浏览器原有 IndexedDB、快照或 localStorage 草稿，它们继续作为恢复材料，但草稿不进入服务正式数据；首次真实迁移仍须核对已下载备份中的草稿数量和原版本。应急“导出原始工作区”与完整迁移备份用途不同：前者允许保留未来/损坏原件供修复，不能替代包含草稿且通过校验的迁移备份。已有正式工作区时，另一浏览器旧缓存不能再次初始化或覆盖它；页面先拒绝读取覆盖，要求下载含草稿的完整备份并明确切换，切换前还保存浏览器快照。并发初始化只有提交自身命令成功或相同命令幂等回放才算完成，不能把任意 `409` 或另一来源的工作区当成本次迁移成功。

v1→v2 为旧数据增加来源绑定/事件；v2→v3 保留这些事件，并建立事实与应用账本的确定性关联，不因格式升级重放简历或招聘状态。迁移覆盖 data、base、pending.data、pending.remote、冲突各侧、草稿原版本、完整备份及两种远端读取入口。首次本机迁移将本机 `data`、pending 本机候选以及冲突中两个可选 live 结果的旧 BOSS 账号归属转换为服务工作区 ID；`base`、pending remote 数据集及冲突 base 继续保存迁移前云端证据，首次同步据此把新身份正常上传，不能让远端选择或旧身份反向覆盖本机。原始迁移文件保持原样。

维护规则：

1. 共享字段变化需提升 DATA_VERSION 并添加纯迁移函数，不能仅扩展白名单。
2. 保留稳定 ID、删除标记、同步基线、未上传修改、冲突双方与草稿原版本。
3. 使用合成旧格式、关联删除、冲突与重复迁移验证；不能用真实记录作 fixture。
4. 未来版本、未知字段、缺迁移或损坏状态停止写入，不能丢字段后同步。
5. 本机正式提交前保存迁移原件；静态模式旧数据升级在 IndexedDB 事务内保留原快照。失败保留紧急导出入口。

本机写接口要求协议 v1；旧本机页面不能绕过新协议上传。但尚未读到 v3 远端的旧手机/公开客户端无法被本机服务远程撤销：首次同步新格式前应备份、关闭/升级其他客户端。读到未知 schema 的旧客户端应拒绝写回，不允许降级覆盖新集合。

## 本机不可变提交

`.local/workspace/` 包含稳定身份、`commits/`、不可变 catalog、原子 `HEAD.json`、写者锁和迁移原件。每次正式变化保存完整工作区，提交记录关联前一版本和内容摘要；完整候选提交与 catalog 各自完成文件及所在目录 fsync 后，唯一 HEAD v2 同时发布两者指针，再同步根目录。若 HEAD 原子替换已经可见而目录同步短暂失败，服务核对包含 catalog 的完整根并只重试本地持久化屏障；确认成功后才返回同一幂等提交。持续失败会隔离写者并报告持久性未知，不能发队列回执或把“可见”冒充“已持久化”，重启后按实际 HEAD 和相同命令核对。网页 API 只接受固定业务命令：白名单业务记录编辑、同步配置、冲突暂存/解决、同步确认、恢复和 BOSS 账号绑定；通用完整工作区提交只存在于服务内部事务，不能由网页调用或借业务编辑改写来源集合。同步确认只接受服务在真实 SSH 读取时签发、并在精确计划上传成功后置为可确认的一次性事务 ID；冲突暂存也引用该事务，不接受网页自报的 remote/captured/uploaded 整库。已有同步基线时远端文件缺失会在权威服务边界停止，不能被旧页面或错误同源客户端当作空远端重建。单服务写者和 `expectedRevision` 防止并发静默覆盖；`commandId` 和持久命令结果使响应丢失后的相同请求可幂等确认。

正常启动完整验证最新提交和 HEAD 指定的 catalog；catalog 完整覆盖 1 到 HEAD revision，命令 ID 和 revision 唯一，只保存请求摘要和提交定位，不保存业务快照或结果。首次旧 HEAD v1 必须完整审计全部历史后建立索引；新格式 catalog 缺失、损坏、不完整、未知字段或未来版本停止写入，不能返回空索引或将旧命令当新命令。旧命令重放与结果查询重新完整校验原提交，显式 `auditHistory` 完整检查历史链；按需读取或审计发现异常会隔离写者，不能返回未找到后再次执行业务命令。

不要手工改 HEAD、提交内容或活跃写者锁。当前摘要、catalog、外部更改 HEAD、未知当前格式或另一活动写者会拒绝写入；未访问旧历史的缺失、篡改或未知格式可以到访问或完整审计时才发现。D041 明确调整了 D026/D040 的启动发现范围。先停止相关操作、保留私有目录和原始导出，在副本上诊断；恢复通过验证后的新提交执行，不改写旧历史。当前不自动清理不可变提交；仅保留当前及必要上一版本的派生 catalog，清理失败不改变已持久化业务结果。磁盘历史不能替代异机独立备份，SHA 与原子 HEAD 不保证防止整套文件恶意重写或磁盘回滚。

服务关闭时不写正式数据；浏览器关闭时服务仍能提交已授权 BOSS 队列。BOSS 事实、业务变更、应用处理结果和命令元数据同一提交成功后才发队列回执。磁盘回执不是独立正式数据源，恢复旧备份后不能仅凭它断言事件已录入。采集快照已落盘但转换或入库中断时，`pnpm boss recover-saved` 仅在本机核对检查点、补交批次并消费队列，不连接平台、不占平台预算，也不启动持续跟踪。

v0.8.5 的采集器私有运行状态写入 `.runtime-v3.json`，读取旧 v1/v2 后保留旧文件；旧公平游标和详情退避、平台动作预算均不清空。增量历史任务按会话保存列表指纹、成功消息水位和下一页。每页先保存 `.change-checkpoint-v1.json`，快照提交后才确认任务；中断后优先本地重放检查点，再决定是否访问平台。旧 `.resume-checkpoint-v1.json` 属于显式 `backfill`，先恢复其中的证据，未完成页仍由回填继续。不要手工删除检查点以“清零”等待项；预算耗尽时看 `pnpm boss status` 的下次额度时间，需检查旧会话时明确执行一次 `pnpm boss backfill`。真实浏览器验收未完成前不要把合成测试当作采集成功。

## 来源事实、应用与冲突

v0.8.7 恢复“附件简历请求已发送”表示简历“已发送”的规则。用户确认与目标会话不符的具体观察，可通过按岗位和事件限定的 `reject_boss_resume_observation` 本机服务命令否决。命令核对账号、岗位、唯一简历证据、来源应用和自动字段所有权，存在待处理同步冲突时拒绝；它只撤回该观察造成的自动状态，保留原始事件与来源事实，在应用账本标记否决，防止重放。该操作新增不可变工作区提交，不修改旧快照或云端数据。v0.8.6 的 `correct_boss_resume_request` 不再接受新命令，原幂等命令仍可核对既有结果。

`sourceBindings` 记录账号及平台岗位/会话关联；`sourceEvents` 保留兼容历史观察；`sourceFacts` 保存最小来源事实；`sourceApplications` 保存采用规则和 applied/protected/waiting/review/no_effect 结果。事实 ID 只使用平台、账号、会话、消息 ID 和事实类型；岗位名、联系人、采集时间和规则版本均不参与，不同回执状态使用不同事实类型。缺少稳定消息 ID 的观察只保存为独立等待事件，不创建岗位、事实或应用，后续补证再重算。相同事实跨浏览器同步保留相同 ID，业务是否应用需另查应用账本，不能只看事实或批次是否存在。旧事件 ID 原样保留，并由幂等适配补充语义事实映射。

历史重放不回退较新观察、覆盖人工字段或复活删除岗位。人工修改和主动清空保留字段所有权。等待项可在依赖满足后重评；真正歧义需核对，保护项不能自动覆盖。恢复导致事实或应用缺失时，先查看服务报告的缺口，再以当前工作区 `revision` 明确重放固定批次；版本已变化时拒绝，不能把旧队列无条件重灌。

同步仍按 base/local/remote 合并，云端写入只由用户触发。签发计划后、实际上传前再次核对写者所有权、同步目标、基线和 pending；进入上传窗口后冻结同步目标、基线及 pending 等上下文，普通岗位编辑仍可继续并留待下一次同步，不能先写错仓库再等确认时报错。远端单方面转移或删除本服务已经拥有的 live BOSS 账号绑定会形成身份冲突，不能自动让队列失去绑定；选择 live remote 结果也保留当前服务身份，远端删除仍须人工明确选择。BOSS 导入与人工业务编辑都仅延后冲突岗位及相关依赖；独立岗位的编辑会同时重基到 pending 候选，重基产生新冲突时停止该次编辑。直接修改现有 conflict key 会拒绝，避免最后解决冲突时覆盖新编辑。同批无关岗位仍可提交，只有账号身份、全局记录或无法归属到岗位的结构冲突才停止；恢复、切换同步目标和来源账号绑定等全局操作继续要求先解决冲突，不能绕过用户选择。

## 备份与草稿

“导出完整备份”含工作区、同步基线、冲突双方和当前浏览器草稿，不含令牌、SSH 会话或密钥。浏览器内自动快照最多 20 个，在删除、导入、恢复、升级和同步前保留，清理网站数据会删除它们。v0.8 本机正式提交另外留有独立磁盘历史；这些不同层次的保护不能互相替代。

页面无法启动时可“导出原始本地状态”，跳过模型校验保留原件供修复；本机缓存可能不是服务最新正式状态，诊断时也保留 `.local/workspace/`。损坏/未来格式不能当成空数据导入。

草稿单独存 localStorage，最多 200 份；输入、选择和中文组合输入结束保存。关闭表单不丢弃，恢复时新建副本 ID，成功提交只清理本次版本。草稿不自动正式提交或云同步，也不因服务后台导入而被覆盖。

`.local/backups/<浏览器来源 UUID>/` 保存含草稿完整备份：页面修改约 2.5 秒后聚合写入，打开时每 30 秒重试；每日首份固定，latest 为最近成功状态，最多 30 个日期及 latest。此流程仍需要网页和服务同时运行，立即关页可能来不及包含最后草稿；服务正式提交历史不受关页影响。目录 `0700`、文件 `0600`，均不公开。设备丢失仍需其他私有位置的副本。

恢复备份草稿先做数量/配额预检，再以新 ID 导入，工作区成功后完成草稿恢复。localStorage 与正式工作区无跨介质事务；强制终止可能留下未提交草稿副本，需在草稿箱核对。备份外层 v2 未变不表示旧版可读取其中的工作区 v3。

## 两种恢复

| 操作     | 行为                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------- |
| 合并恢复 | 相同 ID 采用备份记录，本机独有记录保留；备份删除标记联动关联记录                                  |
| 回到快照 | 采用快照记录，将本机和基线中快照没有的记录标记删除；保持当前同步目标和 base，成为一次新的本机修改 |

普通恢复不自动上传或标记已同步，恢复前保留原状态。本机模式通过 CAS 提交新版本；静态模式使用 IndexedDB 事务。含冲突的完整备份只允许“回到快照”，保留其同步目标、基线及冲突双方。当前已有未解决冲突时，先备份并处理冲突再恢复。

旧 schema v1/v2 数据 JSON 仍可逐版本导入。Markdown 导出用于阅读，不是完整往返备份。回退代码前必须保留 v3 完整备份、服务提交目录、采集队列与原始快照，不能让旧程序写新工作区。

## 恢复与迁移验收

用合成记录做非浏览器测试；真实页面由用户验收：明确迁移 → 核对岗位、同步基线、冲突及草稿 → 同一服务另一浏览器读取相同正式状态 → 服务断开时不能静默写缓存 → 恢复服务 → 关页后台导入 → 重开核对 → 手动同步往返。真实迁移未确认前应标“待人工验收”。

换电脑前先解决冲突、手动同步并下载独立备份；新设备先配置同一私有目标并同步，只在需要找回未同步内容时恢复备份。静态站点、不同设备仍是独立工作区；同一本机服务的浏览器共享正式工作区，但地址变化仍影响缓存、草稿和浏览器备份来源。

## v0.9.0 归属依据与本机诊断

正式数据、工作区与完整备份格式保持 v3/v3/v2。本次不批量审计或撤销历史已应用记录。新私有快照为 v4，队列为 v3，历史检查点内容为 v2（路径沿用 `.resume-checkpoint-v1.json` / `.change-checkpoint-v1.json`，旧内容仍可恢复）。新版本先读取旧材料再写新快照；不修改旧不可变快照。旧客户端不能处理新的私有协议，不应回退旧服务继续消费。

旧队列可恢复，但缺归属依据的简历观察只能进入 waiting，不据唯一候选岗位更新状态。新批次摘要绑定归属依据；稳定事件和事实 ID 不变。补证会触发等待项重评，同批自相矛盾的依据拒绝提交。人工否决、删除标记和工作区恢复缺口检查继续有效。

`.local/boss-collector/<账号>/attribution-diagnostics/` 和 `.local/boss-integration/attribution-diagnostics/` 保存首次出现的问题摘要，目录 0700、文件 0600。材料不含原始身份、聊天正文、简历或凭据，不同步到 GitHub。重复证据不追加相同材料，当前未应用数量不取决于文件数。不增加自动清理。

诊断写入失败时保留原进度，修复目录/磁盘问题后使用原有本地恢复流程；不要删除队列或检查点清零。`recover-saved` 只处理本机材料，不启动跟踪。页面和 `pnpm boss status` 提供只读原因，用户可核对后编辑岗位；人工编辑不确认平台观察的归属。

### 跨观察上下文的恢复（D034）

v0.9.7 不新增备份或私有协议字段。跨观察检查每次由当前未删除来源事件与整批候选重建，不能沿用恢复前的缓存或把回执视为事实存在。明确恢复缺口后，恢复材料仍须执行同一检查；新应用可进入 waiting/review，已应用历史不批量回退，人工否决和删除保护保留。早期采集诊断只代表当时材料，正式消费诊断加入当前工作区；诊断保存失败不确认相关交付。

### 会话关联规则的重放（D035）

v0.9.8 允许符合联系人、参与者、唯一岗位关联及跨观察检查的等待项和明确恢复批次，在缺少消息岗位身份时依据会话关联应用。缺归属材料的旧格式仍等待；回执不能替代事实存在，恢复缺口仍须用户明确核对，人工否决和删除保护保留。应用规则 v6 不迁移已有已完成决定，也不建立新的持久基线；会话依据应用由原因后缀标识，不代表已证明历史按岗位隔离。

## 人工忽略观察

ignore_boss_observations 的 payload 仅包含 applicationIds（1–100 个、不重复）。服务校验当前有效 waiting、BOSS 来源事实与观察、当前工作区账号绑定，按 expectedRevision 和 commandId 原子提交，存在 pending 同步冲突时拒绝。仅改变应用决定，来源事实和岗位不修改。备份与同步保留该决定；恢复早于忽略的备份可能恢复等待状态，仍需当前版本核对。忽略不豁免回执事实存在性或删除标记检查。共享数据 v3 与私有协议不变。

## 等待项资料重评（0.9.19）

应用规则 v8 可复用精确匹配的完整本机岗位资料完成普通缺标题观察。旧队列消费与恢复重放使用同一实现；原始缺失字段、事实和事件 ID 保留。已有岗位资料不代表简历归属已确认，人工字段、否决、忽略和删除规则不变，共享格式仍为 v3。

## 数据 v4 与恢复（0.10.0）

共享数据 v3→v4 增加岗位/应用平台状态、来源与时间，以及应用的人工补齐来源、目标岗位 ID 和规范链接。旧状态为 unknown，人工处理字段为空，不回退已应用历史。data、base、pending.data/remote 及各冲突侧共同迁移；未知字段和未来版本拒绝写入。工作区外层仍 v3，备份外层仍 v2，旧私有批次 v1–v3 继续读取，新的 v4 详情依据随批次摘要保存。人工 no_effect 结果和关闭标识须在同步、备份、恢复中保留；回执不替代恢复后的事实存在性。

恢复旧等待材料时，同一事实的当前人工资料补齐决定保持有效；旧 v3 备份缺少平台状态时保留当前人工状态。恢复含同步冲突的备份，若缺少人工补齐所需目标，停止恢复并保留当前工作区，不制造缺失目标或丢弃决定。

### 人工指定现存岗位（0.10.1，D039）

`resolve_boss_job_details` 的可选 `retiredOpportunityIds` 是明确指定的已删除重复岗位 ID 列表，必须与当前同一规范岗位身份的全部非目标匹配记录完全一致。列表不写成新的共享实体；命令、预期 revision 与持久幂等键按原有提交规则保存。目标空 `externalId` 的补齐和所选来源应用的人工决定共同提交，校验或持久化失败不产生部分结果；非空 ID 矛盾、现存重复项或仍有效的旧记录绑定继续拒绝。

旧记录的删除标记及原始来源事实保留，人工决定沿用 v4 的目标、规范岗位身份和处理来源字段。重放原命令返回原结果；恢复仍核对事实及目标存在性，不能把命令回执或人工映射当作平台详情证据。应用规则仍 v9，本次无数据、工作区、备份或私有批次迁移。

## 重复计算优化与恢复（0.10.2，D040）

v0.10.2 将应用规则升至 v10，共享数据保持 v4，该版本无新迁移字段或持久索引；v3→v4 去除重复账本适配后，所有工作区侧仍完整迁移并保留旧状态。进程内有界身份计算复用不落盘，不保存提交已验证标志；每次启动完整历史校验的约束从 v0.10.3 起由 D041 调整，当前状态及实际读取历史的未知格式拒写仍适用。

等待项重评从当前已有材料重建同事实候选，各候选独立核对，完整验证不能跨观察补字段，冲突不能被较新或较完整候选掩盖。相同材料得到稳定原因及业务结果，避免没有变化的重复提交。恢复、旧队列及明确恢复重放共用该规则；已有人工处理、删除标记、账号隔离、同步冲突与恢复缺口检查保留，旧回执仍不是事实存在的证明。

回退代码前保留完整私有备份和现有提交、队列、快照；规则版本改变不自动撤销已应用或人工决定。无需清理历史文件或检查点获得优化效果，不得为缩短启动时间直接删除它们。

## catalog 升级、备份与回退（0.10.3，D041）

应用 0.10.3 保持共享数据 v4、工作区 v3、完整备份 v2、BOSS 规则 v10 和服务协议 v1。HEAD 升为 v2、catalog 为 v1，完整提交及 identity 继续为 v1。首次旧盘转换完整审计并保存 catalog 后只原子发布新 HEAD，不改写旧提交、不制造业务编辑或改变正式 revision。旧代码不能写入新 HEAD 格式，不能通过去掉索引字段或替换 HEAD 原地回退。

恢复旧业务备份仍追加新编辑，当前 catalog 中的旧 commandId 继续保留，不能随旧业务状态回滚。catalog 命中、命令结果或磁盘队列回执都不能证明当前工作区仍包含来源事实，恢复缺口、删除标记和人工所有权继续核对。工作区备份不因新增索引而升级外层格式；复制整个磁盘工作区时应同时保留 HEAD 指定 catalog、完整提交及迁移原件。

新格式索引故障不得从最新业务快照重建历史或自动回退为空索引；需保留原文件并通过明确的完整历史审计诊断和修复。缺 HEAD 但已有历史或索引材料也不能初始化为空工作区。显式完整审计只处理本机数据，不触发 BOSS、平台采集、跟踪恢复或云同步。完整非浏览器检查、首次旧盘转换及普通冷进程启动已核对；转换前后正式 revision 和完整工作区摘要保持相同，本地重复消费未发现故障或恢复缺口，BOSS 跟踪保持停止。普通启动成本仍随当前数据和 catalog 命令数量增长，真实界面待人工验收。
