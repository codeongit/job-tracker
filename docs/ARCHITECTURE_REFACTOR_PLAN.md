# BOSS 采集重构清单

## 先看结论

这次想解决的是：**让 BOSS 采集流程更容易理解和维护，修改一项公共规则时，减少多个入口分别修改的情况。**

目前，增量跟踪和历史补录已经共用消息读取、简历含义和岗位归属规则。重复主要集中在三个地方：准备读取消息、安排岗位详情采集，以及把已保存的材料交给本机服务。

建议按下面三步调整。**目前仍是方案，代码重构尚未实施。**

| 顺序 | 准备调整什么                 | 主要收益                             |
| ---- | ---------------------------- | ------------------------------------ |
| 1    | 共用读取聊天与保存进度的步骤 | 账号检查、请求计数和中断恢复集中维护 |
| 2    | 共用岗位详情采集的完整流程   | 正常采集和单独补查详情使用同一套安排 |
| 3    | 共用把材料交给服务的步骤     | 多个导入命令使用同一套排队和恢复流程 |

预期收益是减少重复逻辑、明确每一步由谁负责。实际耗时是否改善，需要实施后测量。

## 第一步：统一读取聊天与保存进度

### 现在的问题

增量跟踪和历史补录已经使用同一个消息读取程序，但外围还有各自的准备和收尾步骤：检查账号与任务页面、检查平台转换版本、统计请求次数、保存材料和进度。调整这些步骤时，仍要分别检查两条流程。

### 调整方法

集中维护这套公共步骤：

1. 确认账号、浏览器实例和任务页面仍与本轮预定对象一致。
2. 按本轮范围读取消息，并统计实际发出的请求。
3. 保存读到的消息及暂时无法识别的原因。
4. 材料保存成功后，再记录这部分采集已完成。

增量跟踪继续选择发生变化的会话；历史补录继续按原来的轮转方式补查旧消息。各自读哪些会话、读到哪里停止，仍由各自的任务策略决定。

### 预期变化

以后调整账号检查或请求计数，只需修改公共实现。程序中断后，已保存的材料可以从本机继续处理，恢复步骤有明确的负责人。

### 验收条件

- 两种入口处理相同材料时，记录的消息类型、身份和处理结果与原来一致；各自的扫描范围保持。
- 已完成且没有变化的任务不增加历史请求。恢复已保存材料时不重新访问平台，下一项任务仍要检查剩余额度。
- 请求已经发出，即使之后保存失败，也计入额度；结果不明时不重发该请求。
- 模拟“材料保存失败”“进度保存失败”“恢复记录删除失败”，确认成功进度不会早于材料保存。

**另有一项需要核实的风险：** 可选的页面补采方式，代码中存在先标记完成、稍后才保存材料的顺序。它在生产中默认关闭，尚未证明发生过真实数据丢失。实施时先用模拟中断验证，再单独修正失败路径。

## 第二步：统一岗位详情采集

### 现在的问题

正常采集和单独补查详情，都在各自安排：先查哪些岗位、读取详情、采用哪些资料、失败后等多久、下一轮从哪里继续。底层的详情读取程序已经共用，整段流程仍有重复。

### 调整方法

让一个共用模块负责完整的详情阶段：

```text
选择本轮岗位 → 读取详情 → 核对并采用资料 → 记录失败等待时间和下次起点
```

两个入口提供本轮范围和额度，取得统一的阶段结果。岗位名称、用人公司等资料的判断继续调用现有规则。

### 预期变化

调整详情轮转或失败处理时，正常采集和单独补查可以一起生效。入口更容易看出本轮要做什么，也更容易区分详情故障和账号故障。

### 验收条件

- 相同材料、范围和额度下，两种入口产生相同的详情结果；原有采集资格和保存时机保持。
- 单个详情页丢失、普通导航或读取失败，仍只停止详情部分；登录、账号、浏览器实例、主任务目标等身份/安全异常，以及最终身份核验失败，仍按账号故障处理。
- 没有额度、没有合格岗位、部分成功、失败等待和下轮继续，都按原规则运行。
- 详情失败不撤销已保存的聊天材料；人工确认的资料继续受到保护。

## 第三步：统一把材料交给本机服务

### 现在的问题

增量、首批导入、指定日期补录、简历观察入队，以及已保存材料的恢复，都需要安排下面这些步骤：

```text
检查材料 → 按对应规则转换 → 保存诊断并排队 → 记录交付进度
```

这些步骤目前分散在多个命令中。修改“排队成功后程序中断，如何继续处理”时，需要逐个检查入口。

### 调整方法

由共用的本机交付模块负责材料检查、转换调用、排队、进度保存和恢复。各命令只选择本次范围及原有转换方式。

服务收到材料后，继续按当前工作区核对简历含义、岗位归属和人工保护，再通过现有唯一写入流程更新岗位。

### 预期变化

多个命令共用中断恢复处理。读取聊天、材料交付和岗位更新分别报告结果，能够看清流程停在哪一步。

### 验收条件

- 同一材料仍产生相同的事件、事实和应用身份，以及批次摘要和业务结果；首批、日期、简历与增量规则各自保留。
- 模拟“快照已保存但导出失败”“排队成功但进度保存失败”“岗位已更新但处理回执保存失败”，确认可从本机恢复，不重复修改岗位。
- 恢复旧备份后，重新核对当前数据是否包含对应事实；旧回执不能替代这项检查。
- 人工状态、删除记录、不同账号及同步冲突的处理保持。

## 改完后，谁负责什么

| 部分           | 负责的事情                                         |
| -------------- | -------------------------------------------------- |
| 跟踪调度       | 用户授权、一次只执行一轮、额度预留与结算           |
| 聊天与详情采集 | 读取平台资料，保存材料和采集进度                   |
| 本机材料交付   | 检查和转换已保存材料，排队并保存交付进度           |
| 正式岗位更新   | 根据当前工作区重新核对规则，保存岗位变更和处理结果 |

**采集完成、材料已交付、岗位已更新，是三种分别记录的结果。** 上一步成功后，后续步骤仍可能等待或失败。

现有消息含义、岗位归属、人工保护和正式写入规则继续复用。页面导航、岗位编辑、手动同步的整理留到后续评估。

每一步单独实施、提交和验收。完成这三步后，再判断采集主入口是否仍有重复，按实际收益决定下一项。

## 几个词的解释

- **账号与任务页面检查（原稿称“目标守卫”）：** 读取前后确认登录账号、浏览器实例、任务标签页和网址与绑定一致，防止页面或账号变化后继续采集。消息属于哪个岗位，仍由归属规则单独核对。
- **采集材料或观察：** 从平台读到的消息、状态或岗位资料。材料存在不代表已经用于更新岗位。
- **检查点、进度：** 记录已经保存到哪一步，供程序中断后继续处理。
- **回执：** 记录某个批次已经处理过；恢复旧备份后，仍需检查事实是否存在于当前工作区。
- **退避：** 某个岗位采集失败后，等待一段时间再安排下一次读取。

## 实现与验收对照（开发时参考）

### 代码依据与修改位置

现状核对日期为 2026-10-12，代码基线为 `68187539e26899042a4add76b10b5bec9a8a18fb`，应用 `0.10.21`、规则 `v16`。本次只改写清单的表达，三个代码阶段仍待实施；实施前重新核对实际工作树。

#### 阶段 1：历史读取

**现在：** [`tracker.mjs`](../collector/boss/tracker.mjs) 的 `collectChangedResumeOperation` / `collectResumeOperation` 共用 `runResumeHistoryRequests`，外围各自准备读取上下文。请求计数 wrapper 还了解 `platform_reference` 不占历史请求。

**准备调整：** 集中身份检查、已加载脚本版本检查和实际用量；提交复用 [`history-commit.mjs`](../collector/boss/history-commit.mjs)。不同策略的水位、页码、游标和检查点格式分别保留。

#### 阶段 1 的风险项：页面补采保存顺序

**现在：** [`dom-supplement.mjs`](../collector/boss/dom-supplement.mjs) 先保存 completed 并移除检查点，之后由 tracker 保存新材料。

**准备调整：** 先验证、再修正；保留默认禁用、唯一会话身份、零未读和页面所有权要求。正常结果保持，失败确认行为的修正单独记录。

#### 阶段 2：岗位详情

**现在：** 独立详情补查与正常轮次已共用底层读取器，仍各自安排公平选择、`collectDetailTitleEvidence`、`applyDetailEvidenceV2`、退避和游标计算。

**准备调整：** 共用完整详情阶段；原入口保留授权、锁及最终快照保存，范围显式输入。资料判断继续使用 `job-evidence.mjs`。

#### 阶段 3：材料交付

**现在：** [`boss-integration.mjs`](../scripts/boss-integration.mjs) 的 `applySnapshot`、兼容入队与 `recoverUnexported` 分别安排已保存材料的交付步骤。

**准备调整：** 共用交付顺序。转换器保留旧 ID、日期、输出和哈希规则；消费者的 `prepareBatch` 与 `WorkspaceStore` 保持。

### 必须保留的技术规则

`job-evidence.mjs`、`boss-job-materials.js`、`resume-rules.js`、`boss-attribution.js` 及批次/来源身份规则继续共用。采集、交付和正式消费各自按当前阶段可见材料核验。

- **读取与恢复：** 普通消息、简历观察和仅有 unresolved 的材料都保存及恢复；已完成检查点的零请求恢复只豁免当前任务。已发出请求在后续保存、导出失败时仍计用量；结果未知不重发。`recover-saved` 只用本机材料。采集证据、成功进度和检查点移除顺序分别验证。
- **平台转换版本：** 按 [D049](adr/0049-boss-versioned-opaque-action-evidence.md) 保留 `known / changed / unavailable`。正常授权读取只检查已加载脚本 URL，不自动下载或执行源码；URL 相同不证明字节一致。版本检查只控制已核实的不透明扩展分支，显式文字和 JSON 分支保持；有效保存依据的重放不依赖当前页面版本。
- **结果分类：** 保留 `classified / not_relevant / unsupported` 三种语义分类；空页、请求失败和未采到这三种读取情况也分别记录。固定错误及未支持原因保持、重复材料去重；读取完成不替代业务应用成功。
- **稳定身份：** 保留事件/事实/应用 ID、批次摘要及缺省转换输出；`observationIds` 定点过滤仍在事件映射之前。旧材料不因读取兼容格式取得新的可信地位。
- **业务保护：** 简历语义与归属必须在同一观察中成立。纯卡片按 [D043](adr/0043-boss-observation-only-archive.md) 存档、正式目标为空，真实发送仍独立检查。人工字段、否决/忽略、已应用历史、删除标记和账号隔离保持。
- **详情边界：** 保留岗位退避/隔离、公平轮转、所有权阻断、实际导航计数及 `detail / account` 故障分流。覆盖 `~`/长度边界、猎头代招、匿名公司、矛盾身份与人工确认匹配。
- **正式提交与冲突：** 保留单写者、expected revision/CAS、持久 commandId；响应重试复用原命令，版本冲突重新核对。提交前用最新正式 revision 重算，不直接提交缓存预览。保留受影响岗位及依赖的冲突范围、独立 pending 重基和双方材料；缓存失败不否定已确认提交。
- **交付与隐私：** 保留进程隔离、账号锁、producer lock、队列及检查点；诊断或关键保存失败不确认配套交付。未知格式/字段继续拒写。测试使用合成数据和临时目录，不访问真实平台、浏览器或工作区；公开文件不含真实记录、身份、正文、简历或凭据，诊断沿用私有权限和脱敏规则。

### 每阶段的交付要求

按[改动工作流](agents/change-workflow.md)分别核对现状和原始目标，使用独立预期验证完整结果及失败恢复，完成 Spec 与 Standards 审查。各阶段运行相关非浏览器测试、`pnpm check`、`pnpm format:check`；发布前运行完整 `pnpm test`，代理不运行 `pnpm verify`。浏览器与真实平台由用户验收，未确认前保留待验收状态。

当前计划保持原生 ES modules、现有存储和协议，无新增持久化索引、通用流水线框架或迁移。BOSS 纯业务与网页 adapter 的物理分离、详情导航、岗位编辑和手动同步编排仍为后续候选；`local-workspace.js` 与 `github.js` 的既有共用流程继续使用。

本次纯文档不升版本、不新增 ADR。未来代码发布维护版本与 CHANGELOG，关键决定变化时新增 ADR。保持明确授权、串行操作和现有预算；服务升级由用户执行，重启不恢复跟踪，不自动增加平台任务或 GitHub 同步。
