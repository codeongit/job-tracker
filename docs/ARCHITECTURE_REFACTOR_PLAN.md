# BOSS 采集职责重构记录

## 第一步：统一读取聊天与保存进度

### 原问题与实现

增量和公平补录原来共用消息读取器，外围身份检查、平台转换版本读取、请求计量及收尾各自安排。现在由 [`history/history-phase.mjs`](../collector/boss/history/history-phase.mjs) 的 `collectHistory` 共用这些步骤并返回材料、状态候选、统计和实际用量。

变化策略继续由 `change-history` 选任务，通过 `history-commit` 逐任务保存证据、进度并移除检查点。公平补录保持原页码、游标和检查点格式，先恢复已有证据，未完成页在有额度时继续；入口成功保存 JSON 与 Markdown 后调用 `settleSaved` 结算。列表准备与水位更新集中在历史阶段，零历史额度也保留准备工作。阶段不拥有跟踪授权或滚动小时预算。

已完成且未变化的任务不新增请求；检查点纯本机恢复只豁免当前任务，后续任务仍检查额度。仅有无法识别原因的材料也保存和恢复；已发请求在后续保存或导出失败时仍计实际用量，结果未知不重发。

### 页面补采保存顺序修复

原清单提出“完成进度先于材料保存”的风险，本次已通过合成中断场景修正，未据此宣称生产发生过数据丢失。

目标动作前先保存已校验输入 JSON；取得结果后，依次保存 v2 `result_ready` 检查点、规范 JSON 与 Markdown、完成进度，最后删除检查点。失败保留可恢复材料和实际动作计量。`recover-saved` 在账号锁内纯本机恢复取得的结果，再扫描交付快照；没有结果的旧 `switch_issued` 不自动重放。

DOM 仍默认关闭，人工策略、稳定身份、零未读和页面所有权要求保持。真实选择器和页面行为待人工验收；当前契约见[采集阶段](boss/IMPLEMENTATION.md#采集阶段)。

## 第二步：统一岗位详情采集

### 原问题与实现

正常轮次与独立补查原来分别安排岗位选择、详情读取、证据采用、失败等待和游标。现在由 [`details/detail-phase.mjs`](../collector/boss/details/detail-phase.mjs) 的 `collectDetails` 提供整段详情阶段，入口传入范围、额度和页面操作函数。

阶段返回采集材料、状态候选、实际导航量及可能的 `stateError`，不写快照或运行进度。独立详情先保存材料和导出，再保存详情状态并执行最终账号核验；整轮先执行最终账号核验，再保存最终快照与完整运行状态。状态候选失败时，独立入口保留已采用材料后报错，整轮在最终快照前报错；两者都不确认失败进度。采用失败仍保留已发导航用量，入口合并最新运行状态，保留中途连接重试和历史状态。

零额度、阻断或无目标不调用页面操作；公平选择、退避、技术隔离、游标、详情清理和人工资料保护保持。岗位资料判断继续调用共用纯规则。

### 最终账号故障分类修复

独立详情结束时若最终账号核验失败，优先报告账号范围及原安全错误码，保留已保存材料、清理结果和实际导航用量，与正常轮次一致。单个详情页丢失或普通读取失败仍属于详情故障，不扩大为账号失败。当前边界见[失败行为](boss/DESIGN.md#失败行为与限制)。

## 第三步：统一把材料交给本机服务

### 原问题与实现

首批、日期、简历、增量与恢复原来分别编排材料校验、转换、诊断、入队和 control 更新。现在由 [`delivery/saved.mjs`](../scripts/boss/delivery/saved.mjs) 的 `deliverSaved / recoverSaved` 共用顺序：

```text
严格读取与校验快照 → 按模式调用既有转换器 → 诊断与原子入队 → 交付检查点
```

请求显式携带 mode、当前与前一快照引用、control 和 inbox；不引入通用流水线框架。initial、dated、resume、incremental 各自保留原转换。首批批准名称/摘要及 30/10/60 范围、显式日期、跳过与确定性重试、来源序号、旧身份投影和批次摘要保持。增量没有事件时仍推进快照检查点，不增加序号；恢复按原快照文件名顺序逐份交付。

integration 保留生产者锁、内部票据、报告阶段与暂停处理。inbox 拥有诊断保存和队列原子写入；入队失败不推进 control，入队成功而 control 保存失败保留已提交批次和未确认进度。正式 consumer、WorkspaceStore、恢复事实缺口及人工保护继续沿用现有机制。具体模式语义见[入队与正式消费](boss/IMPLEMENTATION.md#入队与正式消费)。

**采集完成、材料已交付、岗位已更新仍是分别记录的结果。** 文件移动没有合并这些状态，也没有改变 shared model、存储、同步或备份的归属。

岗位证据在 `rules/job-evidence.js` 共用 `collector / detail_delivery / legacy_identity` 三种投影；现代资料选择与冻结的旧身份输入分别保留。批次全部格式常量在 `contracts/batch-format.js` 共用，当前版本仍 v8。Node `batch-validation.mjs` 只处理结构与哈希，`inbox-error.mjs` 共用错误类型，队列文件保存留在 inbox。`shared/paths.mjs` 固定源码根、CLI 与私有默认路径，移动模块后仍可从原命令启动。

## 检查范围与保留条件

`pnpm check` 以 Node 24 的 `SourceTextModule.moduleRequests` 解析生产静态 import、side effect import 与 reexport，不链接或执行代码。检查缺失文件、大小写、符号链接及父路径、循环、层级和 dist 全部传递依赖的独立性；语法检查递归覆盖采集器，测试不进入生产依赖图。私有、依赖、第三方技能与旧采集数据/profile 跳过。

基础 contracts/rules 的传递依赖仅限 contracts/rules 和纯叶 `dist/source-identity.js`，不能引入界面或共享状态模块。application 可使用共享 model。collector 不导入 control/delivery，只允许共用 Node 诊断叶模块；所有 Node 入口的传递依赖不能到 client。正常同层细分不受限制，没有新增总汇入口。

新增动态 import、require、importScripts、Worker、eval 或 Function 等写法会被保守拒绝。词法检测不能覆盖任意计算、别名与运行时生成代码，静态依赖合法不证明运行时全纯度。检查入口及发布分工见[维护手册](MAINTENANCE.md#每次改动)。

以下保留条件继续按原来源核对：

- [历史任务](adr/0028-change-driven-history.md)与[收敛处理](adr/0033-boss-import-convergence.md)：水位、页码、游标、恢复、实际计量及账号隔离。
- [明确系统确认](adr/0047-boss-explicit-system-confirmations.md)、[动作依据](adr/0048-boss-action-resume-confirmation.md)和[平台版本](adr/0049-boss-versioned-opaque-action-evidence.md)：同观察语义/归属、版本门槛、不透明扩展及稳定身份。
- [当前业务规则](boss/DESIGN.md)：人工字段、否决、忽略、删除、原应用历史及局部冲突。
- [数据与恢复](DATA_AND_RECOVERY.md)：单写者、CAS、持久 commandId、恢复事实存在性与完整冲突双方。
- [人工浏览器分工](adr/0017-manual-browser-testing.md)：合成测试不替代真实页面验收，不扩大平台授权。
