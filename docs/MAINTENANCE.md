# 开发、发布与排障

## 新电脑开发

安装 Node.js 24 LTS、Git 和 package.json 指定版本的 pnpm。使用系统 Node 即可，双击启动脚本的 Codex runtime 路径只是兼容现有机器的后备方案。

```sh
pnpm install --frozen-lockfile
pnpm service start
pnpm service status
```

需要本机源文件或 SSH 时，将 `config.example.json` 复制到 `.local/config.json`，按实际情况填写；不需要的字段可以删除。配置无效时服务会明确停止启动。使用系统 SSH agent，不要把私钥复制到项目。

真实浏览器相关测试由用户人工负责，详见下方分工；日常开发和启动不要求安装测试浏览器。

`pnpm start` 仍可在当前终端前台启动服务；`pnpm service start/status/stop` 提供带实例身份校验的管理入口。服务不登录自启，启动服务也不访问 BOSS。首次升级在工作台明确确认旧浏览器工作区迁移到本机正式存储，随后以 `pnpm boss start` 开始持续跟踪；重启服务后必须再次明确开始。普通批次入队和录入不需要重启或刷新。

## 每次改动

```sh
pnpm format
pnpm test
pnpm check
pnpm format:check
```

小改动可按影响范围运行定向非浏览器测试；发布前运行完整 `pnpm test`。`pnpm check` 检查语法与公开资源，`pnpm format:check` 检查格式。纯文档改动只需检查格式、链接与差异。

新增功能按模块职责修改，说明数据影响，补能复现具体故障的测试。不要重写测试只匹配实现；也不要将真实数据作为测试输入。

## 真实浏览器测试分工

按用户明确要求，真实浏览器相关测试由用户人工负责，包括页面交互、移动端布局、系统中文输入法，以及 Playwright/headless 等真实浏览器回归。代理负责实现、相关非浏览器测试、静态与格式检查，交付时提供简短的人工验收项；用户未反馈前，浏览器验收状态记为“待人工验收”。

除非用户后续明确委托，代理不启动、连接或控制浏览器，不安装测试浏览器，也不申请浏览器测试权限或尝试其他浏览器途径。`pnpm verify` 包含 `pnpm test:browser`，因此代理本地使用上面的非浏览器子命令。

现有浏览器脚本和 CI 保持不变，CI 结果单独报告，不能替代人工验收。人工需要运行隔离回归脚本时，可安装 `pnpm exec playwright install chromium` 后执行 `pnpm test:browser`；macOS 已装 Chrome 时也可使用 `PLAYWRIGHT_CHANNEL=chrome pnpm test:browser`。`pnpm verify` 仍可供人工或 CI 执行完整检查。

浏览器脚本只启动 dist 静态服务器、使用临时 profile，拦截所有外部请求，不读取 `.local`，测试使用合成数据。中文输入的自动回归通过 Chromium CDP 触发组合事件，系统输入法候选窗口与实际输入体验由人工检查。

## 发布

1. 下载完整私有备份；确认数据格式是否变化并阅读 DATA_AND_RECOVERY.md。v0.8 首次迁移另保留浏览器原工作区与 `.local/`，关闭旧客户端。
2. 更新版本号与 CHANGELOG，完成非浏览器检查，并记录人工浏览器验收结果；尚未验收时明确标为待人工验收。
3. 检查 Git 差异和暂存文件，确保没有 `.local`、真实记录、备份或凭证。
4. 提交代码，正常 push main，等待此提交的 GitHub Actions CI 成功。
5. 用对应版本的 Git tag 标记验证过的提交。当前仓库只运行 CI，不自动发布网页。
6. 仅服务代码或配置变更才停止并重启服务（CLI 管理的实例用 `pnpm service stop/start`，前台实例可 Ctrl+C）。刷新页面检查版本、模式、正式工作区 ID；按需重新 `pnpm boss start`，不能假设重启恢复跟踪授权。

未来发布公开静态网页只发布 dist。不能把 `.local`、本机服务或私有仓库内容作为构建输入。

GitHub Actions 使用 contents:read，不配置真实仓库 PAT 或 SSH key。依赖更新先更新锁文件、跑同一套检查；不自动合并依赖升级。

## 回退

代码用 Git 提交/tag 保留历史，优先修复或 `git revert` 产生新提交，不强推历史。数据与代码版本分开处理。

v0.2.0 将浏览器数据库升到版本2，因此不能直接用 v0.1.0 操作已经升级的同一浏览器数据库。出现故障先导出完整或原始状态，在独立测试配置验证恢复；不要删除当前网站存储。仍兼容云端 schemaVersion1；修复版应保留对工作区v2的支持。

v0.3.0 不改变工作区v2或共享数据v1，但完整备份升为v2，旧版不识别。回退前先下载包含草稿的v2备份，保留 `.local/backups/`；不要删除浏览器 localStorage。备份测试只操作临时目录，不能把用户目录当 fixture。

v0.7.0 的共享数据升为 v2，旧版工作台不认识 `sourceBindings` 与 `sourceEvents`。回退代码前先下载完整备份并保留 `.local/boss-integration/`、采集器原始快照及浏览器存储；不能让 v0.6.0 写回新格式。工作区/备份外层仍为 v2，但这不表示旧客户端可安全操作新共享数据。

v0.8.0 将共享数据、工作区升为 v3，本机正式存储改为不可变提交；备份外层仍 v2、磁盘存储和本机协议为 v1。不能用 v0.7 直接操作已迁移本机工作区，不能把浏览器缓存当唯一正式数据。先保留完整备份、`.local/workspace/`、队列和原始快照，在副本验证恢复；不手动改 HEAD 或删除活跃写者锁。旧静态客户端也应在首次 v3 云同步前关闭/升级，避免它仍基于旧远端版本工作。

## 排障

先运行 `pnpm doctor`、`pnpm service status` 查看 Node、Git 和服务身份，再运行 `pnpm boss status` 或 `pnpm boss doctor`。`status` 只读汇总生命周期、预算和队列；`doctor` 还会调用采集器的只读诊断，核验正式工作区、CDP 绑定/策略及生产者暂停状态，不创建、刷新或采集页面。连接文件存在或浏览器显示调试中，不等于账号、任务页、采集和正式录入均健康。

这些命令必须在运行服务的宿主机终端执行，或明确使用能够访问宿主机回环网络的执行上下文。Codex 沙箱、容器和其他受限执行环境可能能读取宿主机共享目录中的 `.local` 持久状态，却不能连接宿主机的 `127.0.0.1`；此时它们返回的 `SERVICE_UNAVAILABLE` 只表示“当前执行上下文无法访问服务”，不能据此断言宿主机服务已经停止。判断优先级为：宿主机终端的 `pnpm service status` / `pnpm boss status` 实时结果优先；`.local/boss-integration/tracking.json`、工作区 `HEAD.json` 和运行记录只用于确认最后持久化状态；沙箱内的回环连接失败不能覆盖宿主机实时结果。报告状态时必须同时说明命令执行上下文，不得把“服务不可达”“服务已停止”和“BOSS 跟踪已暂停”混为一谈。

| 现象/代码                        | 处理                                                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 沙箱中 `SERVICE_UNAVAILABLE`     | 在宿主机终端重新运行 `pnpm service status`；沙箱可能无法访问宿主机回环地址，不能仅凭该结果重启或判定服务已停止          |
| 页面版本与本机服务不同           | 重启本机服务，再刷新页面                                                                                                |
| 请关闭旧版页面                   | 关闭其他工作台标签页，刷新后完成数据库升级                                                                              |
| GIT_NOT_FOUND                    | 安装 Git，重新打开终端后再启动                                                                                          |
| SSH_AUTH_FAILED                  | 检查系统 SSH agent 和 GitHub SSH keys，可手动运行 `ssh -T git@github.com`                                               |
| SSH_HOST_VERIFICATION            | 在终端核实 GitHub 官方主机指纹，不关闭主机校验                                                                          |
| REPOSITORY_ACCESS                | 检查账户、私有仓库名和 SSH key 对应账号                                                                                 |
| VISIBILITY_RATE_LIMIT            | 等待 GitHub 接口限流恢复后重试                                                                                          |
| SSH_NETWORK / SSH_TIMEOUT        | 检查网络后重试；工作台会核对超时写入是否已完成                                                                          |
| CACHE_TARGET_MISMATCH            | 核对 .local 配置；停止服务后先保留缓存副本，再为新目标使用独立缓存                                                      |
| VERSION_CONFLICT                 | 重新同步获取新版本，有冲突时逐项选择                                                                                    |
| 超过5MB                          | 先导出独立备份，再设计历史原文归档；不要直接清空云端文件                                                                |
| 草稿保存失败                     | 先复制当前输入；整理草稿箱并检查浏览器存储配额，不要清理全部网站数据                                                    |
| 独立备份未完成                   | 按设置页错误检查服务、目录权限、磁盘空间或50MB备份限制；记录/草稿仍保留                                                 |
| 工作区无法打开                   | 下载原始状态；保留网站存储，在副本上检查版本或损坏字段                                                                  |
| BOSS_CHECK_TOO_SOON              | 避免重复触发同轮；当前不再使用 45 分钟/每日 16 次旧限制，先核对是否运行了旧版脚本                                       |
| BOSS_USE_UNIFIED_RUNTIME         | 不要直接运行旧 `boss-integration check/collect-cycle`；改用 `pnpm boss run/check`，由控制器签发单次预算票据             |
| 平台动作预算耗尽                 | 查看 `pnpm boss status` 的滚动小时预算，等待有关阶段恢复；本地预览、队列录入和未发出动作的失败不计入平台额度            |
| BOSS_INTEGRATION_PAUSED          | 保留 `.local/boss-integration/incidents/`，检查登录/验证码/账号/结构原因；确认消除后手动 `pnpm boss resume`，不自动重试 |
| 已保存快照转换或入库失败         | 先保留快照和故障材料，运行 `pnpm boss recover-saved` 纯本地补交；它不会连接 BOSS、消耗平台额度或启动持续跟踪            |
| BOSS 任务页失效                  | 暂停/停止后明确 `pnpm boss recover-page`，核对登录后 resume；不反复刷新或导航用户原标签                                 |
| 详情退避或技术隔离               | `pnpm boss status` 查看 `detailEnrichment`；等待 `nextRetryAt`，隔离项保留本机诊断且不混入业务人工核对                  |
| DETAIL_TAB_OWNERSHIP_MISMATCH    | 保留详情标签现场，确认归属问题消除后执行 `pnpm boss resume-details`；列表、历史和正式录入无需暂停                       |
| BOSS 队列有待录入                | 检查服务、首次迁移、账号归属、回执与局部冲突；已绑定正常队列由服务处理，不必重启或开工作台                              |
| waiting / protected / review     | 分别是依赖未满足、人工字段保护、真正歧义；先看原因，不把所有观察都当人工待核对                                          |
| 工作区 revision 冲突             | 重新读取服务最新状态，保留草稿后核对再保存，不盲目重放用户修改                                                          |
| 浏览器本地记录尚未迁移/身份不同  | 先下载含草稿的完整迁移备份并核对数量与摘要，再明确切换到当前本机正式工作区；不要清空 IndexedDB 规避保护                 |
| `SYNC_REMOTE_MISSING`            | 保留正式记录，核查远端文件、分支和路径；已有同步基线时不能按首次初始化把缺失远端重建为空文件                            |
| 协议或格式不支持                 | 升级页面/服务并保留原件；不删未知字段、不静默降级为静态写入                                                             |
| 活跃写者或 HEAD 不一致           | 保留 `.local/workspace/`，核对服务实例/外部修改；不手动删除锁或编辑 HEAD                                                |
| `WORKSPACE_DURABILITY_UNCERTAIN` | 停止继续录入并保留整个工作区目录，重启服务后读取实际 HEAD 与原命令结果；未确认前不要重提业务动作或确认队列回执          |
| 服务所有权不符                   | 核对 `pnpm service status` 与端口占用者；不要按旧 PID 直接终止进程                                                      |
| 已回执但来源事件缺失             | 可能恢复了旧备份；不要以磁盘回执判为正式录入，按页面提示以当前 revision 核对重放；版本变化后重新查看，不复活删除岗位    |

诊断不输出 Git 原始 stderr、私钥、PAT 或个人记录。报告问题时提供应用版本、错误代码、复现步骤；使用合成记录复现。

BOSS 接入自动化测试只用合成快照和临时目录，不触碰真实服务、浏览器或 `.local`。人工升级验收：确认迁移与账号绑定；切到其他标签检查后台读取不抢焦点；关闭工作台后核对正式录入；重复批次无重复岗位/事件；人工清空受保护；有冲突时只延后有关岗位；任务页或登录异常暂停且不刷新；服务重启不自动跟踪；静态版手动同步往返保持事实与应用去重。首批历史 30/10/60 及 2026-09-18 日期规则保持原义，不在升级中重导。未完成真实验收应明确记录待人工验收。

## v0.9.0 人工验收

非浏览器测试通过后，用户核对以下项目：

1. 设置 → BOSS 只读接入，能看到证据不足/归属冲突/采集问题数量及只读原因，候选岗位明确标识；这些问题不额外出现在行动页任务中。
2. 手动编辑岗位仍有效，重复本机消费不覆盖人工状态、不重复增加事实。两条同公司不同岗位的聊天不得相互改变简历状态。
3. 如需检查真实平台，明确开始跟踪后验证；当前独立会话映射及本人身份尚未核实，真实简历观察显示“证据不足”是预期结果。不要仅凭合成测试认定平台归属链可靠。
4. 服务重启后跟踪保持停止；核对需要时再明确 `pnpm boss start`。查看状态、诊断或恢复本机材料不会授权访问平台。

本轮版本没有自动部署、同步或启动跟踪。升级服务后刷新页面核对版本；浏览器验收仍需人工反馈。
