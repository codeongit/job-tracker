# 开发、发布与排障

本文维护开发检查、通用服务与同步排障、发布和回退。当前 BOSS 行为见[设计说明](boss/DESIGN.md)，技术契约见[实现说明](boss/IMPLEMENTATION.md)，启停、补录、状态、排障及人工验收见[操作说明](boss/OPERATIONS.md)。下方历史章节保留当时的执行与验收结果，不作为当前操作规则。

## 新电脑开发

安装 Node.js 24 LTS、Git 和 package.json 指定版本的 pnpm。使用系统 Node 即可，双击启动脚本的 Codex runtime 路径只是兼容现有机器的后备方案。

```sh
pnpm install --frozen-lockfile
pnpm service start
pnpm service status
```

需要本机源文件或 SSH 时，将 `config.example.json` 复制到 `.local/config.json`，按实际情况填写；不需要的字段可以删除。配置无效时服务会明确停止启动。使用系统 SSH agent，不要把私钥复制到项目。

项目应用的真实浏览器测试由用户人工负责；Archify 生成物的已授权例外见下方分工。日常开发和启动不要求安装测试浏览器。

`pnpm start` 可在当前终端前台启动服务；`pnpm service start/status/stop` 提供带实例身份校验的管理入口。服务不登录自启，启动或重启服务不授权 BOSS 访问。首次迁移按[数据与恢复](DATA_AND_RECOVERY.md#首次迁移与版本保护)核对；BOSS 后续操作见[命令与操作](boss/OPERATIONS.md#命令与操作)。

## 独立 UML 源码浏览器

`pnpm uml` 使用 [unclebob/uml-viewer](https://github.com/unclebob/uml-viewer) 浏览公开源码的目录、模块、静态依赖及源码位置。它是可选 JVM 桌面开发工具，不参与网页部署；Archify 的独立 HTML 继续用于系统职责和流程说明。选择依据见 [D059](adr/0059-standalone-uml-viewer.md)。

需要 Node 24、Git、Java 21+ 和 [Clojure CLI](https://clojure.org/guides/install_clojure)。Java 使用 `JAVA_HOME` 或 `PATH`；可用 `UML_JAVA_HOME` 与 `UML_CLOJURE` 指向专用安装。也支持项目本机目录：Java 放在 `.local/uml-viewer/runtime/java/`（macOS 的 Java home 为其 `Contents/Home/`），Clojure 可执行文件放在 `.local/uml-viewer/runtime/clojure/bin/clojure`。安装官方归档时校验发布方 SHA-256；运行环境无需全局安装，不提交二进制。缺少依赖时命令明确失败，不自动修改系统环境。

```sh
pnpm uml setup   # 首次联网获取固定上游和 Maven 依赖；不打开窗口
pnpm uml check   # 真实上游的无 GUI 加载、下钻、源码定位和隔离检查
pnpm uml         # 生成当前图，前台打开桌面窗口；等同于 pnpm uml open
pnpm uml export  # 仅生成图，不需要 Java/Clojure
```

上游固定为 `f65dafe93b3cb1b4e6bb02dbe41503ed05bd9ebf`，Clojure 库为 `1.12.0`、Quil 为 `4.3.1563`；checkout、CLI 配置、Maven 缓存和生成物均位于 `.local/uml-viewer/`。重复 setup 复用已完成内容；上游提交不符、tracked 文件改动或出现额外文件时拒绝执行，保留旧副本后重新 setup，不自动覆盖个人修改。升级上游须同时复核启动接缝和执行 `pnpm uml check`。

图来源是 Git 跟踪的 `dist/`、`scripts/`、`collector/` 中公开 `.js/.mjs` 工作树内容（新增文件需先 `git add`），排除测试和私有目录。统一解析静态 import、side-effect import 和 re-export，保留跨根依赖；文件不执行，符号链接、未知相对依赖和不支持的动态加载会报错。生成成功后原子替换 `diagram.edn`；失败保留旧图并返回非零状态，不能把旧图当作本次成功结果。

双击目录组件逐层进入，Esc 或左上角返回；叶模块显示详情，点击模块名或已识别成员打开内置只读源码窗口。修改代码后运行 `pnpm uml export`，在窗口按 `R` 重载；也可关闭后重新 `pnpm uml`。运行依赖与本机服务、BOSS 跟踪、工作区和 GitHub 同步无关。

独立入口禁用 Grok/tmux companion、mailbox 消费、自动改源码及 proposal 保存；相关按钮只提示使用本地命令。不要使用上游 `get-uml-viewer`、`./uml` 或 `--restart` 替代本项目入口，它们有不同的 companion 生命周期。没有指标时的红色质量标记表示缺失度量，不证明代码质量差。图表示模块静态依赖，不包含完整运行时调用、HTTP/文件交互或函数调用图；导出成员识别和行号定位沿用上游有限的解析器。

`pnpm test` 覆盖适配器合成测试，不要求 Java、不下载依赖；`pnpm uml check` 额外验证真实 JVM 连接，不替代桌面交互验收。首次使用或上游升级后，人工核对：总图包含三个生产目录、可逐层进入 BOSS 模块、跨目录依赖存在、源码窗口定位正确、重新 export 后 R 可刷新，退出不影响既有服务或会话。

清理时先关闭查看器，仅移走或删除 `.local/uml-viewer/`；它不包含正式工作区、备份或采集材料，勿扩大到整个 `.local/`。上游目前未提供 LICENSE；本仓库只保存自有适配代码，不再分发上游源码，后续复用或再分发前须核对其[许可状态](https://github.com/unclebob/uml-viewer/issues/14)。

## 每次改动

系统结构与模块职责见[当前架构](ARCHITECTURE.md)。BOSS 变更按[文档影响与维护](agents/change-workflow.md#文档影响与维护)选择设计、实现或操作正文，在同次变更中更新受影响内容，或说明无需更新的核对依据；本次 BOSS 职责重构及保留条件见[重构记录](ARCHITECTURE_REFACTOR_PLAN.md)。

代理实施按 [implement](../.agents/skills/implement/SKILL.md) 推进，独立审查按 [code-review](../.agents/skills/code-review/SKILL.md) 执行，检查范围随影响调整；[变更共用规则](agents/change-workflow.md)统一维护目标依据、阶段交接、验证覆盖、文档与交付记录要求。正式仓库变更按[议题与 PR 约定](agents/issue-tracker.md)通过任务分支交付，Issue 按需，合并另行授权；PR 摘要复用有效证据，本机保留详细及私有材料。

```sh
pnpm format
pnpm test
pnpm check
pnpm format:check
```

小改动可按影响范围运行定向非浏览器测试；发布前运行完整 `pnpm test`。非浏览器测试放在 `test/` 或 `collector/boss/`，以 `*.test.mjs` 命名，两个目录的子目录也会被收集；fixture/helper 使用普通 `.mjs` 后缀。收集范围以 `package.json` 为准，通配符由 Node 解析，不依赖 shell 展开或 Git 忽略规则；私有运行材料仍放在 `.local/`。浏览器回归保持独立入口。

`pnpm check` 递归检查 dist、scripts、test 和 collector 的 JavaScript 语法，检查公开资源、版本号，以及项目文档的本地链接、标题锚点、ADR 编号/索引和规则编号/保障映射对应；文档范围为根目录 Markdown、docs、collector、`.github` 及明确维护的技能目录，排除私有目录、依赖、名单外技能和测试材料，不访问外链。技能名单统一维护在 [owned-skills.mjs](../scripts/owned-skills.mjs)，包括初次引入后已在本仓库定制的技能及其共用参考；接管其他技能时更新该名单。`pnpm format` 和 `pnpm format:check` 在常规格式范围之外，分别格式化和检查同一名单内的 Markdown/YAML。纯文档改动核对格式、链接与差异；修改检查器本身还须运行其合成测试。

[规则保障映射](agents/rule-assurance.md) 记录各规则的已有机制、验证入口和缺口。检查器要求根 AGENTS 的实际顶层条目使用合法唯一编号，并与固定六列表中的行一一对应；漏项、重复、未知编号、缺少文档或空必填列均报错。代码块、引用示例和嵌套说明不计为顶层规则，总数不固定为 30；链接检查仍只验证目标存在和文档章节，不执行所列命令或推断测试通过。新增规则同次增加映射，编号稳定性及正文含义由差异审查核对。修改此机制运行 `node --test test/docs-check.test.mjs`，只使用临时目录和合成文件。

每次交付按[交付与验收记录](agents/change-workflow.md#交付与验收记录)在 PR 中说明来源与结果、适用规则和验证依据、被测提交及未验证项；仅本地交付在本次回复中说明。原始日志引用原位置。结果使用“通过、失败、未运行、需补查、待人工验收、不适用（附理由）”，随版本和场景保存，不把一次通过写成永久保障。

直接运行适用的非浏览器检查，以任务分支的候选 commit 固定最终审查版本；按[证据版本规则](agents/change-workflow.md#证据版本与检查配置)核对执行前后版本、检查配置和覆盖范围，变化后补查。流程语义变化按[流程回归案例](agents/workflow-regressions.md)选择受影响场景进行独立试验。

本机工作区客户端与服务接口的联动回归可运行 `node --test test/local-workspace-http.test.mjs`：真实客户端经回环 HTTP 调用真实服务，读写临时目录中的 `WorkspaceStore`，使用合成数据；客户端缓存和本机模式身份标记（authority）使用内存替身。它不启动浏览器，不访问真实平台或用户的 `.local`，已由文件命名自动纳入 `pnpm test` 及 CI 的非浏览器步骤。真实浏览器存储和页面交互仍按 [D017](adr/0017-manual-browser-testing.md) 由人工验收。

BOSS 检查点、分页、恢复或消息依据格式变化时，先运行 `pnpm test:boss-contracts`。此命令固定选择已有的运行状态、历史读取/阶段/提交、实际采集入口和动作依据测试，包含跨轮与旧版本门槛，不启动浏览器、不读取真实工作区；新增格式影响其他调用者时相应扩充集合。它用于尽早发现契约联动问题，发布仍运行完整测试和其余检查。定点排障先按[已有材料核对](boss/OPERATIONS.md#定点排障先核对已有材料)，复用[维护入口](boss/IMPLEMENTATION.md#定点维护复用入口)，避免另写预算、锁与保存协议。

生产依赖检查由 `scripts/module-check.mjs` 完成：Node 24 子进程以 `--experimental-vm-modules` 的 `SourceTextModule.moduleRequests` 解析静态 import、side effect import 与 reexport，不链接或执行被检查模块。生产图只包括 dist、scripts、collector 的 `.js / .mjs`，不纳入测试；检查文件存在、大小写、目录及父路径符号链接、循环和依赖层级。

dist 的全部传递依赖须留在 dist，不能依赖 Node 内置模块或外部包。BOSS 基础 contracts/rules 的传递依赖只允许同属 contracts/rules 的模块和明确的纯叶 `dist/source-identity.js`，不能引入 application、client、共享 model/storage 或界面模块；application 可以使用 model。采集器不能导入 control/delivery，只允许共用 Node 诊断叶模块；Node 服务及其传递依赖不能导入浏览器 client。

扫描跳过私有目录、依赖及第三方技能；旧采集目录中的 data/profile 等材料也跳过，不能把公开目录里同名的合法源码一并排除。新增动态 import、require、importScripts、Worker、eval 或 Function 等写法会被保守拒绝。动态写法检测是词法检查，不能覆盖任意计算、间接别名或运行时生成代码；静态依赖合法不等于模块或运行行为全都纯净。

结构检查不判断业务语义、历史版本是否过期或验收状态，结论仍由同一版本的独立 Spec 与 Standards 审查确认。

新增功能按模块职责修改，说明数据影响，补能复现具体故障的测试。不要重写测试只匹配实现；也不要将真实数据作为测试输入。

## 真实浏览器测试分工

按用户明确要求，项目应用的真实浏览器相关测试由用户人工负责，包括页面交互、移动端布局、系统中文输入法，以及 Playwright/headless 等真实浏览器回归。代理负责实现、相关非浏览器测试、静态与格式检查，交付时提供简短的人工验收项；用户未反馈前，浏览器验收状态记为“待人工验收”。

项目应用测试除非用户后续明确委托，代理不启动、连接或控制浏览器，不安装测试浏览器，也不申请浏览器测试权限或尝试其他浏览器途径。`pnpm verify` 包含 `pnpm test:browser`，因此代理本地使用上面的非浏览器子命令。

Archify 生成物的浏览器检查、预览与导出适用 [R023](../AGENTS.md#测试与发布) 的已授权例外，隔离范围及授权来源见 [D057](adr/0057-archify-browser-exception.md)。图表的浏览器检查与项目应用验收分别记录；前者通过不替代后者。

浏览器回归与 CI 持续保留，CI 结果单独报告，不能替代人工验收。人工需要运行隔离回归脚本时，可安装 `pnpm exec playwright install chromium` 后执行 `pnpm test:browser`；macOS 已装 Chrome 时也可使用 `PLAYWRIGHT_CHANNEL=chrome pnpm test:browser`。`pnpm verify` 仍可供人工或 CI 执行完整检查。

浏览器脚本只启动 dist 静态服务器、使用临时 profile，拦截所有外部请求，不读取 `.local`，测试使用合成数据。中文输入的自动回归通过 Chromium CDP 触发组合事件，系统输入法候选窗口与实际输入体验由人工检查。

### CI 失败定位与启动检查

CI 在同一 `verify` 作业内分别运行非浏览器测试、静态检查、格式检查、启动冒烟及完整浏览器回归。先打开红色步骤的具体日志；Ubuntu runner 迁移通知与退出码摘要不能单独说明根因。启动冒烟未通过时，不继续运行完整浏览器回归。

页面根元素的 `data-app-state` 初始为 `starting`；工作区读取和首屏初始化完成后为 `ready`，失败时为 `failed` 并保留既有恢复和应急导出界面。它不代表后台 BOSS 采集、备份或 GitHub 同步结果。测试共用就绪检查，初始化失败直接报告，不等待保存提示文案；迁移后重试会先回到 `starting`。

浏览器失败附件只包含隔离合成页面的截图、测试标识及简短初始化信息，不保存完整响应、请求凭据或真实数据。CI 失败作业的附件保留 7 天；本地人工回归输出位于忽略目录 `test-results/`，不要提交。无附件时以失败步骤日志为准，不因附件写入错误隐藏原测试失败。

人工可只运行启动冒烟：`node --test --test-name-pattern='^启动冒烟：静态工作台可初始化$' test/browser-regression.mjs`。代理不执行该命令；本地非浏览器测试覆盖启动标识成功、失败及重试状态转换，CI 仍需验证真实浏览器路径。

获准合并 PR 后，使用[合并脚本](agents/issue-tracker.md#合并脚本)核对版本与检查状态、执行合并并回读结果。脚本沿用已完成的独立审查与验收结论。

## 发布

日常任务在 PR 中记录变更、验证与风险，应用版本和 CHANGELOG 在用户主动发起版本发布时统一维护。发布决定见 [D058](adr/0058-manual-version-releases.md)。用户主动发起版本发布后，代理可准备版本 PR，并在获准合并、满足发布条件后完成该版本的 tag 与 GitHub Release；合并仍按[议题约定](agents/issue-tracker.md#合并与验收)另行授权。

1. **确定范围。** 核对远端已有 tag 与 Release，固定上次发布 tag 的提交和本次目标，读取区间内合并的 PR、Git 差异及已有版本记录。缺少可用 tag 时先确认起始 commit；首次采用此流程时，在版本 PR 说明历史记录覆盖范围。版本标题本身不证明已经发布。
2. **准备版本 PR。** 在任务分支同步更新 `package.json` 与 `dist/version.js`，在 CHANGELOG 顶部整理本版本摘要。版本使用 `X.Y.Z`，按修复、新增功能与兼容性影响确定，并在 PR 说明选择依据；数据、协议与备份等格式版本仍按[数据与恢复](DATA_AND_RECOVERY.md#版本与两种存储模式)随格式变化维护。版本 PR 列明起点、目标范围和适用验收状态。
3. **验证与合并。** 运行完整 `pnpm test`、`pnpm check` 与 `pnpm format:check`，完成同版本独立审查、适用人工验收和 CI。核对公开差异不含真实记录、备份或凭证；取得合并授权后，按既有流程合并版本 PR。
4. **标记版本。** 固定版本 PR 的实际 merge commit，核对该提交的双版本、摘要、CI 及适用检查和验收依据；合并带来相关变化时先补查。为这个明确提交创建附注 tag `vX.Y.Z`，只推送该 tag。main 后续前进不改变本次目标；已有同名 tag 时先回读目标，匹配则沿用，冲突则停止，不移动或覆盖已发布 tag。
5. **发布摘要。** 基于已回读确认的远端 tag 创建 GitHub Release，复用 CHANGELOG 的本版本摘要与已知限制。回读 tag 的目标提交、Release URL 和正文后报告完成。响应未知时先查询再续做；tag 已成功而 Release 失败时保留已完成状态，只补后续步骤。

### 版本摘要

按版本倒序排列，标题包含版本和北京时间发布日期（`YYYY-MM-DD`）。参考 [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) 的分类，按需使用“新增、变更、弃用、移除、修复、安全”，省略空类别。条目面向使用者说明关键结果，关联 PR，并提供版本 tag 或完整比较链接；GitHub 自动生成的说明可作为整理输入，最终正文需核对取舍。

优先保留用户可感知变化、重要修复、兼容性变化、升级操作和数据恢复限制；开发细节沿用 PR。已有“未发布”材料可在发版时按实际范围归纳，未纳入本次范围的内容保留待发布状态。历史正文与验收状态保持，新的摘要不能把未验收事项写成已通过；相关验收尚未完成时，版本 PR 保持待验收。

### 本机升级与网页部署

## 排障

先运行 `pnpm doctor`、`pnpm service status` 查看 Node、Git 和服务身份。BOSS 的诊断入口、状态含义和逐项错误处理统一见[操作说明的排障](boss/OPERATIONS.md#排障)；连接文件存在或浏览器显示调试中，不等于账号、任务页、采集和正式录入均健康。

这些命令必须在运行服务的宿主机终端执行，或明确使用能够访问宿主机回环网络的执行上下文。Codex 沙箱、容器和其他受限执行环境可能能读取宿主机共享目录中的 `.local` 持久状态，却不能连接宿主机的 `127.0.0.1`；此时它们返回的 `SERVICE_UNAVAILABLE` 只表示“当前执行上下文无法访问服务”，不能据此断言宿主机服务已经停止。判断优先级为：宿主机终端的 `pnpm service status` / `pnpm boss status` 实时结果优先；`.local/boss-integration/tracking.json`、工作区 `HEAD.json` 和运行记录只用于确认最后持久化状态；沙箱内的回环连接失败不能覆盖宿主机实时结果。报告状态时必须同时说明命令执行上下文，不得把“服务不可达”“服务已停止”和“BOSS 跟踪已暂停”混为一谈。

0.10.14 的 start/status/doctor 共用运行记录端口和服务身份检查。`healthCheck` 显示 `reason`、`durationMs`、`timeoutMs`、`attempts` 及已取得的 `httpStatus`：`timeout` 是检查超时，`connection_refused` 是端口拒绝连接，`permission_denied` 是执行环境不允许连接，`invalid_response` 是响应格式无效，`http_error` 是异常 HTTP 状态，`identity_mismatch` 是服务身份不符，`transport_error` 是其他未明确的连接异常，`ok` 才表示身份核对通过。进程存活不能替代健康及身份核对；这些新原因不能追溯证明升级前一次故障的根因。

status 和 doctor 只检查一次且不写日志。只有 start 对仍存活进程的超时／连接拒绝等待 200ms 后再检查一次，每次最多 1500ms，两次预算 3200ms；首次启动原 30 秒等待窗口不因补查重置，启动耗时仍以实际指标为准。权限、格式及身份异常立即结束核对，不自动杀进程、清理运行记录或创建另一个不确定实例。doctor 只在得到已验证的明确版本差异时建议重启，缺失信息显示未知。

失败或未确认的 start 向 `.local/service/service.log` 追加 `service_start_diagnostic` 摘要，只含时间、固定原因、端口、PID、记录阶段及检查耗时等白名单字段，权限 0600，不保存凭据、响应正文或原始异常。`diagnosticSaved: false` 表示摘要未能保存，服务判断与所有权保护仍保持；不要因此盲目重复启动。CLI 诊断代码下次运行即可生效；如果已验证的服务版本不同，由用户重启服务并刷新页面，重启不恢复 BOSS 跟踪。相关回归仅使用合成状态，未进行本机服务重启或平台采集。

## 历史执行与验收记录

以下章节记录相应版本当时的改动、兼容范围、执行结果和人工验收要求。章节中的“本次”“本轮”指该历史任务；尚未确认的真实验收继续保持原状态。当前 BOSS 操作按[操作说明](boss/OPERATIONS.md)执行，不从历史记录扩大授权或恢复已结束的临时任务。

### v0.9.0 人工验收

非浏览器测试通过后，用户核对以下项目：

1. 设置 → BOSS 只读接入，能看到证据不足/归属冲突/采集问题数量及只读原因，候选岗位明确标识；这些问题不额外出现在行动页任务中。
2. 手动编辑岗位仍有效，重复本机消费不覆盖人工状态、不重复增加事实。两条同公司不同岗位的聊天不得相互改变简历状态。
3. 如需检查真实平台，明确开始跟踪后验证；身份字段排查已收尾，具体观察仍按联系人、参与者、会话及跨岗位规则判断；历史缺少材料时仍显示“证据不足”。不要仅凭合成测试认定平台归属链可靠。
4. 服务重启后跟踪保持停止；核对需要时再明确 `pnpm boss start`。查看状态、诊断或恢复本机材料不会授权访问平台。

本轮版本没有自动部署、同步或启动跟踪。升级服务后刷新页面核对版本；浏览器验收仍需人工反馈。

#### 服务启动确认（0.9.3）

`pnpm service start` 最多等待 30 秒，以运行记录与匹配实例的健康检查确认就绪。若返回 `SERVICE_START_NOT_CONFIRMED`，表示尚未确认就绪，不等于进程已经退出；先执行 `pnpm service status` 并检查本机服务日志，避免重复启动。服务启动不恢复 BOSS 跟踪授权。

#### 启动耗时与历史索引（0.9.5）

`pnpm service status` 在服务就绪后返回 `processStartedAt`（进程创建时间）、`readyAt`（监听就绪时间）和 `startupDurationMs`（初始化耗时）。UTC 时间按本地时区查看。旧服务记录缺少的指标返回 null。`SERVICE_START_NOT_CONFIRMED` 只表示 30 秒内未确认就绪；初始化较慢时不要重复 start，先检查状态及服务日志。

v0.9.5 工作区初始化仍校验全部不可变历史提交，幂等索引只常驻提交文件、摘要、版本、哈希和小型回执，不保留全部历史工作区。v0.10.3 的启动校验和持久 catalog 改为下方 D041 规则；首次旧盘转换和显式完整审计仍需全历史读取，不保证在 30 秒内完成，不通过删除原始历史加速。

### 一次性身份排查结论（0.9.6）

本轮双会话样本已覆盖两个目标。联系人响应的 `encryptJobId` 与各自列表岗位一致，联系人、本人账号及消息参与者能对应。批准检查的消息岗位字段没有出现，未知字段名只计数；部分 `body.extend` 为字符串，未解析其中内容。结论限于这次检查范围，不能推断整个平台不提供岗位依据，也不能以联系人岗位代替消息自身岗位身份。

本轮排查以“消息岗位证据不足”结束，原始误关联原因仍未查明，自动简历联动保持严格关卡；人工仍可在既有岗位编辑中修正状态。无需继续重复采样。临时取样和一次性任务代码、专用测试已删除，既有补录入口恢复正常轮转。本机私有 attribution-diagnostics/identity-check 下的 v1/v2 脱敏样本和 `.conclusion` 保留作依据，不会因采集、浏览器清理或本轮代码清理而删除，也不进入公开源码和共享数据。目录外的一次性任务记录已失去执行作用。

若以后明确要求核实字符串扩展字段或其他新范围，先确定具体只读白名单和隐私边界，单独安排一次排查；现有结论不会自动扩大采集范围。

### 跨观察防错（0.9.7）

“同一消息关联了不同候选岗位”表示候选关联矛盾，进入归属冲突摘要，不能据此断言平台响应错误；“会话曾关联不同岗位，消息缺少岗位身份”表示证据不足。两项均只读，不新增行动任务或确认按钮。人工仍用既有岗位编辑修正状态，平台文案“附件简历请求已发送”的含义保持已发送。

无需为该升级重新采集。新材料和恢复重放均经过统一关卡；已应用历史、人工否决和人工字段不自动回退或重新应用。缺少完整身份的旧队列不能绕过检查。用户浏览器验收：确认两项原因与候选标签显示正确，人工状态仍有效，普通列表建档不受简历拦截影响；服务重启后跟踪保持停止。没有发现异常不代表身份核实完成，自动联动未宣称恢复。

### 会话关联联动（0.9.8）

用户明确取消消息岗位身份必填后，联系人与消息双方完整匹配、会话关联岗位可唯一落到既有岗位且无跨观察异常时，可联动简历及原有状态。已有等待项、补录和明确恢复重放同样适用；无归属材料的旧队列仍等待，人工否决和人工字段不重新应用。成功使用会话依据的来源应用原因带 conversation_association 后缀，不表示消息岗位身份已核实。

加载新版服务需要用户重启服务，之后按需要明确 `pnpm boss start`；重启本身不恢复跟踪。无需为字段核实再次循环补录，也不自动执行历史纠正。人工验收：无消息岗位身份的正常发送观察可联动，错误联系人、跨岗位重复及岗位变化仍拦截，人工状态保持。若发生新的误关联，保留本机材料并明确编辑或否决，不把历史联系人岗位视为已证明的消息岗位。

### 单条消息预览收尾（0.9.11）

用户授权代理执行后，重新登录并核验账号、恢复聊天页绑定，单次人工 backfill 已完成临时预览：一个联系人请求和一个第一页历史请求，无 DOM 操作或详情导航，不生成业务批次、快照或历史进度。采到的是平台职位竞争者 PK 卡片，扩展字符串位于 body.articles[0].extend，内容为高亮位置和头像列表；样本中没有直接 body.extend。这条卡片不能证明简历发送，也不能据此说明所有消息的扩展字段都不含岗位身份。
