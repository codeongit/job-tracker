# D005：三方合并、显式冲突与删除标记

> 2026-09-21：[D026](0026-local-authoritative-workspace.md) 将本机模式下后台自动导入和人工业务编辑的阻塞范围缩小到冲突岗位及依赖，并启用独立字段三方合并；静态模式的整库冲突冻结、同字段人工选择、删除标记和手动同步仍按本条。以下保留原决定作为历史理由。

- **记录日期 / 状态：** 2026-09-11 / 部分由 D026 替代。
- **问题：** 多设备修改和删除同一批记录时，如何避免静默覆盖？
- **决定：** 使用稳定 ID 对齐 `base/local/remote`。当前规则按字段合并同一记录的独立变化；同字段分歧及有关联语义的原子字段组由用户选择，双方冲突版本均带上已确认的独立变化。删除保留 `deletedAt`，岗位删除与新增关联任务也进入冲突处理。写入使用文件版本校验和普通 Git push。
- **原因：** 云端最后确认版本提供共同基线；保留删除标记使其他设备能够识别删除。显式选择保留双方内容，避免仅凭设备时间决定覆盖顺序。
- **备选与取舍：** “最后写入者优先”实现简单但可能覆盖另一设备的修改；整条记录选择较保守但会放大无关字段冲突。v0.8 已采用字段级合并，并把岗位状态语义和任务完成语义分别作为原子组，避免拼出无效组合。
- **约束：** 静态模式在未解决冲突时不继续业务编辑；本机 v0.8 按 D026 仅阻断冲突岗位及依赖，把独立岗位编辑重基到 pending，恢复和切换同步目标等全局操作仍须先解决冲突。超时写入先读回核实，不能盲目重复提交；非法或在已有基线后缺失的远端数据不得解释为空数据。
- **重新评估条件：** 同记录冲突频繁且用户很难选择，或引入多人实时协作；再评估字段级规则或新的同步模型。
