# 代码改动：现状理解与目标核对

适用于功能开发、缺陷修复、重构、性能优化、配置和迁移。共用要求在此维护，诊断、实现、测试和审查技能引用本页。

技能回引本页时，只查阅相应共用规则，不重新启动整套流程。

## 1. 修改前分别核对现状与目标

开始执行已明确目标时，按[任务记录试行](#任务记录试行)创建或沿用任务说明，记录实际开始时间；后续核对与交付复用同一说明。

**现状依据：** 从受影响的入口追到主要逻辑及输出，读取关键调用者和依赖，核对相关测试、配置及既有决策。按实际影响检查接口约定、副作用、数据或资源所有权、异常处理、顺序与并发、持久化及后续读取或恢复；纯文字或局部样式调整只核对相应路径。必要时用最小合成输入或获授权的只读验证确认实际行为。

**目标依据：** 从用户原始要求、已确认的业务规则和外部契约确定可观察结果、必须保留的行为及完成条件。区分用户明确要求、当前系统约束、实现者建议和待验证假设；新方案、新 ADR 和新测试同属待审材料。当前行为可包含缺陷，不能仅凭现状决定正确预期。

**适用规则：** 按任务影响从 [AGENTS](../../AGENTS.md) 及[规则保障映射](rule-assurance.md) 选择相关规则 ID，核对条目中各项要求及已知缺口。文件路径和映射用于提示范围，仍须追踪受影响机制；不要求每次勾选全部规则，也不把映射中的验证入口当成本次已通过的证据。

**修改前基线：** 记录任务起点与变更范围。已有提交可用 commit/ref；起点含未提交修改时，保留相关公开文件的修改前副本及状态，在本机临时目录或已有任务笔记中使用。尊重原有修改，记录本任务改变哪些文件；私有材料按项目权限和脱敏规则处理。

简短记录以下内容，写入任务说明或链接已有任务笔记、评论；小改动可用几句工作说明，无需另建背景文档或 ADR：

| 内容 | 要求                                         |
| ---- | -------------------------------------------- |
| 现状 | 关键链路、约束和来源位置；运行结果只说明现状 |
| 目标 | 可观察结果、保留条件及原始要求或契约依据     |
| 影响 | 修改点、受影响的调用者及后续行为             |
| 假设 | 尚未确认的事实，以及如何验证                 |
| 验证 | 关键场景、失败或边界场景、检查入口           |

**完成条件：** 能用来源位置或最小验证解释受影响机制；关键预期有独立依据；会改变方案的假设已解决。可从代码或已有资料查出的事实由代理核对，已授权事项继续执行；只有确需用户决定的意图或授权缺口才提问，独立工作继续推进。

## 2. 实现与验证

按影响逐步修改并核对依赖。增加测试时，以原始要求、契约或独立推演的已知结果确定断言；用合成材料表达已确认的历史状态。测试预期与被测实现分别核对，避免从本次实现的返回值生成预期，或让当前实现生成事故状态后自行证明正确。

测试先行开发、缺陷回归或编写集成测试时，读取并使用 `tdd` 技能（`.agents/skills/tdd/SKILL.md`），复用已有反馈循环与已约定的接缝。缺陷修复沿用诊断技能的复现、定位、修复与回归流程，完成一次有效反馈循环。验证覆盖实际影响，复用已有检查；检查通过仍需核对目标是否正确。

**覆盖核对：** 涉及跨层接口、持久化或运行模式变化时，实施与独立审查均核对受影响的入口到结果路径、测试实际经过的生产组件、替身边界，以及对应的验证和仍未验证的部分。发现连接缺少验证时，补充测试或明确剩余限制及对应验收安排。在已有任务说明中按影响简述即可；测试数量或各层分别通过不能证明它们之间的连接已经验证。局部变更只核对受影响路径，不要求每次重列全项目覆盖。

**完成条件：** 目标场景满足预期，必须保留的约束有对应依据或验证，错误路径及剩余不确定性明确。发现新的影响或原假设不成立时，更新现状与目标核对后继续，按项目规则完成相关检查。

## 文档影响与维护

修改 BOSS 行为、归属、业务规则或额度前读 [DESIGN](../boss/DESIGN.md)；修改模块、字段、交付或恢复契约前读 [IMPLEMENTATION](../boss/IMPLEMENTATION.md)；修改命令、状态说明或排障步骤前读 [OPERATIONS](../boss/OPERATIONS.md)。跨类变更读取对应正文，共享事务与恢复仍按[数据与恢复](../DATA_AND_RECOVERY.md)核对。

- 同次变更更新受影响的完整正文，其他入口保留摘要和具体章节链接，避免第二份完整定义。
- 每次交付或 PR 说明影响哪些文档、更新了什么；无需更新时说明核对依据。纯内部重构不机械要求修改全部文档。
- 行为、接口或关键决定变化先分别核对现状与原始目标，再更新正文、代码及测试。历史决定保留理由，关键决定变化按[ADR 维护约定](../adr/README.md#如何维护)新增；待实施方案与历史验收记录明确标识。
- `pnpm check` 检查项目文档的本地链接、标题锚点、ADR 编号/索引及规则编号/保障映射对应，`pnpm format:check` 检查格式。检查不访问外链，不执行映射中的命令，不推断历史版本或业务含义；独立审查核对规则是否准确、例外是否完整及历史范围是否被扩大。

**完成条件：** 文档影响有明确结论、相应正文及引用已更新、结构检查通过，Spec 与 Standards 审查在同一版本确认结果及限制。无需更新的结论同样进入审查。

## 3. 独立审查

进入独立审查阶段时，读取并使用 `code-review` 技能（`.agents/skills/code-review/SKILL.md`），由其组织材料、分派双轴审查并记录结果。

审查输入包括原始用户要求或原始规格、修改前基线、相关既有规则，以及完整的本次变更范围。未提交修改、暂存修改和新增文件同样进入审查，冻结或校验所审文件的版本；原有改动和本任务改动明确区分。

Spec 审查分两次提供材料：

1. **独立核对现状与目标：** 先给原始要求、基线代码和相关既有规则，由审查代理独立列出机制、预期影响和保留条件。此时不提供实现者的结论、新方案、新 ADR 或修改后的测试。用独立上下文启动审查代理，并保留它的判断；对同一目标复用，不重复要求用户确认。
2. **对照修改：** 再提供同一范围的 diff、新增文件和测试材料，核对前一步判断。发现原始规格也有歧义或与既有规则冲突时，报告具体来源和影响；实现者假设不能自行升级为“用户已确认”。

Standards 审查按项目规范独立检查相同版本的变更。简单改动按影响缩小材料和输出，两阶段仍可各用几句话完成。审查发现新增影响时补查相关基线；审查期间文件变化，重新核对受影响内容。

两个审查轴同时核对适用规则的选择及证据是否足以支持结论。规则或保障映射变化时，对照基线检查规则删除、含义变化和编号复用，确认部分覆盖与未验证项已明确；结构校验无法判断这些历史和语义问题。

### 发现与交接

按证据区分三类，分别汇报，避免把设计偏好计为缺陷：

- **确定问题：** 给出来源位置、适用要求、触发条件和具体影响，标明是本次引入、加重还是基线已有。仅有代码形状相似或气味名称不足以成立。
- **改进建议：** 说明收益、代价及适用条件；未采纳的建议不自动升级为阻断问题。
- **待核实：** 说明缺少的证据、受影响的结论和核实方式；由代理解决可查证的事实，真正需要用户决定的意图缺口才提问。

阻断项是违反硬约束或妨碍目标、必须保留行为成立的确定问题，以及会改变正确预期或关键机制判断的未决事项；注明阻断理由与解除条件。既有问题按实际影响判断是否阻断，不归为本次新增缺陷；无关建议不扩大本次交付范围。

审查者提出问题与重构建议；实施者在已有任务授权内处理阻断项，判断并执行有收益的重构，按影响验证后交回审查者复查。纯审查任务交付发现与限制，实施交接不自动扩展用户授权。修正后仍保留原发现与处理结果，不把已修复的问题当成误报。

**完成条件：** 两个审查轴明确报告分类后的发现、覆盖范围和未核实内容；声称完整审查通过或实施完成前，阻断问题已解决，受影响内容已复查。缺失原始目标或关键机制仍未核实时，Spec 保持未完成。只依据错误或缺失规格得出的“实现一致”不能作为完整验收，测试通过也不能代替目标核对。

## 4. 交付与验收记录

在已有交付说明或任务记录中标明被测 commit；存在未提交修改时，同时保留所测差异与新增文件的快照或内容摘要（如文件哈希），使结果能对应实际文件版本。分别说明本地检查、CI 和人工验收的结果与未完成项；未取得的结果明确标为未运行、未查询或待验收。

记录本次相关规则 ID、实际检查或审查证据、适用的代码状态及剩余未验证项；多个规则共用同一证据时可合并说明。每项验证使用“通过、失败、未运行、待人工验收、不适用”之一，不适用附理由。代码或测试文件存在只证明入口存在，规则保障映射不保存永久通过状态。证据只保留必要的公开摘要和来源，不写入真实求职数据或凭据。

审查统计复用 `code-review` 技能生成的 `.local/reviews/<编号>/` 记录，交付说明附统计摘要和记录链接；计时、判定和反馈更新按该技能执行。

用户后续提供验收反馈时，追加到任务说明并链接对应版本的证据。代码继续变化时，评估哪些已有结果受到影响，补充相应验证；保留旧结果适用的版本与范围。

**完成条件：** 能确定每项结果对应的代码状态、实际验证范围和剩余限制；后续反馈与改动不会把旧版本结果误作当前版本验收。

### 任务记录试行

从本试行方案交付后的新开发任务开始，由主代理维护 `.local/tasks/<任务编号>/delivery.md`，编号使用 UUID。只在被 Git 忽略的本机目录保存任务材料，不补造历史任务的时间或验收结果；本轮保持人工记录，不增加统计命令、后台提醒或看板。

- **开始任务：** 为一个明确的验收目标创建一份说明，记录目标来源、类型（docs/code/mixed）、影响范围和实际开始时间。同一目标的多次审查、复查及后续修复沿用编号；跨会话继续已明确关联的任务时沿用原说明，新增独立目标另建任务并关联来源。
- **首次交付：** 交付可验证版本、必要检查结果及适用的人工验收项时，记录首次交付时间与版本，固定保留；在给用户的交付说明中附任务记录链接。审查与验证材料仅保存链接，审查问题通过记录路径和问题编号引用，不复制台账或向审查 JSON 增加任务字段。
- **收到反馈：** 按自然反馈追加日期、对应版本、证据和处理结果；不在每次交付额外索取确认。后续版本及反馈另记，不覆盖首次交付。用户发起复盘时，再核对影响结论的关键缺口。

### 任务评估口径

| 项目           | 口径                                                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 首次可验收时间 | 实际开始执行已明确目标至首次可验收交付的经过时间，包含等待；不是用户确认验收的时间。只在两端时间可靠时计算，未交付记未完成，缺失或异常记未知，不用审查时间代替或倒推。时间记录包含时区。 |
| 验收状态       | 以最新交付版本为准，默认待确认；仅依据该版本的明确反馈更新为通过或需修正。历史反馈保留日期、版本与依据，不沿用至新版本。实施前的“可以”、检查通过及用户沉默均不自动算验收通过。           |
| 返工轮次       | 首次交付后，为满足原目标完成的一批修正算一轮，记录完成日期与修正版本；同批多个问题只算一轮。交付前修正、测试重跑不计，新需求另记。                                                       |
| 交付后已知缺陷 | 确认存在于对应交付版本且属于原范围后计入；记录发现日期、影响与证据，按根因去重汇总。已有审查问题引用原编号及判定；交付前已修复的审查问题不计入。                                         |
| 使用与复核     | 保留实际使用或核对的范围、日期和依据；未使用、未反馈均保持未知。有观察证据时才能写“截至某日在该范围未发现问题”，不能据此声称没有未知缺陷。                                               |
| 同根因复发     | 前一问题已有修复与验证证据，之后出现新的同根因缺陷，保留新版本事件并关联双方证据，另计复发次数，不重复增加缺陷根因数。重复报告、旧问题未修好或重新发现旧问题不算新的复发。               |

返工、缺陷与复发数量从已确认的条目读取，不另维护一份可编辑总数；空白记录不能作为已使用后零缺陷的证据。

### 任务说明短模板

开始时填写已知项，反馈相关条目按实际发生追加；说明保持简短，详细证据使用链接。

```markdown
# 任务：<UUID>｜<名称>

- 原始目标与来源：
- 类型与影响范围：
- 开始时间（含时区；缺失记未知）：
- 首次交付时间与版本：尚未交付；发生后固定保留
- 审查与验证材料：<记录链接，必要时附问题编号>
- 最新交付版本与验收状态：尚未交付／待确认

## 后续记录（按需追加）

- 验收反馈：<日期／版本／状态／依据>
- 返工：<完成日期／原目标内的修正批次／修正版本／证据链接>
- 使用与复核：<日期或观察截止时间／实际使用与核对范围／结果和依据>
- 确认问题：<新问题编号或已有审查引用／发现日期／交付版本／影响与证据>
- 复发关联：<前一问题的修复及验证证据／新的同根因问题证据>
```

### 跨任务评估

用户要求评估整个开发流程时，按任务编号归并材料，一个任务的多次审查和复查只算一个样本。说明选取范围及可比性，按类型与相近影响范围比较；约有 10 个可比较任务时，可按交付先后对照前后各 5 个，不足时展示案例，不作趋势结论。

每次分析列出总任务数、明确验收数（按各任务最新交付版本，通过与需修正分列）、实际使用并复核数、有效时间样本数，同时说明待确认、未观察和缺失数据。修正版尚无反馈时，该任务计入待确认；旧版本反馈仍作为历史证据。对照首次可验收时间中位数、交付后返工轮次、已知缺陷影响及同根因复发案例；未完成或未知时间不参与中位数，零个有效样本时显示无法计算。

结论分别列出改善证据、退化证据和暂不能判断的部分，链接相应任务与证据。变化只作初步信号，不自动归因于某次流程修改，不生成综合评分或真实漏报率；某项检查或审查通过只证明其核对范围，不能代替任务验收或后续使用情况。
