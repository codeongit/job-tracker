# 变更共用规则

本页维护需求澄清、规格与工单交接、实施、诊断、测试和审查共用的证据与记录要求。各技能按当前任务读取相关章节；执行顺序由对应技能维护，技能回引本页时继续当前步骤。

实施步骤见 [implement](../../.agents/skills/implement/SKILL.md)，独立审查步骤见 [code-review](../../.agents/skills/code-review/SKILL.md)。需要选择入口时查阅 [ask-matt](../../.agents/skills/ask-matt/SKILL.md)；明确的小任务可直接实施，无需先生成规格或工单。

## 现状与目标依据

**现状依据：** 从受影响的入口追到主要逻辑及输出，读取关键调用者和依赖，核对相关测试、配置及既有决策。按实际影响检查接口约定、副作用、数据或资源所有权、异常处理、顺序与并发、持久化及后续读取或恢复；纯文字或局部样式调整只核对相应路径。必要时用最小合成输入或获授权的只读验证确认实际行为。

**目标依据：** 从用户原始要求、已确认的业务规则和外部契约确定可观察结果、必须保留的行为及完成条件。区分用户明确要求、当前系统约束、实现者建议和待验证假设；新方案、新 ADR 和新测试同属待审材料。当前行为可包含缺陷，不能仅凭现状决定正确预期。

**适用规则：** 按任务影响从 [AGENTS](../../AGENTS.md) 及[规则保障映射](rule-assurance.md) 选择相关规则 ID，核对条目中各项要求及已知缺口。文件路径和映射用于提示范围，仍须追踪受影响机制；不要求每次勾选全部规则，也不把映射中的验证入口当成本次已通过的证据。

**修改前基线：** 记录任务起点与变更范围。已有提交可用 commit/ref；起点含未提交修改时，保留相关公开文件的修改前副本及状态，在本机临时目录或已有任务笔记中使用。尊重原有修改，记录本任务改变哪些文件；私有材料按项目权限和脱敏规则处理。

按实际影响核对以下内容，交付时按[材料归属](#材料归属与后续反馈)引用已有来源；小改动可用几句工作说明，无需另建背景文档或 ADR：

| 内容 | 要求                                         |
| ---- | -------------------------------------------- |
| 现状 | 关键链路、约束和来源位置；运行结果只说明现状 |
| 目标 | 可观察结果、保留条件及原始要求或契约依据     |
| 影响 | 修改点、受影响的调用者及后续行为             |
| 假设 | 尚未确认的事实，以及如何验证                 |
| 验证 | 关键场景、失败或边界场景、检查入口           |

**完成条件：** 能用来源位置或最小验证解释受影响机制，区分有依据的预期与待验证假设，说明缺口对下一步的影响。分析与草稿可保留未决事项；开始实施的条件见[阶段交接](#阶段交接与可实施条件)。可从代码或已有资料查出的事实由代理核对，已授权事项继续执行；只有确需用户决定的意图或授权缺口才提问，独立工作继续推进。

## 实施前设计核对

在形成方案、准备拆单或直接实施时，按实际影响识别设计变化。改变数据所有权、事务与同步恢复机制，或改变跨模块契约、依赖方向、进程与运行模式的关键变更，须在确定相关工单边界或编码前完成独立设计核对。新增子系统、外部依赖或调整关键 ADR 时，同样核对这些影响。不改变上述边界的局部修复、样式和内部整理，沿用现状与目标核对即可。

按 [系统设计核对](../../.agents/skills/codebase-design/SKILL.md#系统设计核对)说明完整行为路径、责任与状态、失败处理、实际取舍和验证安排。内容放在已有规格或任务说明中，按影响裁剪；不新增固定文档、统计或审批。尚有关键未知时可以探索或交付明确标识的草稿，依赖该决定的拆单与实施等待核对完成。

复用 [Spec 第一阶段](../../.agents/skills/code-review/SKILL.md#4-分派独立审查)：审查者先只取得原始要求、修改前基线及既有规则，独立判断目标与保留条件；保留判断后再提供设计方案，核对其职责、契约及取舍是否支持目标。与适用的[高风险验收条件核对](#验证依据与覆盖)合并安排，分别说明设计和验收的结论；多工单由主协调者统一安排，已有有效结论直接引用。

实施中若所有权、接口契约、事务或恢复策略等受审决定改变，更新原说明，重新核对影响并补做相关独立设计与验收核对，再继续依赖新决定的实施；未受影响的工作和有效证据继续使用。最终审查核对实现是否兑现设计及跨工单连接，前置结论不替代最终 Spec 与 Standards。

**完成条件：** 设计结论、依据和适用范围可定位，会改变正确预期或关键方案的未知已解决，阻断项按[发现与交接](#发现与交接)关闭；设计偏好保留为建议。完成核对后仍按下节检查实施授权及依赖，存在缺口时说明影响与下一步。

## 阶段交接与可实施条件

从讨论整理规格、拆分工单或交给实施者时，保留原始目标及后续修正的来源、已确认决定、必须保留的行为、范围限制、可观察的验收条件，以及未决问题和它们的影响。来源可为用户指示的必要摘要、议题与评论、已有契约或确认记录；链接应足以定位依据。使用必要摘要和具体指针，避免复制整份上游材料。

目标、保留约束和验收条件充分，会改变正确预期或关键方案的未决事项已解决，才符合[可交代理实施](triage-labels.md)的规格要求。任务依赖另行记录，实际开始实施还须满足前置依赖。生成文档、添加标签或写入 ADR 本身不增加确认或实施授权。

沿用仍适用的用户决定、测试接缝和授权；实施时重新核对当前代码与基线，发现变化只补查受影响部分。真正需要用户决定的缺口才提问，能独立推进的已授权工作继续执行。

按下一步实际需要分别记录下列事实，不用一个“就绪”状态推导其他条件：

| 条件             | 判定依据                                                                       |
| ---------------- | ------------------------------------------------------------------------------ |
| 分析或草稿可交接 | 来源、已确认结论、未决事项及其影响可定位；关键未知可以保留在草稿中             |
| 材料可供实施     | 目标、保留约束及验收条件充分，会改变正确预期或关键方案的未知已解决             |
| 可以开始实施     | 材料充分，当前动作在已有授权内，所需前置结果已满足                             |
| 可以交付当前成果 | 本次范围的检查、独立审查与文档维护完成，证据适用于交付版本；适用的人工验收另列 |
| 人工验收通过     | 存在对应版本、场景的明确人工反馈；授权实施、自动检查通过与沉默均不等于验收     |

交接或恢复上下文时，沿用 Issue、PR、规格、Git 提交和原始日志，保留原始来源及修正、必要决定与理由、授权范围、依赖、当前版本及证据位置、未决事项和下一步。已有编号可以沿用，无需为交接另建 UUID。接收者回查最新来源与变化后继续；上下文切换本身不清除有效授权，也不补足缺失授权。

用于实施或跨会话交接的正式规格保存为仓库 Markdown，随 Git 管理，由相关 Issue／PR 引用。需求变化时更新规格并保留关键决定来源及变化说明。普通小任务无需单独规格；聊天中的分析或草稿按请求交付，不因整理材料自动开始实施。

## 验证依据与覆盖

增加测试时，以原始要求、契约或独立推演的已知结果确定断言；用合成材料表达已确认的历史状态。测试预期与被测实现分别核对，避免从本次实现的返回值生成预期，或让当前实现生成事故状态后自行证明正确。

验证覆盖实际影响，复用已有检查和有效反馈循环；检查通过仍需核对目标是否正确。具体命令和浏览器测试分工以[维护手册](../MAINTENANCE.md#每次改动)为准，检查结果对应实际交付的文件版本。

**验收条件前置核对：** 涉及数据迁移、同步、恢复、权限或跨模块契约的关键变更，在实现前由独立审查者核对“原始要求 → 可观察结果 → 失败或反例 → 验证方式”，检查错误实现能否被验收条件区分。适用[实施前设计核对](#实施前设计核对)时合并进行；其他高风险变更仍保留本项要求。复用已有规格或 Spec 第一阶段结论，在原材料中补充即可；普通小改动按影响直接核对，不新增必经文档或重复审批。

**覆盖核对：** 涉及跨层接口、持久化或运行模式变化时，实施与独立审查均核对受影响的入口到结果路径、测试实际经过的生产组件、替身边界，以及对应的验证和仍未验证的部分。发现连接缺少验证时，补充测试或明确剩余限制及对应验收安排。在已有任务说明中按影响简述即可；测试数量或各层分别通过不能证明它们之间的连接已经验证。局部变更只核对受影响路径，不要求每次重列全项目覆盖。

覆盖说明保存在 PR 或当前审查报告中，其他位置引用即可。跨层或高风险改动可用下表；小改动用一两句话表达相同事实，纯文档说明权威来源、受影响正文及引用链路。

| 目标或保留条件       | 受影响路径                             | 验证证据                       | 未覆盖部分                               |
| -------------------- | -------------------------------------- | ------------------------------ | ---------------------------------------- |
| 原始要求及可观察结果 | 入口、实际生产组件、相关依赖与替身边界 | 对应版本的检查、断言或审查位置 | 尚未验证的路径、影响及补查或人工验收安排 |

独立审查对照本任务差异、调用者及依赖，核对覆盖说明是否包含受影响的源码、测试与规则；明确关键错误实现会由哪项验证区分。发现验证遗漏相关输入时，执行受影响检查并复查。范围外的原有改动保留其归属及排除依据，不因工作树有变化就扩大本次任务。

**完成条件：** 目标场景和保留条件能对应到适用版本的路径与证据，错误路径及剩余不确定性明确；缺口是否阻断按[发现与交接](#发现与交接)判断。发现新的影响或原假设不成立时，更新现状与目标核对后继续，按项目规则完成相关检查。

## 证据版本与检查配置

检查与审查结果注明目标来源、适用规则、受检版本、检查配置和覆盖范围。目标、规则、相关源码、测试、依赖或配置变化时，将受影响的结果标为“需补查”，重跑相应检查并复查，保留旧结果及版本；未受影响的证据可以复用。实际执行前后输入发生变化，或最新执行失败、中断、未完成，均不能沿用此前通过作为本次结果。

普通实施任务完成格式化与适用检查后，只将本任务改动保存为任务分支上的本地候选提交，再以该 commit 进行最终独立审查。检查前后核对受检文件是否变化，并确认候选提交与实际受检内容一致；提交只是固定版本，不代表审查通过、工单完成或获准合并。修复后追加提交，按影响重跑检查并复查。

复用旧结果时，比较固定提交之间的相关源码、测试、规则、依赖和检查配置，包含新增及删除文件；目标、输入或执行环境变化时评估影响。无法证明适用的结果重新执行，不从源码相同推定外部状态或环境相同。

检查命令、收集范围、排除与跳过规则、阈值、CI 配置和检查器自身变化，作为验证能力变化审查。对照修改前基线说明覆盖扩大、缩小或等价的依据；先核对目标和保留条件，再决定是否接受新的检查基线。不得用同次降低验证要求来解释原有失败已经修复。所有检查配置变化均须对照任务起点审查。

Git 提交与检查记录用于定位版本及实际结果，不判定授权、覆盖充分性、审查独立性或人工验收，也不是防篡改门禁。普通文件、CLI 和 Hook 可在同权限下被改写；要强制阻止绕过，需要另有受保护的执行入口。本项目现有 CI 与浏览器分工保持，当前没有据此宣称已配置受保护的合并门禁。

## 文档影响与维护

修改 BOSS 行为、归属、业务规则或额度前读 [DESIGN](../boss/DESIGN.md)；修改模块、字段、交付或恢复契约前读 [IMPLEMENTATION](../boss/IMPLEMENTATION.md)；修改命令、状态说明或排障步骤前读 [OPERATIONS](../boss/OPERATIONS.md)。跨类变更读取对应正文，共享事务与恢复仍按[数据与恢复](../DATA_AND_RECOVERY.md)核对。

- 同次变更更新受影响的完整正文，其他入口保留摘要和具体章节链接，避免第二份完整定义。
- 每次交付或 PR 说明影响哪些文档、更新了什么；无需更新时说明核对依据。纯内部重构不机械要求修改全部文档。
- 行为、接口或关键决定变化先分别核对现状与原始目标，再更新正文、代码及测试。历史决定保留理由，关键决定变化按[ADR 维护约定](../adr/README.md#如何维护)新增；待实施方案与历史验收记录明确标识。
- `pnpm check` 检查项目文档的本地链接、标题锚点、ADR 编号/索引及规则编号/保障映射对应，`pnpm format:check` 检查格式。检查不访问外链，不执行映射中的命令，不推断历史版本或业务含义；独立审查核对规则是否准确、例外是否完整及历史范围是否被扩大。

**完成条件：** 文档影响有明确结论、相应正文及引用已更新、结构检查通过，Spec 与 Standards 审查在同一版本确认结果及限制。无需更新的结论同样进入审查。

规格、领域建模或讨论任务实际修改仓库文档时，复用 [implement 第 2—4 步](../../.agents/skills/implement/SKILL.md#2-分步实现与验证)完成适用检查、独立审查、提交与交付；已完成步骤不重做。仅在聊天中交付分析或草稿时说明来源和状态即可。文档交付不扩展为方案实施授权。

## 审查证据与发现

审查输入包括原始用户要求及后续修正、修改前基线、相关既有规则，以及完整的本次变更范围。默认引用本地候选提交及基线；原有改动和本任务改动明确区分。纯只读工作树审查沿用 code-review 的范围与变化核对，不因审查而擅自提交。原始来源、适用规则和所审文件的版本均须可定位，两个审查轴使用同一版本。

Spec 与 Standards 使用相同版本的变更，按 [code-review 的独立审查步骤](../../.agents/skills/code-review/SKILL.md#4-分派独立审查)执行。简单改动按影响缩小材料和输出；原始目标缺失、规格有歧义或与既有规则冲突时，保留具体来源、影响及未完成结论。

两个审查轴同时核对适用规则的选择及证据是否足以支持结论。规则或保障映射变化时，对照基线检查规则删除、含义变化和编号复用，确认部分覆盖与未验证项已明确；结构校验无法判断这些历史和语义问题。

已有审查只有在目标、规则、文件及依赖仍适用时才可复用，注明原记录、范围及版本核对。最终整体验收重点补查跨工单连接、集成变化和未覆盖条件；保持 Spec 与 Standards 对最终范围的明确结论。高风险路径可增加相应专业关注点，按实际影响委派，不固定增加审查角色。

### 发现与交接

按证据区分三类，分别汇报，避免把设计偏好计为缺陷：

- **确定问题：** 给出来源位置、适用要求、触发条件和具体影响，标明是本次引入、加重还是基线已有。仅有代码形状相似或气味名称不足以成立。
- **改进建议：** 说明收益、代价及适用条件；未采纳的建议不自动升级为阻断问题。
- **待核实：** 说明缺少的证据、受影响的结论和核实方式；由代理解决可查证的事实，真正需要用户决定的意图缺口才提问。

阻断项是违反硬约束或妨碍目标、必须保留行为成立的确定问题，以及会改变正确预期或关键机制判断的未决事项；注明阻断理由与解除条件。既有问题按实际影响判断是否阻断，不归为本次新增缺陷；无关建议不扩大本次交付范围。

审查者提出问题与重构建议；实施者在已有任务授权内处理阻断项，判断并执行有收益的重构，按影响验证后交回审查者复查。纯审查任务交付发现与限制，实施交接不自动扩展用户授权。修正后仍保留原发现与处理结果，不把已修复的问题当成误报。

历史发现是否成立与当前是否阻断分别记录，修复不把历史有效问题改成误报。当前阻断项按原问题编号引用修正版本、复查结论及剩余影响。关闭依据须能对应实际交付版本；发现数为零或报告存在本身不证明两个审查轴完成。

**完成条件：** 两个审查轴明确报告分类后的发现、覆盖范围和未核实内容；声称完整审查通过或实施完成前，阻断问题已解决，受影响内容已复查。缺失原始目标或关键机制仍未核实时，Spec 保持未完成。只依据错误或缺失规格得出的“实现一致”不能作为完整验收，测试通过也不能代替目标核对。

## 交付与验收记录

**时间展示：** 面向用户的任务记录、审查报告、交付说明及相关日期时间引用统一使用北京时间（`Asia/Shanghai`，`UTC+08:00`），格式为 `YYYY-MM-DD HH:mm:ss +08:00`；原值含毫秒时保留毫秒，仅显示日期时也按北京时间确定日期。机器生成的原始日志、证据 JSON 和协议时间戳保留原值，引用到说明中时转换展示。修正历史记录的显示格式须保持同一时刻及首次交付语义；来源时区不明时标记未知，不猜测转换。

正式仓库变更按[议题与 PR 约定](issue-tracker.md)交付。Issue 或规格保存需求，PR 保存公开的最终变更、验证与风险摘要，日志与私有诊断材料沿用原位置；同一份完整正文不在多处重复维护，按[材料归属](#材料归属与后续反馈)交付。下列内容按实际影响核对，可合并表达或引用已有材料；详细证据保留原位置：

| 核对项         | 记录要求                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------ |
| 交付版本       | 被测 commit 及基线，核对候选提交与受检内容一致；仅审查工作树时注明范围与变化限制                 |
| 检查有效性     | 引用实际命令、结果与受检 commit；复用旧结果时说明版本、依赖及环境适用性                          |
| 覆盖说明       | 引用[覆盖核对](#验证依据与覆盖)的路径、证据和未覆盖部分；明确缺口对当前交付的影响                |
| 最终审查       | 保存或引用最终两轴结论、依据及适用版本；复用旧结论时保留范围与版本核对依据                       |
| 阻断项处理     | 按原问题编号引用修正版本、复查依据与当前未关闭项；无阻断项须依据实际审查结论，不能从发现数量推导 |
| 验收与外部检查 | 分别说明本地检查、CI、人工验收的实际状态与范围；未取得结果标为未运行、未查询或待验收             |

完成格式化等写入后复核检查与审查版本，再核对最终差异及暂存范围。后续修改按影响补查；适用的人工验收尚未完成时可交付待验收版本，并列出验收项。授权、独立性和覆盖充分性仍依据来源及实际审查判断，不由材料齐全或工具通过推定。待验收版本可以交付审阅，合并条件与授权按[合并与验收](issue-tracker.md#合并与验收)单独核对。

记录本次适用规则依据、实际检查或审查证据、适用版本及剩余未验证项；小改动可合并成一句说明，多个规则共用同一证据时使用同一引用。每项验证使用“通过、失败、未运行、需补查、待人工验收、不适用”之一，不适用附理由；旧证据变化后的有效性按[证据版本规则](#证据版本与检查配置)核对。代码或测试文件存在只证明入口存在，规则保障映射不保存永久通过状态。证据只保留必要的公开摘要和来源，不写入真实求职数据或凭据。

审查结论直接进入 PR 或当前对话的交付说明，详细依据引用原始来源和日志；缺少依据的历史状态保持未知。

用户后续提供验收反馈时，追加日期、对应版本、实际范围和处理结果，链接必要证据。局部反馈仅适用于其版本和范围；代码继续变化时，评估哪些已有结果受到影响，补充相应验证，保留旧结论，不能把旧反馈延用为新版本验收。

**完成条件：** 能确定每项结果对应的代码状态、实际验证范围和剩余限制；后续反馈与改动不会把旧版本结果误作当前版本验收。

## 流程回归与迭代

流程或技能的阶段条件、授权边界、证据规则变化时，从[流程回归案例](workflow-regressions.md)选择受影响场景做独立前向试验，并运行受影响的检查器测试。执行者只取得任务提示和原始材料；预期由裁定者独立核对，保留实际动作及产物，不能用关键词匹配代替行为验证。

实际遗漏或误报按“来源与目标误读、阶段或授权混淆、证据过期、验证覆盖不足、执行遗漏”等原因定位，允许原因保持待核实。先复现有证据的失效，修改负责该规则的最小位置，再回归受影响场景；有收益的旧机制及例外继续保留。在 PR 或当前对话中关联规则提交、案例结果、原始执行日志及剩余限制，审查问题沿用原编号。

后续效果按[任务评估口径](#任务评估口径)观察返工、已知缺陷、复发、误报与交付耗时；样本不足时保持未知。一次情境通过只说明该场景的结果，后续真实反馈再补证。暂缓的改进记录在[流程待办](backlog.md)，不因登记待办而开始实施。

### 材料归属与后续反馈

需求和后续修正保存在 Issue 或规格；关键决定保存在 ADR；源码及审查版本使用 Git 提交；公开验证、两轴审查结论、风险及验收反馈进入 PR。小任务可直接在 PR 说明目标和验收条件，无需另写规格。

原始日志、私有诊断和试验材料在各自位置保存和引用；可能轮转或覆盖的必要现场按已有诊断机制保留最小材料。公开摘要独立说明结果与限制，使外部审阅者无需访问本机私有路径即可理解。

仅本地交付、纯只读审查或远端失败时，在当前对话提供基线、已有候选 commit（只读工作树审查则注明实际范围）、实际检查和两轴结论、剩余事项及已有材料位置；必要正文草稿沿用工具输出位置。交接时引用这些来源并附未决项与下一步。操作授权与失败回查按[议题约定](issue-tracker.md)执行，记录位置不扩大授权。

历史来源保留原状；原始失败与修复结论保持可区分。后续反馈追加到对应 Issue／PR；仅本地事项沿用当前对话及已有材料。缺少可靠起止时间或验收反馈时保持未知，不倒推耗时，也不为填表额外索取反馈。

### 任务评估口径

以下口径供有材料支持的复盘使用，日常交付不要求逐项填写；缺少时间或反馈不阻止交付，也不代表耗时为零、已验收或零缺陷。

| 项目           | 口径                                                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 首次可验收时间 | 实际开始执行已明确目标至首次可验收交付的经过时间，包含等待；不是用户确认验收的时间。只在两端时间可靠时计算，未交付记未完成，缺失或异常记未知，不用审查时间代替或倒推。时间记录包含时区。 |
| 验收状态       | 以最新交付版本为准，默认待确认；仅依据该版本的明确反馈更新为通过或需修正。历史反馈保留日期、版本与依据，不沿用至新版本。实施前的“可以”、检查通过及用户沉默均不自动算验收通过。           |
| 返工轮次       | 首次交付后，为满足原目标完成的一批修正算一轮，记录完成日期与修正版本；同批多个问题只算一轮。交付前修正、测试重跑不计，新需求另记。                                                       |
| 交付后已知缺陷 | 确认存在于对应交付版本且属于原范围后计入；记录发现日期、影响与证据，按根因去重汇总。已有审查问题引用原编号及判定；交付前已修复的审查问题不计入。                                         |
| 使用与复核     | 保留实际使用或核对的范围、日期和依据；未使用、未反馈均保持未知。有观察证据时才能写“截至某日在该范围未发现问题”，不能据此声称没有未知缺陷。                                               |
| 同根因复发     | 前一问题已有修复与验证证据，之后出现新的同根因缺陷，保留新版本事件并关联双方证据，另计复发次数，不重复增加缺陷根因数。重复报告、旧问题未修好或重新发现旧问题不算新的复发。               |

返工、缺陷与复发数量从已确认的条目读取，不另维护一份可编辑总数；空白记录不能作为已使用后零缺陷的证据。

### 跨任务评估

用户要求评估整个开发流程时，从 Issue、PR、规格、提交、对话及原始日志按同一事项归并材料，历史任务记录可辅助定位；一个事项的多次审查、复查和修复只算一个样本。说明选取范围及可比性，按类型与相近影响范围比较；约有 10 个可比较任务时，可按交付先后对照前后各 5 个，不足时展示案例，不作趋势结论。

每次分析列出总任务数、明确验收数（按各任务最新交付版本，通过与需修正分列）、实际使用并复核数、有效时间样本数，同时说明待确认、未观察和缺失数据。修正版尚无反馈时，该任务计入待确认；旧版本反馈仍作为历史证据。对照首次可验收时间中位数、交付后返工轮次、已知缺陷影响及同根因复发案例；未完成或未知时间不参与中位数，零个有效样本时显示无法计算。

结论分别列出改善证据、退化证据和暂不能判断的部分，链接相应任务与证据。变化只作初步信号，不自动归因于某次流程修改，不生成综合评分或真实漏报率；某项检查或审查通过只证明其核对范围，不能代替任务验收或后续使用情况。
