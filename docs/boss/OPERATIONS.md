# BOSS 只读采集与岗位更新：使用与排障

本文回答“现在应该怎么操作”。当前流程和判断条件见[设计说明](DESIGN.md)，代码与字段契约见[实现说明](IMPLEMENTATION.md)。全项目发布、备份与 GitHub 同步步骤仍由[维护手册](../MAINTENANCE.md)维护。

适用版本：应用 0.10.23、规则 v17。各版本当次授权、实际覆盖和验收结果保留在维护手册的历史记录及[ADR](../adr/README.md)，不当作新一轮平台访问许可。

## 运行前提

1. 使用 Node.js 24、package.json 固定的 pnpm 和锁文件，在仓库根目录运行命令。首次环境安装见[新电脑开发](../MAINTENANCE.md#新电脑开发)。
2. 需要本机接入时，在忽略的 `.local/config.json` 配置 bossIntegration 账号标签等固定来源；源码位置固定为仓库 `collector/boss/`，不能由网页指定任意脚本或路径。配置样例见 [`config.example.json`](../../config.example.json)，不要将真实配置提交到仓库。
3. 服务已有正确的正式工作区，并按工作台提示完成首次迁移和账号绑定。首次迁移须保存含草稿的完整备份；空或错误浏览器不能覆盖正式数据，见[迁移要求](../DATA_AND_RECOVERY.md#首次迁移与版本保护)。
4. 平台访问须有用户明确的本轮或跟踪授权。启动服务不登录 BOSS，也不恢复以前跟踪。人工完成登录、验证码及真实页面验收；代理未经另行委托不启动或控制浏览器。

日常操作使用下面的统一 CLI；不要直接反复调用 tracker 或旧 integration 采集命令。详情与历史使用同一账号锁、持久预算及固定脚本，不能为了完成数量绕过限制。

## 命令与操作

### 日常命令

| 命令                                | 用途与结果                                                        |
| ----------------------------------- | ----------------------------------------------------------------- |
| `pnpm service start`                | 单次启动本机服务；尚未确认就绪先看 status，不连续创建新进程       |
| `pnpm service status`               | 只读核对服务实例身份、starting/ready/failed、阶段时间和健康检查   |
| `pnpm service stop`                 | 核验实例身份后安全停止，不按陌生 PID 强杀                         |
| `pnpm boss start`                   | 核对固定配置与工作区，建立/复用任务页，明确开始持续跟踪           |
| `pnpm boss run` / `pnpm boss check` | 明确执行一轮正常采集，同一轮在途复用；不堆积补跑                  |
| `pnpm boss backfill`                | 明确执行一轮公平历史回填，保留游标；不会改为长期回填模式          |
| `pnpm boss pause`                   | 停止后续调度，在途动作安全收尾，保留预算和进度                    |
| `pnpm boss resume`                  | 原因排除并核验后恢复暂停跟踪，不清空预算或自动重建失效任务页      |
| `pnpm boss stop`                    | 等待前序在途轮次结束，停止跟踪，保留已录入数据和用户原有标签      |
| `pnpm boss status`                  | 只读汇总跟踪生命周期、额度、账号绑定、队列、历史进度与详情任务    |
| `pnpm boss doctor`                  | 核对正式工作区、CDP 绑定/策略及生产者暂停，不创建、刷新或采集页面 |

### 有明确原因时使用的恢复命令

| 命令                       | 适用情况与边界                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `pnpm boss recover-page`   | 停止/暂停下显式恢复失效任务页，最多创建或导航一次；核对登录后再明确 start/resume，不循环刷新用户原标签 |
| `pnpm boss resume-details` | 仅解除详情所有权技术阻断；不访问浏览器，不改变账号生命周期，不清空岗位退避或隔离                       |
| `pnpm boss recover-saved`  | 等在途结束后，纯本机补交已保存快照并消费队列；保持停止，不访问 BOSS、不占平台额度                      |

`recover-saved` 先在本机恢复 DOM 已取得的结果，再补交快照；恢复不依赖当前 DOM 开关或额度，不访问浏览器。未知 DOM 切换仍保留核对状态，不自动重放，也不据此清除本机暂停。`recover-saved` 仅在完整恢复后清除快照/检查点类本机暂停。登录、验证码、账号和任务页类问题仍须核对，再走 resume/recover-page；旧磁盘回执与恢复缺口另按[恢复与升级](#恢复与升级)处理。

### 旧材料兼容入口

| 命令                                            | 适用范围                                                 |
| ----------------------------------------------- | -------------------------------------------------------- |
| `pnpm boss preview`                             | 首批固定快照的纯本机预览，不能把首批规则复用于日常采集   |
| `pnpm boss enqueue`                             | 在已有明确范围授权下入队对应首批材料                     |
| `pnpm boss enqueue-yesterday --date YYYY-MM-DD` | 用户明确确认日期后，处理对应“昨天”标签，不从当前日期猜测 |
| `pnpm boss enqueue-resume`                      | 将已保存快照中的简历观察转换入队，仍经当前语义和归属检查 |

这些命令保留旧读取能力，不提供新的平台访问或长期写入授权。历史首批、日期及定点核实的范围在对应 ADR 和维护历史中保留。

### 一轮补录怎样结束

执行一轮 backfill 后，等待命令返回，再用 status 查看本轮请求、已保存快照、覆盖/截断、未完成任务和正式处理结果。有限列表、请求与页数可能未覆盖需要的旧消息；不要把“命令成功”解释为全部历史已读完。

有已保存但未交付材料时，正常轮次会先本机补交而不请求平台。若只需补交，使用 recover-saved；若需要其他旧会话，按实际覆盖和剩余额度另行明确下一轮 backfill，不自动重复或恢复持续跟踪。

## 状态与统计

### 先看三个独立状态

| 状态      | 怎么理解                                                        |
| --------- | --------------------------------------------------------------- |
| 服务      | 本机正式存储及接口是否可用；进程存活不等于身份核对和 ready 完成 |
| BOSS 跟踪 | running/stopped/paused；停止不是服务故障，暂停须看原因          |
| 材料处理  | 采集是否取得/保存，批次是否交付，事实是否正式提交，各自核对     |

“最近成功处理（含本机恢复）”包括纯本机恢复成功。要判断平台是否真实重新读取，须同时看新的采集运行结果、账号/页面检查及实际请求用量，不能只看时间更新。电脑休眠或停机期间不采集，也不补跑错过轮次。

### 页面数字的单位

| 显示                        | 统计什么                                           | 不表示什么                                                      |
| --------------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| 等待资料或证据              | 当前仍有等待应用的消息观察组；卡片内可包含多项观察 | 不等于待建岗位数；归属不足只是等待的一类                        |
| 需要核对                    | 有明确矛盾的消息组，冲突优先显示                   | 不用已处理回执遮住同消息未处理项，也不自动清空                  |
| 人工决定已保留              | 去重的来源应用保护项，包括人工字段和否决           | 不是采集失败，也不应靠补录覆盖；已忽略另列                      |
| 已忽略                      | 用户明确不再自动应用的来源应用                     | 原事实保留，未确认归属，同会话新消息仍独立处理                  |
| 待录入批次                  | 已交付、等待本机服务消费的批次                     | 一个批次可含多个消息或观察                                      |
| 采集批次处理记录 / 本机回执 | 批次去重及恢复核对记录                             | 不证明每条消息都改变岗位，也不证明恢复后事实仍存在              |
| 已有历史检查记录的聊天      | 持久进度中当前无后续检查任务的聊天                 | 不是最近一轮新增聊天数，也不保证全部历史已读取                  |
| 采集次数限制                | 下一轮当前可用额度，过去 60 分钟占用另列           | 历史请求、详情导航、会话操作是不同单位；有上限不代表 DOM 已启用 |
| 故障材料、技术退避/隔离     | 采集/交付技术问题及保存的诊断                      | 与业务 waiting/review 区分，不能删材料减少数量                  |

状态刷新是本机读取，不触发平台采集：BOSS 状态约 30 秒刷新、正式数据约 15 秒检查变化，恢复焦点/可见性也会刷新。短暂失败保留最近状态并标为过期；需要提交正式操作前先刷新核对。展开状态、滚动位置和仍有效选择在当前页面内存保留，不是跨设备状态。

### 等待和核对怎样处理

1. 打开对应观察清单，先看缺项、原因、消息包含的观察和候选岗位；候选不代表归属已确认。
2. 有唯一精确本机目标时，可直接查看候选或进入已有编辑表单。无唯一目标时到岗位列表核对；同公司候选只是线索。
3. 编辑明确保存后，服务通常在下一轮约 30 秒本机消费中重新判断现有材料，不保证固定完成时间，不访问平台。缺标题资料可能被现有精确资料解决，简历含义和归属仍独立检查。
4. 可用的普通资料确认只处理规定范围；人工编辑不确认归属，也不会自动忽略。真正归属冲突没有通用确认或清空入口。
5. 无法补齐且决定不再自动应用的旧等待项，可多选后“忽略所选观察”。确认同时核对消息数和观察数；默认不勾选，不自动清理剩余项。当前状态、revision 或同步冲突变化时刷新重选。

完整应用条件见[人工决定与应用结果](DESIGN.md#人工决定与应用结果)。编辑、资料确认与忽略互相独立，人工忽略无撤销入口。

## 排障

### 确认是在宿主机还是受限环境

先在**实际运行服务的宿主机终端**执行 `pnpm doctor`、`pnpm service status`，再看 `pnpm boss status/doctor`。受限沙箱或容器可能读到共享目录，却不能连接宿主 `127.0.0.1`；其中的 `SERVICE_UNAVAILABLE` 不能证明宿主服务已停止。

判断优先级：宿主终端实时 status 优先；磁盘 tracking、HEAD 和运行记录只说明最后持久状态；沙箱回环失败不能覆盖宿主结果。报告须注明执行上下文，区分服务不可达、已停止和跟踪暂停。连接文件存在或浏览器显示调试中不代表采集和正式录入都健康。

服务 start 未确认就绪时查看阶段时间及 `.local/service/service.log`，不要按 30 秒 CLI 等待窗口推断一定失败。healthCheck 的 timeout、connection_refused、permission_denied、invalid_response、http_error、identity_mismatch、transport_error 分别表示不同检查结果，只有 ok 才是通过。start 对存活进程的超时/拒绝连接最多补查一次；status/doctor 不自动杀进程、清理记录或另建实例。通用服务诊断的完整机制见[维护手册](../MAINTENANCE.md#排障)。

### 按 BOSS 错误范围处理

| 现象或错误                                      | 下一步                                                                                                          |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `LOCAL_UNAVAILABLE / SERVICE_UNAVAILABLE`       | 宿主终端核对服务；页面暂时刷新失败先刷新本机状态，不据沙箱结果重启                                              |
| `SERVICE_START_NOT_CONFIRMED` 或 starting       | 看实际阶段、进程身份和日志，复用当前启动，不反复 start                                                          |
| 页面与已核实服务版本不同                        | 停止并单次升级服务，再刷新页面；跟踪授权不会自动恢复                                                            |
| `BOSS_CHECK_TOO_SOON`                           | 不重复触发同轮；核对是否使用旧脚本，不使用旧 45 分钟/每日 16 次限制                                             |
| `BOSS_USE_UNIFIED_RUNTIME`                      | 改用 pnpm boss run/check，由统一控制器签发单次票据，不直连旧采集入口                                            |
| 平台动作预算耗尽                                | 看滚动小时额度和下次可用时间；本机处理可继续，不重启清零或连续补录                                              |
| `BOSS_INTEGRATION_PAUSED`，登录/验证码/账号不符 | 保留 incidents，人工排除原因并核验账号后明确 resume；不自动登录或绕过验证码                                     |
| 主任务页失效、实例变化或网址漂移                | 停止/暂停后明确 recover-page，核对登录再恢复；不循环导航用户原标签                                              |
| `LOADED_LIST_NOT_READY`                         | 核对采集任务页登录、验证及列表挂载；该码不单独证明网络、登录或结构变更，持续失败保留暂停检查提取规则            |
| 无副作用的 CDP 传输失败                         | 查看有限重连与等待状态；已发未知请求不重放，身份错误不属于传输重试                                              |
| 已保存快照转换、入队或录入失败                  | 保留快照、检查点、诊断，修复后 recover-saved 纯本机补交，不重新采集替代恢复                                     |
| `JOB_EXPORT_FAILED`                             | 修复私有岗位 Markdown 导出，已保存 JSON 保留；分别核对快照和交付，不能按清单失败判定材料未保存                  |
| 详情退避或技术隔离                              | status 查看 detailEnrichment 和 nextRetryAt；核对实际失败、等待退避，不删任务清零；成功证据保存后才清除对应失败 |
| `DETAIL_TITLE_NOT_READY`                        | 核对页面加载、完整标题和验证码；部分标题或读取失败不是职位关闭依据                                              |
| 详情标签丢失、网址变化或导航/读取超时           | 属 detail 级，停止详情批次，保留现场；列表、历史及本机录入可继续                                                |
| `DETAIL_TAB_OWNERSHIP_MISMATCH`                 | 保留目标现场，排除归属问题后明确 resume-details；仅解除详情阻断，不恢复账号或清空退避                           |
| 队列待录入、坏批次或账号依赖暂停                | 检查服务、首次迁移、账号绑定、局部同步冲突和安全诊断；不删队列，不跳过账号失败顺序                              |
| `waiting / review / protected`                  | 分别看缺项、实际矛盾或人工决定；不统一当作采集错误或全部忽略                                                    |
| `no_effect / observation_only`                  | 纯卡片仅存档、不确认发送/接收/归属；明确冲突和缺稳定消息 ID 仍独立处理                                          |
| `WORKSPACE_REVISION_CONFLICT`                   | 读取最新正式版本、保留草稿并重新核对；不改算并自动重放用户修改                                                  |
| 旧浏览器未迁移或工作区身份不同                  | 下载含草稿完整备份并核对后明确迁移/切换；不清空 IndexedDB 绕过保护                                              |
| 未知协议、字段或未来格式                        | 保留原件，升级兼容客户端/服务；不删字段、不降版、不改为静态独立写入                                             |
| 活跃写者、HEAD 或服务所有权不符                 | 保留工作区和日志，核对实例/外部修改；不手工删锁、改 HEAD 或按旧 PID 强杀                                        |
| `WORKSPACE_DURABILITY_UNCERTAIN`                | 停止继续写入、保留整个工作区；重启核对实际 HEAD 和原命令结果，未确认前不重提业务或发回执                        |
| 已回执但当前来源事实或应用缺失                  | 可能恢复了旧备份，按当前 revision 明确核对固定批次重放；不把旧回执当已录入，不复活删除岗位                      |
| 诊断或关键保存失败                              | 检查权限、磁盘和安全路径，保留未确认进度；不删除现场或假报完成                                                  |

如果旧故障轮已经发出请求却未记用量，修复不自动补写旧预算；当前没有人工补记命令。保持暂停到相关轮次退出滚动窗口，再明确恢复，不直接改 tracking 或重启清零。

服务、SSH、GitHub、备份等通用错误继续查[维护手册排障表](../MAINTENANCE.md#排障)。对外提供版本、固定错误码、执行环境和复现步骤，不贴真实消息、简历、完整带凭据链接、私钥或 PAT。

## 恢复与升级

### 按材料分别恢复

| 情况                               | 处理方式                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| 已保存快照尚未交付                 | recover-saved 本机校验并补交；保持停止，不访问平台                                         |
| 历史页已有检查点但进度未完成       | 先重放已有观察及不足原因，再确认进度；尚未读取的页另需正常授权与额度，不能删检查点强制重读 |
| DOM 结果已取得但材料或进度未保存   | recover-saved 从 result_ready 纯本机重放；旧 switch_issued 结果未知保持核对，不重发动作    |
| 正式工作区恢复旧备份后存在来源缺口 | 使用页面当前版本的明确恢复确认；旧回执不能证明事实存在，固定批次仍执行当前规则             |

工作区“合并恢复”和“回到快照”是正式数据恢复，与采集 recover-saved 不同，均按[数据与恢复](../DATA_AND_RECOVERY.md#两种恢复)形成新的本机编辑并保留当前基线与删除语义。备份、冲突双方、人工决定及缺口检查不能以清空材料替代。

### 升级与回退

升级前停止跟踪，下载完整私有备份，保留 `.local/workspace/`、队列、快照、运行状态、检查点和故障原件。按照[发布步骤](../MAINTENANCE.md#发布)完成非浏览器检查；只有服务代码/配置变化才单次重启，页面资源变化刷新页面。升级后跟踪仍停止，需要采集时由用户明确 start/resume。

0.10.23 的模块移动不需要数据迁移；共享数据 v4、工作区 v3、备份 v2、规则 v17、快照与批次 v8、历史检查点 v6 保持，仅 DOM 检查点内容升至 v2 并读取旧 v1。根目录 CLI 命令保留，源码位置与私有默认路径由固定仓库路径计算，测试仍使用合成材料。

当前应用与规则版本不等同于共享、工作区和私有格式版本，见[版本表](../DATA_AND_RECOVERY.md#版本与两种存储模式)。旧程序不能写入无法识别的材料；回退前在副本验证恢复，不裁剪新字段、替换 HEAD、删除 catalog、检查点或历史。正式历史完整审计是纯本机操作，正常启动和旧历史按需检查的区别见[本机不可变提交](../DATA_AND_RECOVERY.md#本机不可变提交)。

新版本不要求为字段核实反复全量采集；定点真实核对必须针对新问题另有明确只读授权。过去首批、日期、当日补状态或单会话定点权限仍是过去范围，不由文档整理延续。

## 人工验收

代理运行合成非浏览器检查，真实浏览器及平台验收由用户负责；未确认时保留待人工验收，不能以测试通过或已存本机回执代替。实际操作只在明确授权的范围中进行。

- 启动服务后 BOSS 仍停止；显式开始才采集，停止不关闭用户原标签，页面关闭后已授权本机处理仍继续。
- 一轮 run/backfill 的实际范围、请求用量、快照、批次和正式结果分别正确；额度、分页和失败剩余项可理解。
- 明确简历发送/查看正确联动，普通卡片、作品集、引用文字不误报；同公司不同岗位、错误联系人、会话换岗和跨岗位重复继续拦截。
- 人工字段、否决、已忽略、平台关闭及删除标记保留；一条消息多观察汇总、选择数量、候选标签、就地查看/编辑和返回位置正确。
- 本机故障、详情阻断和业务等待分别显示；恢复不重复应用，不凭旧回执补造事实；GitHub 保持手动同步。

具体版本的已执行结果及未完成验收见[维护历史](../MAINTENANCE.md)，不要在本页重复累积当次数量、真实岗位名称或平台样本。
