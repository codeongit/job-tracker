# 研发流程评估

评价对象是**流程机制或一次流程调整**，任务是提供证据的样本。回答该机制是否以合理成本改善交付，形成保留、调整、有限试点或继续观察的建议。既有会话复盘可作为来源，不要求先执行其他复盘技能。

用户按需调用时执行本次评估，默认只读并在当前对话交付报告；建议的实施及定时安排作为另外的任务处理。遵循仓库的权限、隐私与测试分工，只读取评估所需的研发材料。

## 1. 明确问题与范围

读取根目录 `AGENTS.md`、`CONTEXT.md`、ADR 索引及相关决定，沿用[变更共用规则](../../../docs/agents/change-workflow.md)的证据与记录口径。说明机制原本要防止什么问题、适用哪些任务，以及比较的流程版本或基线；评估历史执行时使用当时适用的规则。

- **总体评估**：先建立概览，再选择少量值得深入判断的机制。
- **指定机制**：围绕用户的问题选择任务和相关证据。
- **调整效果**：回查原预期、实际实施提交和后续反馈，区分接受建议、已经实施和效果已观察。

用户指定范围优先。首次未指定时以最近 30 天为观察窗口，写明起止日期和截止点；后续优先读取上轮截止之后的新任务及新反馈，包括旧任务的新状态。上轮结果不可取得时说明限制并明确本轮范围，不凭记忆续接。窗口内仍在进行、取消或失败的任务保留在范围说明中；无新增材料时简短说明即可结束，不重复整轮调查。

**完成条件：** 评估问题、观察范围、比较基线和资料缺口明确，能够说明接下来要查什么及其用途。

## 2. 归并样本并核对证据

按[材料归属](../../../docs/agents/change-workflow.md#材料归属与后续反馈)定位原始要求、Issue、PR、提交、会话、执行日志及验收反馈。按同一目标归并事项，多轮审查、多个 PR 和后续修复不重复计为独立任务；无法归并的关联保持待核实。先看摘要与索引，仅为影响判断的疑点追查原始材料，原始记录留在已有位置。

区分观察窗口内的事项集合与实际深查样本。默认深入约 3 个有代表性的案例，兼顾顺利交付、发生问题和证据不足；材料不足时使用已有案例，必要时按影响扩大并说明理由。按类型与影响范围选择可比任务，报告纳入、排除和选择限制。目的抽样用于解释机制，不能据此推断总体受益比例或真实漏报率。

分别核对原始目标、实际执行和后续结果。报告存在或检查通过不能单独证明规则已执行、需求已满足或已经验收；取得的工具输出可能有限，截断或不可回读的关键证据保持明确缺口。需要新验证时依任务范围和权限取得，并与历史结果分开。

**完成条件：** 样本归属与选择依据可解释，关键结论能回指适用版本的原始证据，未观察部分可定位。

## 3. 分别判断落实、效果与投入产出

指标定义、样本数量及比较条件直接使用[任务评估口径](../../../docs/agents/change-workflow.md#任务评估口径)和[跨任务评估](../../../docs/agents/change-workflow.md#跨任务评估)，不另设综合评分或修改验收标准。

| 维度     | 核对内容                                                                               | 判断边界                                                                             |
| -------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 落实     | 适用规则是否实际执行，是否重复执行，偏离发生在哪里及其原因                             | 区分已执行、执行遗漏、不适用与无法确认；执行失败不直接证明机制无效                   |
| 效果     | 需求满足、验收与实际使用、返工、已知缺陷、同根因复发及首次可验收时间                   | 同时呈现改善、退化与未知；无反馈不等于零缺陷，演练通过不等于真实收益                 |
| 投入产出 | 一次性改造、日常执行、等待与交接、误报处置、工具维护和评估自身投入，相对于已有收益证据 | 分开列成本与收益，缺数据保持未知，不把经过时间当成人工工时或把并行耗时相加为交付时间 |

比较时核对需求复杂度、风险、模型、工具、代码成熟度及观察期等差异。“调整后改善”只是一项关联证据；没有可信对照时不归因为调整的结果，也不将未发生的事故折算成已实现收益。样本不足时给案例判断，不倒推耗时或编造 ROI 百分比。

隐私、授权、数据恢复等低频高损害保障，需检查风险是否仍在、真实失败路径是否受保护及是否有等效保障；长期没有事故本身不足以支持移除。执行成本偏高时可评估触发范围或替代措施，并说明残余风险。

**完成条件：** 落实、效果和投入产出各有明确判断，观察事实、推断与未知可区分，比较限制及安全边界未被掩盖。

## 4. 交付判断并接续观察

先给总体结论，再按实际影响提供简短报告：范围、机制与流程版本、样本与数据缺口、三个维度的证据和判断、优先建议及下一次观察条件。按共用评估口径交代总任务数、验收、实际使用复核及有效时间样本，区分总体与深查范围。公开摘要能独立说明结论，不依赖私有材料才能理解。

每项建议包含：**问题与来源 → 最小调整及落点 → 预期收益与新增成本 → 保留条件 → 验证与重新评估条件**。先判断现有机制能否解决问题，再考虑新增、调整、简化或移除。只给值得推动的建议，允许维持现状或继续观察；规则更短、发现更多或新规则被遵守，本身都不是收益证明。

报告保留本轮截止点、纳入事项的来源、未决假设和待观察建议。接受、实施与效果分别记录，实施后关联实际 commit／PR；下一轮依据新增任务和反馈更新支持、反对或仍未知的判断，不把批准或实施完成当作效果成立。复用原报告和来源，不要求所有任务新增填表、计时或另建历史台账。

已获授权的后续实施按[流程回归与迭代](../../../docs/agents/change-workflow.md#流程回归与迭代)及仓库交付流程另行推进。评估本身若持续消耗材料整理成本却不能支持决定，也应提出缩减范围或降低频率的建议。

**完成条件：** 接手者能定位判断依据、适用范围及下一步；新增证据能用于复核具体假设，而非重新开始整轮调查。
