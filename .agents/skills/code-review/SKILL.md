name: code-review
description: 审查分支、拉取请求或工作树改动是否符合项目规范和原始需求。先独立核对现有机制与目标行为，再判断实现。
---

分别从两个维度审查：

- **规范（Standards）**：改动是否符合仓库的编码规范？
- **规格（Spec）**：对现有机制和目标行为的理解是否正确，改动是否满足原始需求？

审查前读取[变更共用规则](../../../docs/agents/change-workflow.md)中的现状与目标依据、审查证据、发现与交接规则。本技能维护固定材料、两阶段独立审查和汇总步骤；专项统计按需启用。

## 流程

### 1. 固定基线与完整审查范围

复用任务已记录的基线与范围。将每个引用一次性解析为具体提交，注明审查目标是已提交版本还是当前工作树。比较已提交版本时，固定共同祖先（merge-base）和目标 HEAD，并记录提交列表。只有确实缺少范围选择时才提问，同时继续检查已知材料。

同时固定原始要求及本轮实际采用的技能、共用流程和相关规范版本：可引用具体提交中的文件，或保存必要副本和文件哈希。来源含后续修正时保留其依据；本次修改的规则仍是待审材料。审查开始、结束及交付前核对目标、规则和文件是否仍适用，变化后补查受影响范围。

材料和结论放在已有本地记录或其附近即可，无需统计编号或统计工具生成的目录。只有明确选择专项观察时，准备材料前按[专项审查统计](#6-按需启用专项审查统计)启动；普通审查直接继续，不运行统计命令或填写统计 JSON。

审查工作树时：

- 保存 `git status --short` 和 `git diff <resolved-base>`；后者包含已暂存与未暂存的改动。同时保存变更的受跟踪文件及其基线内容。
- 用 `git ls-files --others --exclude-standard` 列出新增文件，保存相关文件的内容，遵守项目隐私边界，排除被忽略的私有数据。
- 用已保存的修改前副本区分原有本机改动与本任务改动。缺少副本时，声明实际采用的更大范围或无法归因的部分。
- 在本地记录中保存或引用必要的公开基线、差异、新文件内容、来源和文件哈希；保留可供后续核对的材料，避免长期引用会被清理的临时文件。两个审查者使用同一份固定版本；材料变化时重新保存受影响部分。

已有[本机证据记录](../../../docs/agents/task-evidence.md)时，引用其快照摘要与审查范围，开始及结束审查时核对版本；工具只核验版本和命令结果，仍须独立判断目标、覆盖充分性及检查配置变化。

已提交版本之间没有差异，不代表工作树审查结束；仍须纳入受跟踪文件的工作树差异及相关新增文件。**完成条件：基线、目标与规则版本、纳入的文件和范围限制均可定位；未启用统计不影响材料固定。**

### 2. 定位目标依据与规范

查找原始要求及后续修正，或起始议题、规格。议题引用遵循 `docs/agents/issue-tracker.md`；复用用户提供的路径，或检查 `docs/`、`specs/`、`.scratch/` 中相关的原始规格。按[目标依据规则](../../../docs/agents/change-workflow.md#现状与目标依据)处理证据，将无法取得的依据记为限制。

读取相关项目指令与规范，例如 `CODING_STANDARDS.md`、`CONTRIBUTING.md`。为规格审查保存基线中的决定和契约，为规范审查保存适用规范。本次修改的规则和测试仍是待审材料。报告缺失的必需指针，并继续依据可用材料审查。

### 3. 结合上下文检查代码气味

仓库已有规范优先于下列气味清单。用气味追查具体维护成本；仅凭代码形状不能判定违规。提出重构时，按共用流程的发现分类说明收益、代价与适用条件。机械规则交给工具检查。

- **含糊命名（Mysterious Name）**：名称是否掩盖了领域概念、动作或结果？改名能否在表达清楚的同时保留必要兼容性？
- **重复代码（Duplicated Code）**：这些代码是否表达同一业务规则，并因同一原因变化？共用实现能否减少重复知识，同时避免耦合无关行为？
- **依恋外部数据（Feature Envy）**：将行为移近数据，能否减少跨模块接口泄漏的知识，并符合所有权约定？
- **数据泥团（Data Clumps）**：反复同行的字段是否构成完整概念，组合后能否让调用契约更清楚？
- **基本类型偏执（Primitive Obsession）**：使用基本类型是否迫使调用者重复校验或解释，而这些职责本可由领域表示承担？
- **重复分支（Repeated Switches）**：这些分支是否重复表达同一判断规则？统一判断带来的调用简化，是否大于实现增加的复杂度？
- **霰弹式修改（Shotgun Surgery）**：分散改动暴露的是职责重复，还是现有责任模块之间的必要协作？调整归属能否真正让后续变化集中？
- **发散式变化（Divergent Change）**：无关职责是否相互耦合，拆分能否减少调用者需要了解的知识或降低修改风险？
- **夸夸其谈的通用性（Speculative Generality）**：抽象、参数或扩展点是否服务于当前需求或已接受的约束？删除后能消除哪些复杂度？
- **过长消息链（Message Chains）**：连续访问是否暴露了调用者不该了解的内部结构，还是在使用完整一致的公开接口？
- **中间人（Middle Man）**：移除转发层会消除复杂度，还是把协议、适配或兼容性知识推给调用者？用[删除检验](../codebase-design/SKILL.md#删除检验)判断其价值。
- **拒绝继承契约（Refused Bequest）**：忽略继承行为是否破坏了所承诺的契约，改用组合能否更清楚地表达实际契约？

### 4. 分派独立审查

向**规范审查者**提供固定的差异、新文件内容、适用规范和气味清单。材料已固定且独立执行槽位充足时，优先与规格审查的第一阶段并行；Spec 内部仍保持下面的两阶段顺序。协调者按审查所需容量安排同时进行的任务，避免槽位都被等待子审查的执行者占满。容量或材料不足时先推进可执行步骤，并在已有记录中说明等待原因；不为凑齐并行而暂停全部工作。沿用实际调度记录核对开始、完成及重叠情况，不另建计时台账。

在独立上下文中启动**规格审查者**（工具支持时使用 `fork_turns: "none"`），分两次提供材料，两个阶段使用同一个审查者：

1. **独立核对现状与目标。** 提供原始要求、明确的基线来源和相关既有规则，由审查者独立列出机制、预期影响和保留条件。此时不提供实现者结论、新方案、新 ADR 或修改后的测试。保留它的判断，对同一目标复用，无需重复要求用户确认。
2. **对照修改。** 再提供同一范围的固定差异、新增文件和测试，核对前一步判断。原始规格存在歧义或与既有规则冲突时，报告具体来源和影响；实现者假设保持其原有确认状态。

无法获得独立上下文时，先推演基线再看改动，并说明独立性降低。Standards 审查按项目规范独立检查相同版本的变更。简单改动按影响缩小材料和输出，两阶段仍可各用几句话完成；审查期间文件变化时重新核对受影响内容。

按受影响路径调整探索范围，按[覆盖核对](../../../docs/agents/change-workflow.md#验证依据与覆盖)对照任务差异、实际路径与证据声明，留下覆盖充分性及限制的依据。通过代码、测试或获授权的检查解决事实缺口。审查者发现固定范围之外的新依赖时，保存相关基线和目标材料，重新核对受影响结论。每个审查轴的最终报告保持简洁（通常不超过 400 词），详细覆盖材料引用已有任务记录。

同一目标已有前置验收审查或局部审查时，按[证据复用规则](../../../docs/agents/change-workflow.md#审查证据与发现)核对版本与范围；保留有效结论，补查集成、依赖变化和遗漏路径，最后明确两个审查轴对完整交付范围的结论。

### 5. 汇总与交接

分别使用 `## 规范审查` 和 `## 规格审查` 输出报告。遵循共用流程的[发现与交接规则](../../../docs/agents/change-workflow.md#发现与交接)：为每项发现给出稳定编号、位置、证据和具体影响；两个审查轴讨论同一根因时，引用同一个编号。

末尾分别列出各轴的确定问题、建议和待核实项数量，影响最大的一项及覆盖限制。附上文档影响结论。将已完成的检查与待完成的验证分开，明确本轴结论适用的版本及当前阻断项；修复后的复查按原问题编号核对解除依据，保留历史发现判定。满足共用完成条件后再宣称通过。短结论可直接写入本地交付记录，详细依据按需引用；没有统计编号不影响审查交付，也不因此向 Issue／PR 追加记录。

### 6. 按需启用专项审查统计

仅明确选择专项观察时执行本节。准备材料前，在仓库根目录运行 `pnpm review:metrics start --case "案例名称" --type docs|code|mixed`，保存返回编号；修复后复查增加 `--parent 原编号`。从实际启动时计时；中途才决定启用时，不把之前未采集的过程补成完整历史样本。

统计由主代理串行维护同一编号，数据保存在已忽略的 `.local/reviews/<编号>/`。工具保存审查技能和共用规则的 `rules/` 副本，其他适用规则仍按第 1 步固定；已有材料可直接引用，无需另存一套。输入格式、可用参数和迁移方式读取 `pnpm review:metrics --help`；脚本入口见 [review-metrics.mjs](../../../scripts/review-metrics.mjs)。既有接口和历史记录继续可用，不为启用统计改写旧材料。

- 首次汇总报告形成时，调用 `finish <编号> --input <首报 JSON 路径>`，保存固定版本依据、报告正文与问题明细。即使仍有待修复问题，也在此时结束首次计时；重复结束不改写首次报告。最终交付附脚本输出的统计摘要和记录链接。
- 同根因使用同一发现编号，数量从明细计算。建议和范围外既有问题单列；有效、误报与待确认分别记录。通过复现、规则核对或有依据的反馈确认判定，报告自己的断言不算确认。未采纳、未修复或已经修复都不等于误报。
- 收到有依据的反馈后，调用 `feedback <编号> --input <反馈 JSON 路径>`，按编号更新判定或补记遗漏；保留原报告及证据引用。遗漏须确认在原受审版本中已经存在且属于约定范围，新回归归入新版本。
- 遗漏复核显式提供 `followup` 的范围与证据，记录核对日期。单项反馈不代表整次复核；“已知遗漏 0、尚未复核”不能解释为确认无遗漏。
- 首报经过时间按准备材料至首次汇总报告的实际经过时间计算，包含等待及首报前穿插的修复，并行代理时间不相加。有修复重叠时在报告中说明，不扣除修复时间或称为纯审查用时。修复后的复查使用关联原编号的新记录；反馈不改写首报经过时间。未完成、缺失和异常时间单列，不补估。

需要汇总时调用 `stats`。按变更类型、实际技能与流程版本、首次或复查分组，并核对范围是否可比较。每组至少五个可比较的已完成样本才汇总误报占比 `误报数 /（有效数 + 误报数）`、待确认数、已知遗漏数和首报经过时间中位数，同时注明总样本、复核情况与首报经过时间有效样本数；分母为零时无法计算，缺失或异常时间不参与中位数。未知版本单列，不用于效果比较。没有独立建立的完整缺陷集时，不计算漏报率。
